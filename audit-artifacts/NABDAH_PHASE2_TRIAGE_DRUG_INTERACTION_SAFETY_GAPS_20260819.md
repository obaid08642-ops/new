# Phase 2 Patient — symptom triage and drug-interaction safety gaps

## Confirmed defects

| Priority | Finding | Evidence | Required remediation |
|---|---|---|---|
| **P0** | Drug interaction scanner client and Backend contract are incompatible | Client sends `{meds, newDrug}`; compatibility route accepts `{drugs, drug}` and therefore ignores the new drug. Client expects `safe_interactions`, severity `major/moderate/minor`, title, colour, drug pairs, description, and advice. Backend returns only `interactions: [{severity: high/moderate, note_ar}]` plus `safe`. Any true hit can crash when the client maps missing `interaction.drugs`; failure/no data is displayed as zero dangerous interactions. | Define one versioned, typed, owned interaction DTO; reject an empty/incomplete request; render a safe unavailable state on every error; add contract tests for no-hit, high-risk hit, malformed medication, and unavailable service. |
| **P0** | Scanner claims a large clinical database but uses five static compatibility rules | UI claims “50,000+ interactions”; Backend scans five hard-coded rules only. This is materially misleading and cannot be relied on for medication safety. | Remove the capability until an approved licensed drug-interaction source and clinical governance are available, or label it narrowly as a limited advisory rule checker with its verified coverage; never state unsupported coverage. |
| **P0** | Drug-interaction compatibility endpoint lacks local JWT guard | `AiInteractionsController` in the compatibility module has no `@UseGuards(JwtAuthGuard)` despite receiving `@CurrentUser`; it cannot reliably bind the request to an owned medication record. | Add explicit authentication and patient-only authorization, validate/resolve only owned medications and approved submitted medicine identifiers, rate-limit/audit access, and test unauthenticated/foreign requests as denied. |
| **P0** | Symptom triage is a generic LLM chat presented as medical classification | `/ai/triage/chat` merely forwards user-supplied conversation to a generic “helpful” medical-assistant prompt and returns unstructured text. It has no clinical red-flag protocol, output schema, safety disclaimer, emergency decision contract, or trusted source routing. | Suspend diagnostic/triage claims until a clinically governed protocol and structured response are approved; include visible limitations, crisis/red-flag instructions, audit/rate limits, and fail-closed emergency/consent behavior. |
| **P0** | Triage UI fabricates tests/actions and has a dead non-emergency action | If optional `urgency` appears, UI inserts fixed ECG/cardiac-enzyme or vitals tests irrespective of clinical input. The consultation button body is empty; only emergency pushes an unapproved emergency route. | Remove fabricated tests and unsupported referral outcomes; use only validated Backend actions; keep SOS/QR/emergency fail-closed pending legal/product approval. |
| **P1** | Scan failure is indistinguishable from a safe result | Catching an API error sets `interactions: []` then displays a reassuring result and “no known safe interactions.” | Preserve error status, require retry, and explicitly state that interaction information is unavailable rather than safe. |
| **P1** | Medical suggestions and labels are Arabic-only and lack accessible context | Triage introduction, medical claims, errors, recommendation card, scanner content, and hard-coded medicine suggestions do not cover six locales or user-safe descriptions. | Move to reviewed translations and accessible labels; do not hard-code common-drug recommendations without clinical catalog/region verification. |

## Decision

Both patient-facing AI medical capabilities are **P0 FIX/BLOCKED**. They must not be represented as diagnostic or complete drug-safety services until their contracts, clinical governance, authorization, truthful availability/error behavior, localization, and emergency boundaries are corrected.
