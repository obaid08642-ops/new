# Semantic evidence — Mobile Pharmacy Payment

Baseline: `22526bedb77a3d8148219036367e4714f401aecc`.

`audit-work/source/nabd_plus_patient_app/app/pharmacy/payment.tsx:38–60` reads `GET /orders/{orderId}` and derives the displayed amount from server order total or insurance copay, subtracting wallet-applied amount. This is preferable to route-param/client subtotal math, but the source does not visibly validate the route identifier before requesting, assert owner-scoped 404/401 behavior, reject terminal/cancelled orders, or distinguish a missing/partial/inconsistent payment state. Load failure has a retry UI (`:104–126`) but no typed error mapping or support for forbidden/not-found versus transient failure.

`handlePay` (`:64–102`) bypasses online charging for cash, already-paid, or zero-remaining orders and navigates to tracking; otherwise it calls `POST /payments/intent/pharmacy/{orderId}` with `paymentIntentHeaders('pharmacy', orderId)` and requires a transaction ID before routing to shared processing. The idempotency helper is a positive control, but no client-visible intent replay/result correlation, amount assertion against returned transaction, order-state precondition, or duplicate-navigation guard is present. Empty/malformed `orderId` is silently ignored. Cash and zero-amount paths do not visibly confirm the server has accepted/settled the order or that tracking is available.

Insurance behavior uses local fields `payment_method`, `insurance_status` and `insurance_copay` (`:53–59,175–183`) and disables payment while not approved, but no explicit eligibility response, authorization reference, coverage denial, copay freshness, claim/preauthorization transition or retry is handled. Wallet-applied amounts are trusted from order payload and the screen does not show wallet debit reversal/reconciliation. The UI claims secure Moyasar processing (`:195–217`) but does not itself handle hosted checkout return/cancel; it delegates to `/payments/processing` and therefore requires cross-screen contract verification.

The screen has load-error retry and a generic intent failure alert (`:104–126,97–101`), but no explicit handling for 401/403/404 ownership, stale order, duplicate intent, provider timeout after authorization, cancellation/return, webhook delay, amount mismatch, or payment reconciliation. Required verification includes live route/method/status checks; owner/stranger/unauth; idempotent intent replay; amount tamper and order-state mismatch; insurance approval/denial/partial coverage; wallet race/refund; cash/pickup; hosted return/cancel/timeout; app restart and webhook reconciliation. No Phase 0 remediation was made.
