# Semantic evidence — Mobile Pharmacy Checkout

Baseline: `22526bedb77a3d8148219036367e4714f401aecc`.

`audit-work/source/nabd_plus_patient_app/app/pharmacy/checkout.tsx:47–68` reads `/users/me/profile` and chooses a default address, while insurance presence is inferred from `profile.insurance`; failures are only logged and the screen continues with an empty address. It also reads `/wallet/balance`, but failure silently leaves balance at zero. There is no explicit address refresh after returning from the picker, no validation of address ownership/precision/availability, and no user-visible retry state.

Coupon validation and loyalty quote use POST endpoints (`:73–97`) but no visible Idempotency-Key, stale quote/version binding, or server quote correlation is present. The page computes delivery fee, discounts and total from local `subtotal` and server-returned display aids (`:70–79,120–123`). The UI labels multiple payment methods and conditionally exposes wallet/split/insurance (`:99–114,301–333`), but selection alone does not establish a payment intent, insurance eligibility/authorization, wallet reservation, split-payment semantics, or method-specific failure/retry state.

The create payload (`:125–167`) sends local item IDs, client names and prices, address coordinates, delivery mode, payment method, coupon and loyalty points, and sends `prescriptionUrl` as `prescription_id`. No visible Idempotency-Key is supplied, so retries/double taps are not demonstrably replay-safe. The source does not visibly obtain a server cart/quote or validate that item IDs, quantities, prescription identity, address and payment context belong to the authenticated patient; it relies on comments that the server will validate. The client sends a URI where a server prescription ID is expected, creating a contract-risk and PHI/file-storage ambiguity.

On success, wallet orders clear the local cart and route directly to tracking, while every other method routes to waiting-for-pharmacy (`:169–181`). Empty order ID is not rejected before navigation. There is no visible payment-intent handoff for card/Apple Pay/Moyasar, insurance authorization result, cash constraints, split settlement, refund path, or reconciliation after app restart. The UI’s local total remains authoritative-looking despite server recalculation.

The UI has loading/submitting and generic error alert paths, but no explicit state for partial payment, payment cancellation, wallet insufficient race, coupon invalidation between quote and order, address changed/stale, insurance rejected, server price/stock mismatch, duplicate order, or missing order ID. No Phase 0 remediation was made.
