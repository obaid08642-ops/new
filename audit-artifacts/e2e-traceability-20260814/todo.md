# قائمة تنفيذ خريطة التحقق واختبارات E2E

- [x] حصر الاختبارات على طلبات قراءة فقط ما دامت البيئة المتاحة إنتاجية.
- [x] تصنيف كل حالة E2E إلى غير متلفة أو متلفة، مع طلب موافقة مستقلة قبل تنفيذ أي حالة متلفة.
- [ ] عدم استخدام أو نسخ بيانات اعتماد الإنتاج أو أوامر الوصول الداخلي في السجلات أو المستودع.
- [ ] تحديد البرانش الأصلي لكل مستودع وحظر أي تعديل أو commit عليه.
- [x] تنفيذ مواءمة المصدر الثابتة وتوثيق فروق المسار المحتملة مع تشغيل الإنتاج.
- [ ] إنشاء برانش معالجة مستقل موثق لكل مستودع قبل أي إصلاح أو ملف اختبار جديد.
- [ ] بناء فهرس جميع شاشات تطبيق المريض مع المسارات ومكوّنات التفاعل ونقاط API.
- [ ] بناء فهرس جميع شاشات تطبيق المزوّد مع أزرار القرار ومسارات API والصلاحيات.
- [ ] بناء فهرس صفحات لوحة الإدارة الحديثة والقديمة مع الأزرار التشغيلية ونقاط API.
- [ ] ربط كل تدفق بمتطلبات الخلفية: المصادقة، الدور، الملكية، المصدر/الوجهة، والبيانات المتوقعة.
- [ ] وسم كل زر بحالته: متصل، غير متصل، محاكاة/بديل، أو يحتاج تحقق staging.
- [ ] فحص وجود رابط staging مصرح به وحسابات اختبار منفصلة لأدوار المريض والمزوّد والصيدلي والمشرف.
- [ ] إعداد بيانات اختبار غير إنتاجية وحالات دورة حياة لكل خدمة: إنشاء، قبول، رفض، إلغاء، دفع، استرداد، إغلاق.
- [x] تنفيذ جولة E2E للهوية وطلبات GET المحكومة بالأدوار، مع دليل منقح وبدون تغيير حالة.
- [ ] تنفيذ BOLA بهويتين sandbox وموارد مخصصة، واختبارات المال والملفات والرسائل والاتصال الفوري بعد موافقات منفصلة.
- [ ] المجموعة A: إنشاء مورد sandbox واحد لكل خدمة مصرح بها ثم إلغاؤه أو إغلاقه وتوثيق الأثر.
- [ ] المجموعة B: تنفيذ انتقالات قبول ورفض وبدء وإكمال على موارد sandbox المخصصة فقط، مع مراجعة الحالة بعد كل انتقال.
- [x] المجموعة C: اختبار دفع صفري واحد رُفض بـ 400 قبل إصدار معرف دفع؛ لم تُنفذ أي متابعة مالية أو استرداد أو سحب.
- [x] المجموعة D: رفع ملف اختبار غير حساس إلى تخزين sandbox ثم حذفه والتحقق من الإزالة.
- [ ] المجموعة E: إكمال 2FA للمدير برمز مصرح به ثم تنفيذ GET إداري فقط.
- [ ] استخراج معرّف ملف المزوّد sandbox من مسار تشغيل مصادق أو ربطه بمطالبة JWT دون حفظ المعرّف في التقرير.
- [x] التحقق من معرّف طبيب sandbox على مسار الرعاية بعد إصلاح البيانات: أعاد 200، لكن لم تظهر فتحة قابلة للحجز.
- [ ] طلب رمز OTP إداري طازج ثم إجراء محاولة تحقق واحدة إضافية وGET إداري محدود؛ المحاولة السابقة أعادت 400 بلا JWT.
- [ ] إعادة تحقق الطبيب المنشور بعد إصلاح بيانات sandbox، ثم تشغيل دورة الموعد المحكومة فقط إذا أعادت تفاصيل الطبيب وفتحة متاحة.
- [ ] إضافة ساعات عمل/فتحة مستقبلية متاحة لطبيب sandbox المنشور ثم إعادة دورة الموعد مرة واحدة فقط.
- [ ] تنفيذ دورة الموعد على فتحة sandbox المؤكدة: إنشاء نقدي وإلغاء للتنظيف، ثم دورة بطاقة بلا بدء دفع وانتقالات مزوّد فقط عند تحقق الشروط.
- [x] إنشاء موعد نقدي sandbox وإلغاؤه للتنظيف، وإنشاء موعد بطاقة بلا دفع ثم إلغاؤه بعد فشل قبول المزوّد بـ 404.
- [ ] إصلاح ربط هوية/حساب المزوّد بمورد الموعد أو عقد `provider/jobs/consultation/:id/accept` ثم إعادة اختبار انتقالات القبول والبدء والإكمال على مورد sandbox واحد.
- [ ] إجراء تحقق 2FA للمدير برمز جديد عبر إدخال مخفي ثم GET لهوية الجلسة وfeature flags فقط عند النجاح.
- [ ] بدء دورة دخول 2FA جديدة أولاً، ثم استخدام رمز OTP الصادر بعدها في تحقق واحد منفصل وGET إداري محدود فقط.
- [ ] انتظار تأكيد المالك لانتهاء/إعادة ضبط حد معدل تسجيل دخول المدير؛ آخر محاولتي بدء دورة 2FA أعادتا 429 ولم يُصدر رمز جديد.
- [ ] تنفيذ محاولة 2FA الإدارية الجديدة مرة واحدة بالـ identifier البريدي نفسه ثم GET محدود فقط عند إصدار JWT.
- [ ] لا تعاد محاولة الدفع بقيمة موجبة أو أي استرداد/سحب قبل إثبات وضع sandbox وتفويض مستقل بالقيمة والأثر.
- [ ] تسجيل دليل كل حالة E2E: الطلب، الاستجابة، الأثر في البيانات، وقرار النجاح أو الفشل.
- [ ] تحديث التقرير النهائي وسجل النتائج بحالة كل شاشة ومسار وقيد خارجي متبقٍ.
