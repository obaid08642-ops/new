# التقرير النهائي للمعالجة والتحقق — منصة نبض الصحية

**تاريخ التقرير:** 14 أغسطس 2026  
**نطاق العمل:** الخلفية NestJS، تطبيق مزود الخدمة Expo، تطبيق المريض Expo، ولوحة الإدارة React/CRACO.  
**منهج التنفيذ:** معالجة في مساحة معزولة فقط، مع تجميع الملفات المعدلة في حزم قابلة للمراجعة على فرع Git مستقل. لم يُعدَّل فرع `main`.

## الملخص التنفيذي

أُنجزت معالجة العيوب ذات الأولوية العالية التي أثبتها مسح المصدر ومواءمة العقود وجولة الاختبار المحكومة بالأدوار. شملت المعالجة تثبيت هوية مزود الخدمة في JWT، نقل بيانات OTP الحساسة إلى Redis بصيغة آمنة وذات TTL، توحيد بعض عقود المصادقة والمسارات، وإزالة بيانات تجريبية مؤثرة من تدفقات التمريض والمحفظة والطوارئ والجواز الصحي والإشعارات. كما أُعيد ربط واجهة التمريض بمسارات خلفية محمية بدلاً من عقود محاكاة قديمة.

> لا يثبت هذا التقرير سلامة النشر الإنتاجي أو اكتمال التحقق لكل مسار متلف؛ إذ لا توجد بيئة staging منفصلة. تحققت الجولة السابقة من الطلبات المسموح بها فقط، وأي اختبار متلف جديد يتطلب موافقة صريحة قبل تنفيذه على البيئة الوحيدة المتاحة.

## الإصلاحات المنفذة

### الأمن والهوية والعقود الخلفية

تمت إضافة معرفي حساب وملف مزود الخدمة إلى JWT، ثم توحيد مواضع استهلاك الاستجابة مع حقول الرمز في المستوى الأعلى. يمنع ذلك انقطاع تحديد هوية المزود في العمليات التي تحتاج `provider_account_id` أو `provider_profile_id`.

تم نقل دورة OTP إلى Redis مع تجزئة للرمز ومدة صلاحية وحدود تحقق مستقلة. كما أزيل الاعتماد على حساب إداري مزروع ثابت، وصار إعادة ضبط كلمة المرور مرتبطة بدورة OTP الصحيحة. أُزيلت كذلك بادئة `api/v1` المكررة من المتحكمات المتأثرة، بما يعالج نمط 404 الناتج عن تكرار المسار.

| المعرّف | المعالجة | أثرها |
|---|---|---|
| FIX-001 / FIX-002 | إضافة حقول هوية المزود إلى JWT ومواءمة الملف مع خدمات الرعاية | يمنع فقدان ربط حساب المزود وملفه عند استدعاءات الرعاية |
| FIX-004 | OTP في Redis مع hash وTTL، وإعادة ضبط كلمة المرور عبر OTP | يقلل تعرض الرموز الحساسة ويضبط صلاحيتها واستهلاكها |
| FIX-005 | إزالة بادئة API المتكررة | يعيد توافق المسارات مع عنوان API الأساسي |
| FIX-006 | حقول توافق ملف المزود (`user_id`, `type`, `status`) ومزامنة حالة الاعتماد | يعالج اختلاف مخطط البيانات بين الرعاية وملف المزود |

### تدفق الرعاية والتمريض المنزلي

أغلقت مسارات الزيارات الحساسة التي كانت تسمح بالوصول العام أو لا تستخلص هوية المزود من JWT. أصبحت عمليات العرض والتتبع والاستجابة والانتقال والوصول وبدء الرعاية والإنهاء وطلبات المستلزمات محكومة بالأدوار وبملكية الزيارة. يسمح للإدارة فقط بتحديد `provider_id` صراحة، بينما يستخلص المزود العادي هويته من الرمز.

أزيلت الأرصدة الافتتاحية والمعاملات الوهمية وإحداثيات الموقع والرقم الهاتفي الافتراضي من استجابة المحفظة والتتبع. أضيفت عمليات تعيين كادر تمريض فعلي من حسابات المستخدمين النشطة، وتحديث GPS حقيقي، وتسجيل دخول للزيارة يحفظ إحداثيات فعلية، وإقرار مهني خادمي عند الإكمال. كما صُحح سجل انتقال الحالة عند رفض الزيارة بحيث يحتفظ بالحالة السابقة فعلاً.

| نطاق التمريض | قبل المعالجة | بعد المعالجة |
|---|---|---|
| عرض الزيارة والتتبع | بيانات يمكن الوصول إليها أو افتراضيات موقع | JWT، أدوار، وفحص ملكية الزيارة |
| المحفظة | رصيد افتتاحي ومعاملة وهمية عند عدم وجود بيانات | صفر ومعاملات مشتقة من الحجوزات الفعلية فقط |
| GPS | محاكاة عشوائية في الواجهة | `navigator.geolocation` وتحديث خادمي موثق |
| الإنهاء والتوقيع | توقيع SVG مولد محلياً | إقرار مهني مؤكد وهوية مزود من الجلسة الخادمية |
| طلب المستلزمات | معرف تقرير يدوي بديل | معرف زيارة قائم، تحقق عناصر، وتخزين طلب قابل للتتبع |

### تطبيق مزود الخدمة

صحح عميل تسجيل الدخول إلى `/provider/auth/login` واستخدم البريد الإلكتروني بدلاً من الهاتف في الشاشات المتأثرة. تم تحديث ثمانية عشر موضع تسجيل/تهيئة عبر ست شاشات ذات صلة. عُزلت وحدات Expo الأصلية في إعداد Jest بدلاً من تعطيل التطبيق، ثم حُولت الاختبارات إلى الواجهة غير المتزامنة لمكتبة اختبار React Native.

نجحت حالات اختبار الإجازة المرضية والتقرير الطبي وطلب التحاليل. تتحقق هذه الحالات من حمولات الإرسال الفعلية ولا تعتمد على جهاز أصلي أو EventEmitter خاص بالمنصة.

### لوحة الإدارة

استبدلت عناوين `localhost` الصلبة في عميلين للشبكة بإعداد `REACT_APP_BACKEND_URL` أو مسار نسبي للنشر. أصلح إعداد CRACO أيضاً بحيث لا يضاف React Refresh أو التحرير المرئي إلى بناء الإنتاج عندما تكون `NODE_ENV` غير محددة أو ليست `development`.

أعيدت واجهة التمريض إلى عقود `/nursing` المحمية، وحذفت قائمة الممرضين التجريبية، وتدفق GPS العشوائي، والتوقيع المرئي المولد، ورقم بطاقة التأمين والاسم الثابتين. كما أزيلت حالة طوارئ تجريبية وفيديو خارجي تجريبي من اللوحة القديمة؛ وعند فشل API تظهر حالة خطأ صريحة بدلاً من حالة إسعاف وهمية.

### تطبيق المريض

أزيل معرف مشروع إشعارات تجريبي؛ لا يُصدر التطبيق رمز Push إذا لم يكن معرف المشروع مهيأً. استبدل جواز الصحة الرسم الشبكي الوهمي بمحتوى `qrContent` موقّع يسترجع من `/patients/passport` ويعرض عبر مولد QR. عند عدم توافر المحتوى الموقّع يعرض التطبيق حالة صريحة ولا يعرض رمزاً مزيفاً.

أصلحت شاشة الأوامر الطبية القابلة للتنفيذ التي كانت تستورد ثيمات غير موجودة وتعتمد تأخيراً ورسائل تنفيذ غير حقيقية. أصبحت تستورد من مصدر الثيم المركزي، وتتعامل بأمان مع حمولة مسار غير صالحة، وتنقل المستخدم إلى وحدات الصيدلية أو التشخيص بدلاً من الادعاء بإنشاء طلب. أضيف كذلك مسار توافق لخدمة API التي كانت تستورد من ملف غير موجود.

## أدلة التحقق

| الاختبار | النتيجة | ملاحظة |
|---|---|---|
| `npm run build` للخلفية | ناجح | تحقق تجميع NestJS بعد تعديلات الأمن والتمريض |
| `npm test -- --runInBand` لتطبيق المزود | 3/3 ناجحة | الإجازة المرضية، التقرير، وطلب التحاليل |
| `NODE_ENV=production npm run build` للوحة الإدارة القديمة | ناجح | تحقق CRACO وإعادة ربط واجهة التمريض والطوارئ |
| `npx expo export --platform ios` لتطبيق المريض | ناجح | خرجت حزمة iOS بنجاح |
| `expo lint` لتطبيق المريض | محجوب بأداة lint | تعارض داخلي بين ESLint/AJV؛ ليس خطأً في شاشة QR الجديدة |
| `expo export --platform web` | غير منطبق على مسار التحقق الأصلي | يتوقف على `react-native-maps` الأصلية غير المدعومة للويب؛ تصدير iOS هو التحقق المناسب للتطبيق المستهدف |

## الفجوات والقيود المتبقية

ما زال التطبيق يضم مكونات تجريبية أو غير مكتملة خارج التدفقات المعالجة، خصوصاً في اللوحة الإدارية القديمة مثل تحكم السياج الجغرافي وبعض النوافذ الإدارية. هذه العناصر موثقة كفجوات ولا ينبغي تفعيلها أو تقديمها كوظائف إنتاجية قبل ربطها بعقود موثقة واختبارات صلاحيات. كما أن بعض خدمات المزامنة والتحليلات في تطبيق المريض تحتوي معرفات عشوائية تشغيلية أو تعليقات تشير إلى إرسال تدقيق مؤجل؛ هذه ليست بيانات مستخدم وهمية معروضة، لكنها تحتاج عقد تدقيق مركزي مستقل إذا كانت مطلوبة امتثالياً.

ينبغي معالجة فشل `expo lint` بتثبيت سلسلة ESLint/AJV متوافقة ومقفلة الإصدارات، ثم إعادة تشغيل lint على تطبيق المريض. كما يلزم تنفيذ اختبار E2E لاحق على نسخة منشورة من الشفرة المعدلة، لا على API الإنتاجي الحالي، للتأكد من أن الحراس الجديدة وعقود التمريض لا تؤثر في عملاء قائمين دون ترقية متزامنة.
