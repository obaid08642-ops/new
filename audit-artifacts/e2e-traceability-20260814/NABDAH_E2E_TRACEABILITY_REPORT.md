# تقرير التتبع والتحقق E2E لمنصة نبض

**حالة التقرير:** مكتمل للمواد المصدرية والفحوص المنفذة، مع قيود تشغيلية متبقية موثقة.  
**النطاق:** تطبيق المريض، تطبيق المزوّد، لوحتا الإدارة، NestJS، FastAPI، وعقود API المنشورة.  
**سلامة السجلات:** لا يحتوي هذا التقرير على كلمات مرور أو رموز JWT أو OTP أو معرفات موارد اختبار أو بيانات صحية أو حمولات استجابة.

## الخلاصة التنفيذية

أُنشئت خريطة تتبع تفصيلية للمشروع، ونُفذت مواءمة ثابتة بين مسارات الواجهات ومتحكمات الخلفية، ثم أُجريت جولة E2E تدريجية على بيئة الإنتاج الوحيدة باستخدام حسابات sandbox وبموافقات منفصلة لعمليات تغيير الحالة. تؤكد الأدلة أن عدداً من تدفقات القراءة الأساسية يعمل، وأن رفع ملف اختبار وحذفه نجحا، وأن إنشاء موعد sandbox وإلغاءه نجحا. في المقابل، كشفت الجولة فروقاً تشغيلية حقيقية في هوية المزوّد، انتقالات صف العمل، معدل بدء OTP الإداري، وتوافر بوابة المزوّد.

> **قرار الجاهزية:** لا يوصى بإطلاق عام جديد أو باعتبار التحقق E2E مكتملًا. يجب أولاً تصحيح ربط هوية المزوّد مع موارد المواعيد، وتثبيت سياسة rate limiting للمدير، وتأكيد وصول بوابة المزوّد، ثم إعادة الحالات المحجوبة في بيئة staging منفصلة أو نافذة sandbox مضبوطة.

| محور التحقق | النتيجة المثبتة | الحكم |
|---|---|---|
| خريطة الواجهات والتفاعلات | 293 شاشة و3,822 تفاعلاً و522 نقطة خلفية مفهرسة | مكتمل مصدرّياً |
| مواءمة عقود API | 297 مسار واجهة؛ 138 مطابقة مفردة و32 ملتبسة و127 بلا مطابقة ثابتة مفردة | يلزم تثبيت العقد للتغطية الكاملة |
| E2E القراءة | 33 طلب GET ناجحاً عبر أدوار sandbox، مع 7 رموز جلسة صالحة | جزئي ومثبت |
| رفع وحذف الملف | رفع 201، حذف 200، وفحص غياب 404 | اجتاز للعينة |
| إنشاء/إلغاء الموعد | إنشاء نقدي 201 ثم إلغاء 200؛ إنشاء بطاقة 201 ثم تنظيف 200 بلا دفع | اجتاز ضمن النطاق |
| انتقالات المزوّد | قبول المزوّد لطلب الموعد أعاد 404 | فشل عقدي مثبت |
| OTP المدير | بدء دورة OTP أعاد 429 بعد محاولة وانتظار 65 ثانية | محجوب تشغيلياً |
| الدفع | طلب صفري واحد أعاد 400 بلا معرف دفع أو متابعة | غير مثبت sandbox المالي |

## 1. خريطة التتبع

استخرجت الخريطة من المصادر المستعادة، وتحتفظ بموقع الشاشة والتفاعل ونقطة الاتصال المحتملة. لا تعني نقطة API المستخرجة نجاحاً تشغيلياً؛ بل تمثل علاقة قابلة للفحص بين واجهة المستخدم والعقد الخلفي.

| الأصل | المخرج | الغرض |
|---|---|---|
| `traceability/ui-api-traceability.json` | بيانات الخريطة الكاملة | تحليل آلي للشاشات والتفاعلات ونقاط API |
| `traceability/UI_API_TRACEABILITY_MAP.md` | خريطة قابلة للقراءة | مراجعة بشرية لكل مكوّن |
| `traceability/UI_INTERACTION_CATALOG.csv` | كتالوج تفاعلات | التصفية والمراجعة الصفية |
| `contract-mapping/ui-backend-contract-mapping.json` | سجل مواءمة العقود | ربط واجهة المستخدم بالمتحكمات والمرشحين |

## 2. نتائج مواءمة العقود

أزيلت متغيرات عنوان API وبادئات النسخة من المقارنة قبل مطابقة المسارات، مع تفضيل المطابقة الحرفية على المسارات الديناميكية. لا تكفي النتيجة الثابتة وحدها للحكم على التفويض أو ملكية المورد؛ لذلك استُخدمت لترتيب اختبارات E2E فقط.

| التصنيف | العدد | التفسير |
|---|---:|---|
| مطابقة مفردة | 138 | يوجد متحكم واحد متوافق بنيوياً مع المسار المستخرج. |
| ملتبسة | 32 | يوجد أكثر من مرشح، غالباً بسبب مسار ديناميكي. |
| غير مطابقة ثابتاً | 127 | يلزم مراجعة اختلاف تسمية أو خدمة أخرى أو عقد مفقود. |

كشفت مراجعة التوجيه أيضاً فرقاً بين لقطة المصدر والتشغيل المنشور: المسار ذي بادئة API المفردة وصل إلى حارس المصادقة، بينما المسار المكرر أعاد 404. لذلك لا ينبغي تطبيق إصلاحات مسار على المصدر وحده من دون تثبيت إصدار البناء وإعداد النشر الفعليين.

## 3. نتائج E2E غير المتلف

اقتصرت الجولة الأولى على تسجيل دخول sandbox المصرح به ثم `GET` فقط. لم تُحفظ رموز أو حمولات أو بيانات شخصية. أصدر النظام 7 رموز جلسة لأدوار المريض والمزوّدين، وأثبت بوابة 2FA للمدير.

| الدور | نتيجة المصادقة | القراءة المثبتة | الملاحظة |
|---|---|---|---|
| المريض | نجحت | 21 طلب GET ناجحاً | ملف، إعدادات، صحة، رعاية ومخزون قراءة. |
| الطبيب | نجحت عبر مزود | صف العمل والقدرات: 200 | `/auth/me` غير متوافق مع رمز المزوّد. |
| الصيدلية | نجحت عبر مزود | صف العمل والقدرات: 200 | الدور التشغيلي العام `provider`. |
| المنشأة | نجحت عبر مزود | صف العمل والقدرات: 200 | الدور التشغيلي العام `provider`. |
| المختبر | نجحت عبر مزود | صف العمل والقدرات: 200 | الدور التشغيلي العام `provider`. |
| الأشعة | نجحت عبر مزود | صف العمل والقدرات: 200 | الدور التشغيلي العام `provider`. |
| التمريض المنزلي | نجحت عبر مزود | صف العمل والقدرات: 200 | الدور التشغيلي العام `provider`. |
| المدير | بوابة 2FA مثبتة | لا قراءة إدارية | حُجبت لاحقاً بحد المعدل. |

## 4. نتائج العمليات المصرح بها

نُفذت العمليات التالية فقط بعد الموافقة الصريحة، مع إيقاف تلقائي عند أي فشل ومن دون بدء دفع حقيقي.

| المجموعة | الحالة | الدليل | الأثر المتبقي |
|---|---|---|---|
| رفع/حذف ملف | اجتاز | 201 → 200 → 404 | لا كائن متبقٍ حسب فحص الغياب. |
| دفع صفري | رُفض بأمان | 400 قبل معرف دفع | لا دفع أو استرداد أو سحب أو callback. |
| موعد نقدي sandbox | اجتاز ونظف | إنشاء 201 ثم إلغاء 200 | مورد ملغى. |
| موعد بطاقة sandbox | أنشئ ونظف | إنشاء 201 ثم إلغاء 200 | لم يبدأ دفع. |
| قبول مزوّد للموعد | فشل | 404 | لم يُجر بدء أو إكمال؛ المورد أُلغي. |
| 2FA مدير | محجوب | 429 بعد بدء الدورة ومحاولة لاحقة بعد 65 ثانية | لا JWT ولا قراءة إدارية. |

## 5. النتائج ذات الأولوية

| المعرف | الأولوية | النتيجة | قرار الإصلاح |
|---|---|---|---|
| E2E-001 | P1 | رمز المزوّد يقبل في صف العمل لكن لا يتوافق مع حراس الملف العام. | توحيد claims الرمز والحراس أو فصل العقود بوضوح. |
| E2E-002 | P1 | بوابة المزوّد لا تحل DNS من بيئة التحقق. | تثبيت DNS وNginx والشهادة ثم فحص الوصول. |
| E2E-003 | P1 | ظهر فرق بين ملف الطبيب وفلتر مسار الرعاية ثم عولج في بيانات sandbox. | توحيد مخطط provider profile والترحيل. |
| E2E-004 | P1 | الملف النشط بلا فتحات قابلة للحجز قبل تهيئة ساعات العمل. | اشتراط صحة ساعات العمل في provisioning الاختبار. |
| E2E-005 | P1 | قبول المزوّد لموعد sandbox أعاد 404 رغم مصادقة المزوّد. | ربط `sub` بالـ `doctor_user_id`/`account_id` وتصحيح provider jobs. |
| E2E-006 | P1 | استمر حد بدء OTP الإداري بعد مهلة 65 ثانية. | توثيق مفاتيح ومعدل الحماية وإنشاء نافذة اختبار محكومة. |

## 6. ما لم يثبت بعد

لم تُختبر BOLA بهويتين وموارد متمايزة، ولا الدفع الحقيقي أو الاسترداد أو السحب، ولا إنشاء طلبات الصيدلية/المختبر/الأشعة/التمريض كاملة. كما لم يثبت وصول بوابة المزوّد أو مسارات الإدارة بعد 2FA. هذه ليست حالات اجتياز أو فشل مخفية؛ بل حالات محجوبة موثقة يجب أن تظل ضمن بوابة قبول لاحقة.

## 7. خطة الإغلاق

أولاً، يجب إصلاح تعيين هوية المزوّد في رمز جلسة المزوّد وربطها بملف الطبيب وموارد الحجز، ثم إعادة اختبار `accept → start → complete` على موعد sandbox واحد مع تنظيف واضح. ثانياً، ينبغي تحديد سياسة rate limiting الإدارية ومفتاحها ونطاقها، ثم بدء OTP واستخدام رمز صادر من تلك الدورة في تسلسل واحد. ثالثاً، يجب تثبيت عقد دفع sandbox مستقل ببيانات حجز اختبارية وقيمة رمزية غير قابلة للتسوية، وموافقة منفصلة قبل أي إعادة محاولة.

وفيما بعد، يوصى بإنشاء بيئة staging مستقلة عن الإنتاج تتضمن بيانات sandbox معزولة، وOpenAPI snapshot من نفس الإصدار المنشور، ومصفوفة E2E آلية لكل دور. حتى يتحقق ذلك، يبقى الاستخدام التشغيلي الواسع غير موصى به.
