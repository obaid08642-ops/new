# خطة اختبار E2E بعد المعالجة — منصة نبض

**الغرض:** التحقق من الإصلاحات في نسخة منشورة من الفرع `fix/e2e-operational-contracts-20260814` قبل أي دمج.  
**قاعدة التشغيل:** لا تُنفذ أي حالة تغير البيانات أو ترسل إشعاراً أو تبدأ دفعاً إلا بعد موافقة صريحة جديدة، وبحسابات اختبار فقط.

## ترتيب التنفيذ

| الموجة | نوع العمليات | النطاق | معيار النجاح |
|---|---|---|---|
| A | قراءة آمنة | JWT، عقود المصادقة، قوائم الزيارات، ملف المزوّد، الجواز الصحي | 200/401/403 مطابق للهوية والدور، من دون بيانات افتراضية |
| B | متلفة منخفضة الأثر | تعيين ممرض على زيارة اختبار، قبول/رفض، تحديث GPS اختبار، طلب مستلزمات | فحص ملكية الزيارة وسجل التدقيق والحالة المتوقعة |
| C | متلفة متوسطة الأثر | تسجيل الدخول للزيارة، إدخال تقرير، إكمال زيارة اختبار | لا يكتمل التقرير دون إقرار مهني وحالة صحيحة |
| D | مالية | محفظة ودفع صفري فقط | لا يُنشأ معرف دفع عند الحمولة غير الصحيحة ولا تظهر أرصدة بديلة |

## حالات التحقق الأساسية

| المعرّف | المسار أو التدفق | نوعه | المستخدم | النتيجة المطلوبة |
|---|---|---|---|---|
| R-NUR-01 | `GET /nursing/visits` | آمن | ممرض | لا تعاد إلا الزيارات المعينة لهوية JWT |
| R-NUR-02 | `GET /nursing/visits/:id` لزيارة ممرض آخر | آمن | ممرض | `403` من دون تسريب عنوان أو هاتف أو بيانات طبية |
| R-NUR-03 | `GET /nursing/wallet` بلا حجوزات مكتملة | آمن | ممرض | رصيد وEscrow ومعاملات صفرية، لا أرصدة افتتاحية |
| R-NUR-04 | `GET /nursing/staff` | آمن | مدير ومستخدم عادي | مدير: قائمة كادر فعلي؛ مستخدم عادي: `403` |
| R-PAS-01 | `GET /patients/passport` | آمن | مريض | `qrContent` و`verificationToken` موقّعان، ولا يعرض العميل رمزاً عند الفشل |
| R-PUSH-01 | تسجيل Push بلا `EXPO_PUBLIC_PROJECT_ID` | آمن | تطبيق مريض | عودة آمنة بلا تسجيل token مصطنع |

| R-PHR-02 | فتح تفاصيل طلب وارد وسجله الزمني | آمن | مزود صيدلية | العناصر و`timeline` أو `state_history` تطابق المورد المخزن؛ طلب مزود ثانٍ يرفض بلا تسريب |
| R-PHR-03 | فتح شاشة المخزون والمراسلة والسجل | آمن | مزود صيدلية | تظهر عدم إتاحة صريحة إلى أن ينشر عقد قائمة مصرح به؛ لا بيانات بديلة |
| M-NUR-01 | `POST /nursing/visits/:id/assign` | متلف | مدير | يقبل `nurse_id` لنفس الكادر فقط ويسجل حدث تعيين |
| M-NUR-02 | `POST /nursing/visits/:id/gps` | متلف | الممرض المعيّن | يحدث الموقع فقط للزيارة المملوكة، ويُرفض ممرض آخر |
| M-NUR-03 | `POST /nursing/visits/:id/check-in` | متلف | الممرض المعيّن | يحتاج إحداثيات صحيحة وحالة مؤهلة وينقل إلى `CARE_IN_PROGRESS` |

| M-NUR-05 | `POST /nursing/visits/:id/supply-requests` | متلف | الممرض المعيّن | يرفض العناصر الفارغة ويخزن طلباً مربوطاً بالزيارة |

| M-PHR-02 | تحضير ثم جاهزية طلب صيدلية | متلف منخفض الأثر | مزود صيدلية | انتقالات الحالة متسلسلة، ولا يسمح بتجاوز حالة سابقة أو تكرار غير آمن |
| M-PHR-03 | مراجعة سلة أو تفويض تأمين أو إسناد توصيل | متلف — **محجوب** | مزود صيدلية | لا ينفذ قبل نشر عقد مخزن مع RBAC وملكية وسجل تدقيق؛ لا تستخدم واجهة عدم الإتاحة كبديل للاختبار |

## ضوابط البيانات والتنظيف

تستخدم كل حالة متلفة مورداً معنونا بوضوح كسجل اختبار، وتوثق المعرفات في سجل منفصل غير محفوظ في Git. بعد كل موجة، يجب إلغاء أو أرشفة الموعد الاختباري وحذف أي ملف مرفوع له، ثم التحقق من عدم بقاء معاملة مالية أو إشعار حقيقي غير مقصود. لا تحفظ كلمات مرور أو OTP أو معرفات sandbox أو رموز JWT في التقرير أو المستودع.

> لا تُشغّل هذه الخطة على API الإنتاجي الحالي؛ لأنها لا يتضمن ملفات الإصلاح الموجودة في الفرع. يجب أولاً بناء ونشر نسخة staging أو بيئة مراجعة من هذا الفرع. وبعد النشر، تظل حالات مراجعة سلة الصيدلية والتأمين والتوصيل محجوبة إلى أن يوجد عقد خادمي مخزن ومصرح به؛ فالواجهة المعالجة لا تحاكي هذه العمليات.
