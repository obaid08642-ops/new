# Phase 0B semantic evidence — Family schemas

**Baseline:** `main @ 22526bedb77a3d8148219036367e4714f401aecc`

**Member read in full:** `src/schemas/family.schemas.ts:1–70`

The file defines a FamilyMember subdocument, FamilyGroup, SharedCalendarEvent and FamilyPermissionRequest (`4–70`). FamilyMember contains required user_id, free-form role defaulting to member, a string permission array, joined_at and display/avatar labels (`4–14`). FamilyGroup has unique/indexed id, indexed owner_id, name, Object-shaped members, sparse unique/indexed invite_code, optional invite_expires_at and is_deleted (`16–29`). SharedCalendarEvent has unique/indexed id, indexed group_id, title/description, free-form type, optional ref_id, event_date, created_by/member_user_id, client display labels/time/color and is_deleted (`31–52`). FamilyPermissionRequest has unique/indexed id/group_id, requester/target IDs, required permission array, free-form status defaulting pending, responded_at and response_note (`54–70`).

The schema provides basic required fields, selected unique/indexes, defaults and soft-delete flags, but FamilyMember is not decorated as a nested schema and FamilyGroup.members is `[Object]`, so role, permissions, user identity and joined_at lack nested runtime validation (`5–13,22`). Role and permission values are free-form; there is no owner cardinality, unique member constraint, group-size limit, self-membership rule, owner transfer or capability/consent invariant (`6–10,19–27`). Invite code expiry is stored but no TTL, one-time redemption, issuer, target, hashed secret, attempt limit or consumed state is declared (`23–27`).

Calendar event type, ref_id, labels, color, title and description are unconstrained; references are not bound to the group/member or source booking/order/lab/medication, and event_date has no timezone/range/source semantics (`34–50`). `created_by` and `member_user_id` are strings without referential, membership, delegated-access or tenant/facility scope controls (`35,45–46`). Soft-delete is a mutable boolean without deleted_at, actor/reason, restore/legal hold or retention/DSAR lifecycle (`27,50`).

Permission requests use free-form status and permission arrays with no allowlist, least privilege, group membership, requester/target relationship, consent scope, expiry, revocation or approval actor/reason; no compound uniqueness prevents duplicate pending requests (`55–67`). responded_at/response_note have no state invariant, moderation or privacy policy. All user/group IDs are plain strings and no schema-level tenant isolation or cross-document referential integrity exists (`19–26,34–46,57–63`).

Display name/avatar, event descriptions, member labels and response notes can carry PII/health context without projection, normalization, encryption, consent, access audit or retention controls (`12–13,36–49,66–67`). No CAS/version, append-only audit, idempotency, transaction/rollback or concurrency protection is declared for membership, invite redemption, events or permission approval. No notification/delivery acknowledgement, cache invalidation, rate limit, abuse/enumeration control, index migration/runtime validation or live data evidence is represented. No code was changed and no build/test/application operation was performed during this read.
