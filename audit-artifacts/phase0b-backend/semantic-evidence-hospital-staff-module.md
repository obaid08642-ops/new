# Phase 0B semantic evidence — HospitalStaffModule

**Baseline:** `main @ 22526bedb77a3d8148219036367e4714f401aecc`

**Member read in full:** `src/modules/hospital-staff/hospital-staff.module.ts:1–137`

The module defines a hospital/clinic staff CRUD service and a JWT-guarded controller (`1–17,113–136`). `STAFF_ROLES` allows doctor, lab, radiology, nurse and pharmacy roles (`17`). `getOwnerAccount` restricts callers to HOSPITAL or ADMIN, loads the provider account by owner_user_id, and fails for a non-admin without an account (`26–31`). `list` scopes non-admin results to `parent_account_id` and excludes password_hash, _id and __v (`33–37`).

`create` checks only trimmed full name/phone/password, casts staff_role to UserRole and validates membership in STAFF_ROLES, checks phone/email collision, hashes the password, creates a full User with `verified: true`, parent_account_id, supplied permissions/schedule/provider fields and `consultation_fee || 0`, then removes password_hash/_id/__v from the returned object (`39–68`). `update` loads by staff id, checks parent-provider ownership only after loading, copies an allowlisted field set including permissions, schedule, license_number and consultation_fee, lowercases email and performs updateOne, then returns a projection without password_hash/_id/__v (`70–81`). `suspend`, `remove` and `resetPassword` similarly load by id, apply an owner/admin check, update/delete or hash a password, and return success (`83–110`). The controller applies `JwtAuthGuard` to list/create/update/suspend/reset/delete routes, but all bodies are `any` except narrow inline types (`113–123`).

Critical gaps: create forces `verified: true` and accepts arbitrary staff identity fields, permissions, schedule, license and fee without verifier/approval or institution capability checks (`39–65`). Ownership is computed through an owner account but staff lookup is by global id and the admin path uses an unscoped `{}` list filter, exposing all users to any ADMIN (`26–37,70–98`). The update/remove/suspend/reset checks are post-fetch and do not use a single owner-scoped atomic predicate, leaving race/stale ownership and cross-tenant risk (`70–108`). `parent_account_id` is written on create but update checks `parent_provider_account_id`, creating an ownership-field mismatch that may deny valid records or make authorization semantics inconsistent (`55,74,87,96,106`).

Bodies have no DTO/class-validator bounds for phone/email/name, role, permission allowlist, schedule, specialty/degree/years, license, consultation_fee or suspension; IDs and boolean semantics are unvalidated (`39–43,70–78,83–89,101–109,117–122`). `consultation_fee || 0` can silently replace a supplied zero/invalid/negative/non-numeric value; no currency or authoritative fee policy exists (`64`). `permissions` is directly client-supplied and can grant dangerous scopes, while no separation exists between account owner and platform admin or approval/audit trail (`55–58,76`).

Password hashing is present and response projections remove password_hash, but reset-password has weak minimum length only, no password policy, current-password/MFA confirmation, rotation/revocation or session invalidation (`46,66,101–109`). Email/phone uniqueness is checked before create without transaction/unique-error handling, and create/update operations have no idempotency or replay protection (`44–48,70–80`). Removal is hard delete, with no staff offboarding, booking/record ownership transfer, audit, retention or DSAR behavior (`92–99`). Suspension does not invalidate sessions/tokens or prevent active assignments (`83–90`).

No tests in this member prove owner/stranger/unauthenticated HTTP behavior, tenant/facility isolation, staff capability/licensing, permissions consent, notification/event/cache side effects, PII-safe field-level projection beyond basic password removal, rate limiting, stable error schemas, financial truthfulness, or live Mongo/index/transaction behavior. No code was changed and no build/test/application operation was performed during this read.
