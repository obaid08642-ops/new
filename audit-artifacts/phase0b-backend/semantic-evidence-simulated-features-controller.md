# Phase 0B semantic evidence — simulated-features.controller.ts

**Archive member:** `src/modules/provider/simulated-features.controller.ts`  
**Baseline:** `main @ 22526bedb77a3d8148219036367e4714f401aecc`  
**Read range:** lines 2–197; full 197-line member covered.

Lines 2–26 import Nest decorators/models, auth CurrentUser, campaign/CRM/referral/user/home-care/radiology schemas and DTOs. `@UseGuards(JwtAuthGuard)` is applied to the controller rooted at `provider/features`; no role decorator or explicit provider-type check is visible.

**Promotions:** Lines 28–43 expose `POST /provider/features/promotions`. It creates a pending campaign under `provider_id: user.id`, copying client prices, dates, image URL and arbitrary target parameters. Defaults use current time and current time plus 30 days. No positivity/currency/discount/date-order validation, idempotency, approval actor or ownership beyond the authenticated ID is visible. Lines 45–48 expose `GET /provider/features/promotions`, returning all provider campaigns without pagination/projection/status filter.

**Referrals:** Lines 50–63 expose `POST /provider/features/referrals`. It generates `REF-` plus a six-digit code using `Math.random()` (line 53), accepts patient_id/target_type/notes/tests, and creates a pending referral. No patient ownership/relationship, target enum, duplicate/idempotency or uniqueness enforcement is visible. Lines 65–68 list referrals by authenticated referrer without pagination/projection.

**CRM:** Lines 70–87 expose `GET /provider/features/crm/patients`. It loads up to 200 tags for the current provider, fetches user names, and returns patient IDs/names plus three booleans. This is real PII and access depends solely on provider_id. Lines 89–105 expose `GET /provider/features/crm/patients/:id`; if no tag exists, it returns a default object containing provider_id, patient_id, flags, empty custom tags and empty private notes. This is a synthetic default response and may mask missing persistence/ownership validation. Lines 107–125 expose PATCH update; it upserts a provider-patient tag and copies all DTO fields including unrestricted private_notes, with no idempotency, patient relationship/encounter check, optimistic version or audit event.

**Home-care check-in:** Lines 127–145 expose `POST /provider/features/home-care/bookings/:id/check-in`. It loads booking by ID only, does not visibly verify the current user is the assigned nurse/provider or that the booking belongs to the provider, sets state to IN_PROGRESS, saves, then creates a nursing visit report with nurse_id from current user and optional coordinates. Two writes are non-atomic; repeated calls can create multiple reports and repeat state transitions. `verifiedGps` is true only if both values are truthy, not evidence of geofence/accuracy validation.

**Home-care report submission:** Lines 147–167 expose `POST /provider/features/home-care/reports/:id/submit`. It loads booking by ID only, sets COMPLETED and saves, then upserts a report by home_care_order_id with checkout, tasks, arbitrary vitals object and notes. No assigned-user/visit ownership, allowed state transition, report author binding, idempotency, clinical validation or transaction is visible. The route parameter is called `bookingId` despite route segment `reports/:id`.

**Radiology report upload/publish:** Lines 169–185 expose `POST /provider/features/radiology/bookings/:id/upload-report`; it loads by ID, creates a report entry with client file_id or synthetic `FILE-${Date.now()}`, tracking ID, time and report text, pushes it into booking.reports and saves. No current-user/doctor/facility ownership, report author, file existence/ownership/type/scan, duplicate/replay or size control is visible. The response echoes `report_text` (line 184), potentially leaking sensitive clinical content. Lines 187–196 expose `POST /provider/features/radiology/bookings/:id/publish-report`; it loads by ID and sets REPORT_PUBLISHED with no role, ownership, prior-state or report completeness check.

**Critical findings:** controller-level JWT is not enough to prove provider role or resource ownership. Multiple mutations are non-atomic. Referral codes use weak Math.random and have no visible unique/replay handling. CRM default output is synthetic, contrary to strict no-fake-data requirements when it represents absent persistence. Home-care and radiology flows can be triggered against arbitrary booking IDs if reachable by any authenticated provider. Clinical report content and PII are returned directly. Simulated-feature naming and module wiring require explicit production gating.

**Test implications:** require role/resource owner/stranger/unauth matrices; campaign financial/date/currency/idempotency tests; cryptographic unique referral code and duplicate tests; CRM PII/redaction/default semantics; assigned nurse/provider checks; atomic state+report transactions; legal state machine and replay; GPS geofence; clinical schema/range/size; file binding/AV scan; report publish authorization/completeness; audit/notification tests; and production route exclusion/gating. No tests executed during this semantic read.
