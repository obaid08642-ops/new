# Phase 0B semantic evidence — FamilyService spec

**Baseline:** `main @ 22526bedb77a3d8148219036367e4714f401aecc`

**Member read in full:** `src/modules/family/family.service.spec.ts:1–207`

The spec builds FamilyService with mocked family-group, calendar-event and permission-request repositories plus a raw connection mock (`5–41`). It verifies group creation and rejection when a user already belongs to a group (`43–60`), owner-only invite generation with expiry and rejection for a non-owner (`62–76`), valid invite join, invalid/expired invite rejection and duplicate-member rejection (`78–107`). It verifies a group member can create a calendar event for a member with a real event_date, missing schedule/member rejection without create, creator-only calendar deletion against another member, and creator deletion success (`109–152`). It verifies permission request creation, successful member permission update even with empty update metadata, fail-closed update when matchedCount=0, and owner approval granting requested permissions (`154–205`).

All repositories are mocks and calls are direct; HTTP authentication, verified identity, tenant scope and live persistence are unproven (`11–41`). Group coverage does not test name/member limits, owner transfer, leave/delete/restore, invite uniqueness/one-time redemption, expiry race, invite secrecy, member verification or concurrent membership joins (`43–107`). Calendar tests do not cover title/type/date timezone/range, linked appointment ownership, event privacy, edit/update, group-owner delete, soft-delete/audit or duplicate/replay (`109–152`). Permission tests do not validate permission allowlist/least privilege, requester/target identity, health-data consent, revocation, expiration, duplicate requests, CAS or concurrent approvals (`154–205`). The `respondPermission` path is tested only for approval, not rejection/expiry/terminal states or whether grant and request update are atomic. No PII/PHI minimization, family consent, retention/DSAR, notifications, event delivery, rate limiting, abuse, stable error schemas or live Mongo evidence exists. No code was changed and no build/test/application operation was performed during this read.
