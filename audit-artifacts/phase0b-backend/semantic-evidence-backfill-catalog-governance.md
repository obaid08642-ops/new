# Phase 0B semantic evidence — Catalog governance backfill

**Baseline:** `main @ 22526bedb77a3d8148219036367e4714f401aecc`

**Member read in full:** `scripts/backfill-catalog-governance.ts:1–154`

The script is dry-run by default and documents a cautious policy: legacy records are publicly eligible only where a pre-governance verification signal exists, while other records remain hidden/pending (`3–15`). It declares six target collections. Medicines inherit public eligibility from `verified: true` and `is_deleted != true`; providers inherit from active status plus either `license_verified: true` or `license_status: 'verified'`; facilities and four service catalogs have no inherited filter and therefore remain hidden/pending (`18–46`). The filter is a generic `Record<string, unknown>` and no collection schema, field type, source age, revocation/expiry, tenant, jurisdiction or reviewer identity is validated.

`governanceMissing` requires all three fields—`public_eligibility`, `medical_review_status` and `provenance`—to be absent (`48–52`). `inheritedFilter` spreads this with the legacy verification filter (`54–56`). The presence-only predicate is vulnerable to partial/legacy records that already contain one governance field, and the script does not distinguish null, invalid, stale, conflicting or manually reviewed values. Dry-run counts legacy records and inherited candidates but does not reconcile IDs, duplicates, source freshness, expected totals or field safety (`58–70`).

Apply performs a collection-wide `updateMany` for inherited candidates, setting public eligibility true, indexing eligibility false, medical review approved, current `last_reviewed`, fixed provenance and a backfill timestamp (`73–86`). It then performs a second collection-wide `updateMany(governanceMissing)` that sets all remaining records hidden/pending and overwrites provenance/timestamps (`88–101`). The second predicate is not explicitly limited to records excluded from the first update, and the operation is not wrapped in a transaction, per-collection lock, backup/recovery point or version conflict check. There is no matched/modified postcondition beyond logging counters, no audit actor/change ticket, no schema/unique-index assertion, no staged review or rollback plan tied to a specific migration ID.

Rollback updates every record whose provenance is one of three fixed strings and has a backfill timestamp, unsetting all governance fields (`104–117`). Although comments say later human/governance changes are preserved, the predicate is provenance/timestamp-based and does not include a migration ID, prior-value snapshot or immutable version; records can be affected if those values are copied or retained. Apply/rollback require `MONGO_URL` and a confirmation string, but no environment/database identity, operator authorization, release window, explicit collection allowlist verification or production safety gate is present (`119–143`). The script does use `try/finally` for Mongo disconnect and rejects simultaneous apply/rollback (`124–142`), but it was not executed; no product code was changed and no tests/builds were run during this semantic read.
