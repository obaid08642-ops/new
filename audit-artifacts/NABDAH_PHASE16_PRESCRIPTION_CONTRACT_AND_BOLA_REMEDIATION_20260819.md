# منصة نبض — Phase 16: تغيير عقد الوصفات وإصلاح BOLA للمسارات المعدِّلة

**التاريخ:** 2026-08-19
**الفرع الوحيد:** `manus/on-live-reconciliation`
**النطاق:** Backend الوصفات وتطبيق Provider فقط. لا يتضمن هذا المستند نشر خادم أو قبولاً تشغيلياً نهائياً.

> **الحكم الحالي:** **FIX في المصدر — يلزم بناء أرشيف جديد، commit/push، وتفويض نشر منفصل ثم إعادة اختبار حي بحسابات Sandbox فقط.** لا يُعامل نجاح البناء أو الاختبار المحلي كدليل أن البيئة المنشورة تحمل هذا الإصلاح.

## سبب التوثيق

تغيّر عقد `POST /prescriptions/create` بصورة جوهرية ومقصودة منذ تقوية مسار الوصفات؛ لذلك فإن العبارة السابقة «لا تغيير في العقود» غير صحيحة ولا يجوز استخدامها. كما كشف فحص مستقل قبل تنفيذ دورة حياة Sandbox أن بعض mutations اللاحقة كانت تعتمد على مصادقة عامة من دون تحقق كامل من طرف الوصفة المشارك، وهو مسار BOLA عالي الخطورة تم إصلاحه واختباره سلبياً في المصدر.

| المجال | العقد السابق غير الكافي | العقد المصحح | حالة الإثبات |
|---|---|---|---|
| إنشاء وصفة | كان يمكن لواجهة قديمة أن لا ترسل ربط موعد مثبت، وكان الاستخدام مقيداً عملياً للكتالوج فقط | الطبيب فقط؛ يلزم `appointment_id` و`patient_id`، ويطابق الخادم موعداً `IN_PROGRESS` مملوكاً للطبيب | PASS محلياً؛ يلزم اختبار حي بعد النشر |
| دواء من الكتالوج | حقل `medicine_id` فقط بلا توثيق واجهة كامل | لا يقبل الخادم إلا دواءً `verified: true`؛ يحفظ اسم الكتالوج الخادمي | PASS محلياً؛ يلزم اختبار حي بعد النشر |
| دواء يدوي استثنائي | مرفوض بالكامل بعد التقوية الأولى | يقبل ضمن الوصفة فقط مع `is_manual_entry: true` و`verified: false` و`manual_review_status: PENDING_REVIEW`؛ لا ينشئ صفاً في `medicines_master` | PASS محلياً؛ يلزم اختبار حي بعد النشر |
| مراجعة يدوية | لا يوجد طابور عقدي واضح | `GET /prescriptions/manual-review/queue` للصيدلية المعيّنة أو الإدارة، و`POST /prescriptions/:id/substitute` لتسجيل بديل معتمد | PASS بنائي/مصدري؛ يلزم اختبار حي بعد النشر |
| الصرف | خطر صرف صنف يدوي غير معتمد | يمنع `DISPENSED` ما لم تصبح كل مادة يدوية `SUBSTITUTED_APPROVED` | PASS محلياً؛ يلزم اختبار حي بعد النشر |
| BOLA في mutation | الانتقال/الإرسال/البديل لم تكن تتحقق كلها من طرف الوصفة | الطبيب المالك فقط يرسل الوصفة المنشأة؛ الصيدلية المعيّنة فقط تعدل/تصرف أو تسجل بديلاً؛ الإدارة ذات الامتياز فقط تتجاوز الملكية وفق state machine | PASS محلياً؛ يلزم اختبار BOLA حي بعد النشر |

## العقد التفصيلي

### 1. إنشاء وصفة

المسار المعتمد هو `POST /prescriptions/create`، وهو مقيد بدور `DOCTOR`. يجب أن تحتوي الحمولة على `appointment_id` و`patient_id` و`items` غير فارغة. ينفذ الخادم lookup واحداً مقيداً بـ`id` للموعد و`patient_id` و`doctor_user_id` و`status: IN_PROGRESS`. يعيد المورد الأجنبي أو الموعد المنتهي نتيجة `404` غير مميزة عن الغياب.

```json
{
  "appointment_id": "server-appointment-id",
  "patient_id": "server-patient-id",
  "diagnosis": "optional server-recorded diagnosis",
  "items": [
    {
      "medicine_id": "approved-catalogue-medicine-id",
      "dose": "1 tablet",
      "duration_days": 5
    }
  ]
}
```

لا تستخدم واجهة الطبيب fallbacks مثل `guest_patient` أو معرف موعد محلي. تستخرج الشاشة القيمتين من `GET /provider/jobs/queue?status=active&kind=consultation` وتبقي زر الإصدار معطلاً ما لم تكن حالة العمل الخادمية `IN_PROGRESS`.

### 2. الدواء اليدوي المقيد بالمراجعة

إذا لم يُرسل `medicine_id`، يلزم واحد على الأقل من `manual_name_ar` أو `manual_name_en` إلى جانب `dose` و`duration_days` الموجب. لا يستدعي هذا المسار إنشاء كتالوج أو اعتماده تلقائياً. يحفظ الخادم الصنف داخل `Prescription.items` فقط بالخصائص الآتية:

```json
{
  "is_manual_entry": true,
  "verified": false,
  "manual_review_status": "PENDING_REVIEW"
}
```

تعرض واجهة الصيدلية الصنف اليدوي بصيغة تحذيرية، وتحجب تأكيد الصرف. يُسجل البديل عبر `POST /prescriptions/:id/substitute` بالحمولة التالية، ولا يقبله الخادم إلا إذا كان `new_medicine_id` لصنف كتالوج معتمد:

```json
{
  "item_index": 0,
  "new_medicine_id": "approved-catalogue-medicine-id"
}
```

بعد التحقق يكتب الخادم `substituted_to_medicine_id` و`manual_review_status: SUBSTITUTED_APPROVED` ومرجع المراجع ووقته؛ ثم فقط يمكن لمسار state machine أن يصل إلى `DISPENSED`.

## إصلاح BOLA للـmutations

قبل الإصلاح، كانت قراءة الوصفة محكومة بالمشارك أو الإدارة، بينما لم تطبق methods `transition` و`sendToPharmacy` و`substitute` نفس حدود المورد دائماً. أضيفت قواعد الملكية التالية:

| العملية | الطرف المسموح | الرفض لغيره |
|---|---|---|
| `create` | طبيب فعّال يملك موعداً خادمياً نشطاً | `400` للدور غير الطبيب، و`404` للموعد غير المملوك أو غير النشط |
| `sendToPharmacy` | الطبيب المالك عندما تكون الحالة `CREATED_BY_DOCTOR`، أو إدارة ذات امتياز | `404` مخفٍ للغريب؛ `400` لانتقال حالة غير صالح |
| `transition` | الطبيب المالك للانتقال الابتدائي؛ الصيدلية المعيّنة بعد التعيين؛ أو إدارة ذات امتياز | `404` مخفٍ لغير المشارك؛ `400` للحالة غير الصالحة أو محاولة صرف مادة يدوية معلقة |
| `substitute` | الصيدلية التي يساوي معرفها `pharmacy_id` للوصفة أو إدارة ذات امتياز | `404` مخفٍ للصيدلية غير المعيّنة؛ `400` لبديل غير معتمد |

كما قُيِّد endpoint الموروث `POST /prescriptions/manual-entry` بدور `DOCTOR` فقط؛ لا يمنح الصيدلية أو الإدارة صلاحية إنشاء وصفة باسم طبيب.

## اختبار Sandbox المطلوب بعد النشر

يجب تنفيذ ما يلي بعد أن يؤكد المراجع SHA المنشور، وبحسابات Sandbox فقط ومن دون تسجيل JWT أو PII أو تقرير طبي في Git:

1. يبدأ الطبيب موعد Sandbox حقيقياً حتى `IN_PROGRESS`، ثم ينشئ وصفة كتالوج معتمدة؛ يجب أن تنجح فقط بالـ`appointment_id` و`patient_id` المملوكين.
2. يحاول الطبيب الآخر أو مورد غير مشارك إنشاء وصفة باستخدام نفس الموعد؛ المتوقع `404` أو الرفض الخادمي غير الكاشف.
3. ينشئ الطبيب وصفة تحتوي مادة يدوية معلّمة، ويتحقق أن القائمة الرئيسة للأدوية لا تتغير وأن السجل يحمل `PENDING_REVIEW`.
4. تحاول صيدلية غير معيّنة قراءة طابور المراجعة أو تسجيل بديل؛ المتوقع عدم كشف المورد/عدم تعديل الحالة.
5. تسجل الصيدلية المعيّنة بديلاً معتمداً، ثم تحاول صرف الوصفة؛ يجب أن يفشل الصرف قبل البديل ويصبح ممكناً فقط بعد `SUBSTITUTED_APPROVED` وفق state machine.
6. يوثق لكل صف method/path/status وID منقح وstate قبل/بعد وخطوة cleanup في سجل Phase 16.
