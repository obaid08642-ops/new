## 15.1 — One API client per app (admin BFF client)

### Inventory first: how many HTTP clients did the admin actually have?

Counted before touching anything (`grep` over `admin/src`):

| # | Client | Where | Call sites |
|---|---|---|---|
| 1 | `adminFetch` / `adminMutation` | `src/lib/admin-client.ts` | 87 + 48 |
| 2 | `fetchWithAdminGuard` / `apiFetch` | `src/utils/api.ts` | 48 + 172 |
| 3 | raw `fetch()` in pages | `login.tsx` (4), `theme-control.tsx` (1), `PublicDirectory.tsx` (1), `s/[type]/[slug].tsx` (1) | 7 |
| 4 | BFF → backend `fetch()` | `api/admin/[...path].ts` (3), `auth/{login,verify-2fa,passkey-verify}.ts`, `auth/public/[action].ts`, `impersonation/{start,revoke,context}.ts` | 10 |

No `axios` anywhere. Clients 1 and 2 were near-duplicates: both read the
`admin_csrf` cookie, both rewrite to the BFF path, both set `credentials:
'same-origin'`. So the "one client" problem was really one policy implemented twice
on the browser side plus ten hand-written upstream `fetch` calls on the server side.

### Approach and why it is the least invasive one

New module `src/lib/http/`:

- `policy.ts` — pure and injectable (clock, RNG, sleep): timeouts, the safe-retry
  rule, backoff + jitter, `Retry-After`, request classification, offline check.
- `error-catalog.ts` + `errors.i18n.json` — the client-side view of the 13.R5
  catalogue.
- `client.ts` — `httpRequest()` / `httpJson()`: the **only** `fetch` call site for an
  API in the whole admin, and the error type `AdminApiError`.
- `upstream.ts` — the server-side face of the same client, used by every
  `/api/admin/*` route.

`adminFetch`, `adminMutation`, `fetchWithAdminGuard` and `apiFetch` became thin
wrappers that keep their existing signatures and return contracts and delegate to
the engine. **Consequence: all ~355 existing call sites inherit the policy with zero
call-site edits.** The alternative — rewriting 355 call sites — would have been a
much larger diff with a much larger chance of changing behaviour, and it would not
have been safer. Migrating the 10 raw server-side `fetch` calls and the 7 raw
browser ones was unavoidable, since those bypassed any shared client entirely.

Behaviour deliberately preserved so no page changes meaning:

- `fetchWithAdminGuard` still returns the raw `Response` for every HTTP status and
  still does the 401 → `/login?returnTo=…` redirect, still sends `cache: 'no-store'`.
- `httpRequest` never reads the body, so `res.ok` / `res.json()` call sites keep
  working unchanged (there is a test for exactly this).
- `AdminApiError` is the *same class object* the old `admin-client` exported, so
  `error instanceof AdminApiError` in `AdminGuard.tsx` and `src/lib/step-up.ts`
  still works.
- `error.message` is still the server's own message when there is one (operators
  already read those); the catalogue text is added as `catalogMessage` and
  `nextStep` so nothing is lost.

### The timeout / retry rules, as implemented

- Budgets: **15 s default, 60 s upload, 45 s AI** (`TIMEOUTS` in `policy.ts`).
  An explicit `kind` wins; otherwise a multipart/`FormData` body is an upload and an
  AI path marker is an AI call. The AI markers are the real backend controllers:
  `@Controller('ai')`, `@Controller('ai/content-review')`
  (`backend/src/modules/ai/*.controller.ts`) and
  `medicines.controller.ts` `admin/image-suggestions`.
- Retries: **only** `GET`/`HEAD`/`OPTIONS`, or a request that carries a
  caller-supplied `idempotency-key`. Exponential base 300 ms with equal jitter,
  capped at 4 s. `Retry-After` (delta-seconds or HTTP-date) wins outright, clamped
  to 60 s so a handler is never parked for minutes; the clamp is deliberate and
  asserted by a test.
- The BFF care point from the plan is handled explicitly: `[...path].ts` mints an
  `idempotency-key` when the browser did not send one, and a **minted key is not
  treated as proof of replayability**. Only `callerIdempotencyKey(req.headers)` —
  the key the page actually sent — can make a write retryable. Every non-GET BFF
  route passes `idempotent: false`. Login, OTP verification, passkey verification,
  send-otp, reset-password, device enrolment, impersonation start and impersonation
  revoke are therefore never replayed by the policy (the last two would otherwise
  mint a second support token, and send-otp would send a second SMS).
- Cancellation: `options.signal` is composed with the timeout controller, so a route
  change / unmount aborts the underlying request and the caller sees `AbortError`
  exactly as a bare `fetch` would. `admin/src/pages/admin/fraud-monitoring.tsx`
  already passed a signal and keeps working.
- Offline: `navigator.onLine === false` short-circuits before any network call, with
  the "check your connection" next step.
- Error catalogue: every failure carries `code`, `catalogMessage` (localized) and
  `nextStep`. The code is taken from the backend body when the 13.R5 global filter
  already sent one (`{ code, message }`), otherwise derived from the HTTP status,
  otherwise `UNKNOWN_ERROR` — the catalogue's own documented fallback. Nothing is
  invented.

### The catalogue copy and its parity test

`backend/src/common/errors.i18n.json` was copied byte-for-byte to
`admin/src/lib/http/errors.i18n.json` (the backend file was not modified).

Two genuine bugs were found by these tests while writing them, and fixed in
production code (not in the tests):

- `parseRetryAfter('-5')` returned `0` because `Date.parse` happily parses junk, so

  overloaded backend. Now only the two RFC 7231 shapes are accepted.
- `classifyRequestKind(url)` threw when called without an options object.
