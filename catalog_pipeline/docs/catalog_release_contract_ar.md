# ملحق عقد ملفات الكتالوج — إصدار التنفيذ الأول

**الحالة:** معتمد كأساس تنفيذ. هذا المستند يحدّث فقرة «ملفات الكتالوج» من الخطة، ولا يغيّر قرار السجل الداخلي المعياري متعدد اللغات.

## القرار الحاكم

لن نستخدم ملف JSON ضخمًا واحدًا لواجهة الموقع أو التطبيق، ولن نستخدم ملفًا ضخمًا مستقلًا لكل لغة. يحتفظ النظام داخليًا بسجل حقيقة واحد متعدد اللغات لكل منتج مع الأدلة والحالات، ثم يولّد تلقائيًا مخرجات نشر موزعة: **إصدار immutable، وmanifest عام، وmanifest لكل لغة، وشظايا gzip صغيرة**.

هذا القرار مناسب للبيانات الفعلية: ملف المصدر الحالي يضم 21,013 سجلًا ويبلغ نحو 471.7 MiB بعد فك الضغط، ولذلك لا يجوز أن يكون هو حمولة أي شاشة أو مزامنة على العميل. [1]

> **قاعدة النشر الوحيدة:** لا يظهر سجل في أي شظية عامة إلا إذا كان `public_eligibility=true` و`approval_state="approved_for_display"` و`indexing_eligibility=true` وحالة اللغة المطلوبة `ready_for_export`. غياب قيمة من هذه القيم يعني «لا يُنشر»؛ ولا توجد قيمة افتراضية تسمح بالنشر.

## طبقات التخزين والنشر

| الطبقة | طبيعتها | الغرض |
| --- | --- | --- |
| السجل الداخلي المعياري | سجل واحد متعدد اللغات في قاعدة البيانات أو JSONL منظم | مصدر الحقيقة للوقائع والأدلة وحالة الترجمة والمراجعة |
| سجل التصنيف والأصول | محايد عن اللغة | `product_kind`، شجرة الفئات، الفلاتر، الصور وحقوقها |
| طبقة التجارة المتغيرة | حسب السوق/العملة | السعر، الإتاحة، المخزون والعروض؛ لا تدخل النصوص الثابتة |
| artifacts النشر | لغة واحدة لكل ملف | manifests، فهرس منتجات، وشظايا للويب والتطبيق |

لا يخلط artifact منشور واحد بين اللغات. لا يعني هذا أن هناك «ست حقائق مختلفة»؛ بل توجد حقيقة داخلية واحدة، وتُنتج منها طبقة عرض لكل لغة.

## بنية الإصدارات المعتمدة

```text
catalog-releases/
  latest.json                           # مؤشر قصير الكاش وموقّع
  v2026-08-20.1/                        # إصدار immutable لا يتغير بعد النشر
    manifest.json                       # manifest عام، موقّع
    taxonomy.json.gz                    # الشجرة وتَسميات الفئات المعتمدة
    assets-manifest.json.gz             # الأصول المشتركة ومحايدة اللغة
    ar/
      manifest.json
      product-index.json.gz             # id/slug -> shard + revision
      medicines/id-100000-104999.json.gz
      medicines/id-105000-109999.json.gz
      ...
    en/
      manifest.json
      product-index.json.gz
      ...
    commerce/
      sa-SAR/manifest.json              # اختياري: السعر/الإتاحة سريعَا التغيّر
```

يُعرّف `latest.json` الإصدار النشط فقط. التراجع (rollback) يعني تغيير المؤشر إلى manifest إصدار سابق مكتمل وموقّع؛ ولا تعاد كتابة ملفات الإصدار السابق. يحتفظ العميل بآخر إصدار ناجح محليًا حتى ينجح التحقق من الإصدار الجديد بالكامل.

## قاعدة التجزئة

التقسيم المعتمد هو:

```text
locale → main_category_id → stable ID range → gzip shard
```

| القرار | القاعدة المعتمدة |
| --- | --- |
| المستوى الأول | `locale`، لأن النصوص وSEO وواجهة العرض تختلف فعلاً بحسب اللغة |
| المستوى الثاني | `main_category_id` ثابت، لا الاسم المحلي للفئة |
| المستوى الثالث | نطاق `id` ثابت أو جزء وفق حد الحجم؛ لا تقسيم أبجدي بالاسم |
| بدء التقسيم | الفئة التي تتجاوز 2,000 سجل مرشحة للتقسيم، لكن الحجم المضغوط الفعلي هو العامل الحاسم |
| الهدف الحجمي | 150–400 KiB بعد gzip في الحالة المعتادة |
| الحد الأعلى | 1 MiB بعد gzip للشظية الواحدة، إلا بقرار موثق خاص |
| عدد السجلات | مؤشر مساعد فقط؛ 1,000–2,000 سجل مناسب إذا كانت السجلات مضغوطة وخفيفة، ولا يُفرض إذا كانت حقول الوصف غنية |
| ترتيب السجلات | `id` تصاعدي وثابت داخل الشظية |
| تسمية الشظية | نطاق واضح مثل `id-100000-104999.json.gz`؛ لا يكتفى باسم `part-0001` |

لا نعتمد عدد السجلات وحده لأن طول أوصاف المنتجات والصور وروابطها يغير الحجم بدرجة كبيرة. يحدد مولد الإصدار نطاق الشظية بعد قياس الحجم المضغوط، ثم يسجل `compressed_size`, `uncompressed_size`, `record_count`, `min_id` و`max_id` في manifest.

## عقد الـmanifest

| الحقل | الغرض |
| --- | --- |
| `schema_version` | التحقق من توافق العميل قبل القراءة |
| `release_id` | مثال: `v2026-08-20.1` |
| `created_at` | وقت إنشاء artifact بصيغة ISO-8601 |
| `source_snapshot_hash` | بصمة مدخلات السجل الداخلي |
| `taxonomy_revision` | نسخة الشجرة المعتمدة |
| `locale_registry_revision` | نسخة سجل اللغات والـfallback |
| `signature` و`key_id` | التحقق من أصالة manifest، لا من سلامة الملف فقط |
| `locales` | حالة كل لغة ورابط manifest اللغة |
| `shards` | الرابط، الحجم، SHA-256، النطاق، عدد السجلات، revision |
| `tombstones` | سجلات محذوفة أو غير مؤهلة يجب إزالتها من التخزين المحلي |

يلزم أن يحمل كل manifest خاص باللغة: `locale_id`, `direction`, `language_publication_state`, وعدد سجلات هذه اللغة، إضافة إلى الشظايا وفهرس المنتج. لا يُضاف `hreflang` في artifact بوصفه نصاً فقط؛ إذ يجب أن يُنتج فعلياً في HTML أو sitemap للصفحات العامة المكتملة وبالعلاقات المتبادلة الصحيحة. [2]

## عقد المنتج المنشور

يحتوي السجل المنشور على **صياغة اللغة المطلوبة فقط**، مع معرّفات محايدة مشتركة. لا تدمج الترجمة الإنجليزية وسواها كسطر إضافي داخل `display_name`.

```json
{
  "id": "103108",
  "locale": "ar-SA",
  "record_revision": 4,
  "product_kind": "medicine",
  "primary_taxonomy_id": "medicines.cardiovascular",
  "secondary_taxonomy_ids": ["therapeutic.cardiovascular"],
  "display_name": "…",
  "official_name": "…",
  "search_aliases": ["…"],
  "slug": "…",
  "content": {"description": "…", "warnings": ["…"]},
  "assets": {"primary_image_id": "…", "image_ids": ["…"]},
  "publication": {"approved_at": "…", "indexing_eligibility": true}
}
```

الحقلان `official_name` و`search_aliases` يسمحان بإظهار اسم العلامة الرسمي أو البحث بالإنجليزية من دون إفساد الاسم المحلي أو metadata. تستخدم صفحة الويب العامة هذه البيانات لإخراج العنوان والوصف والـcanonical وبيانات `Product` المنظمة بدقة؛ لا تكفي ملفات JSON وحدها للفهرسة. [3]

## الحَوكمة والأهلية

| الحقل | القيم المقترحة | قاعدة الاستخدام |
| --- | --- | --- |
| `public_eligibility` | Boolean | يحدد السماح المبدئي بالعرض العام؛ لا يستنتج من كونه موجوداً في المصدر |
| `approval_state` | `draft`, `needs_review`, `approved_for_display`, `blocked` | لا ينشر سوى `approved_for_display` |
| `indexing_eligibility` | Boolean | يحدد جواز الظهور في sitemap وعمليات الفهرسة؛ قد يعرض المنتج في تطبيق مسجل دخول دون فهرسة عامة |
| `locale_status` | `not_started`, `partial`, `review_required`, `ready_for_export`, `blocked_by_source` | لا تصدر شظية اللغة للسجل إذا لم تكن `ready_for_export` |
| `medical_claims_status` | `not_applicable`, `requires_verification`, `verified`, `blocked` | لا ينشر حقل طبي حساس إذا لم ينجح مساره المخصص |
| `tombstone_reason` | `deleted`, `withdrawn`, `not_public`, `superseded` | يسمح للتطبيق بحذف نسخة قديمة بشكل صحيح |

هذه البوابة تمنع نشر السجلات التي تبدو مكتملة شكلياً لكنها لم تمر بالحالة الحاكمة. ولا يجوز تحويل حالة مراجعة موروثة عامة إلى `approved_for_display` تلقائياً؛ يجب أن تنتج هذه الحالة من سير المراجعة الجديد.

## الكاش، CDN، والاسترداد

| المورد | سياسة التخزين المقترحة | السبب |
| --- | --- | --- |
| `v<release>/...` وكل shard | `Cache-Control: public, max-age=31536000, immutable` | الاسم يتغير مع الإصدار والملف لا يتغير |
| `latest.json` | TTL قصير، `max-age=60` مع ETag | معرفة إصدار جديد بسرعة دون هدر تحميل |
| manifest الإصدار | immutable عند ربطه بإصدار؛ ويمكن أيضاً فحص ETag | الوثيقة جزء من إصدار ثابت |
| manifest اللغة | immutable داخل مسار إصدار | تطابق الشظايا مع نسخة محددة |
| overlay التجارة | TTL قصير وفق تغير السعر والإتاحة | لا تُعيد تنزيل محتوى ثابت من أجل سعر |

في التطبيق: ينزل manifest إلى مسار مؤقت، ثم يتحقق من التوقيع ونسخة الـschema. بعدها ينزّل الشظايا المتغيرة فقط، ويتحقق من SHA-256 وعدد السجلات، ثم يبدّل مؤشر الإصدار المحلي atomically. لا يحذف الإصدار السابق إلا بعد نجاح كامل الدورة. تحديثات Expo عبر الهواء لتطبيق JavaScript مستقلة عن مزامنة بيانات الكتالوج هذه. [4]

في Next.js: تستخدم صفحات المنتج API قراءة أو product index مباشر من جهة الخادم؛ ويستخدم manifest و`record_revision` لتوجيه `revalidatePath` أو `revalidateTag` للصفحات المتأثرة. ISR مناسب للبيئات التي تشغل Node.js، ولا يعمل مع static export الخالص. [5]

## دور مصادر API وsitemap

تُستخدم واجهة المنتج بالعربية والإنجليزية وخرائط الموقع كمراجع **تحقق موجّهة** عند وجود نقص أو تعارض أو الحاجة إلى مطابقة رابط منتج وفئته. لا تصبح مصدر نسخ جماعي آلي أو مصدر حقيقة بديل عن السجل الداخلي. إن كانت الحقيقة طبية، يكون المصدر التنظيمي أو النشرة المعتمدة أو الشركة الرسمية هو المرجع الأول؛ واجهة المتجر وsitemap تساعدان في الهوية والتصنيف التجاري وعناوين الصفحات فقط.

## معايير قبول إصدار النشر

لا يعد الإصدار جاهزاً إلا إذا تحققت جميع الشروط الآتية:

| الفحص | شرط القبول |
| --- | --- |
| مخطط البيانات | كل manifest وكل shard يجتاز JSON Schema المناسبة |
| المعرّفات | فريدة داخل الإصدار، وتطابق ما في product index والشظايا |
| الأهلية | لا يوجد سجل منشور يخالف بوابة الحَوكمة الأربع |
| اللغة | كل سجل منشور في لغة ما حالته `ready_for_export` لتلك اللغة |
| السلامة | كل SHA-256 صحيح، وتوقيع manifest صحيح |
| الاسترداد | `latest.json` يشير إلى إصدار سابق صالح أو إصدار جديد صالح مع اختبار rollback |
| SEO | لا تُصدر روابط فهرسة إلا للصفحات العامة المؤهلة؛ وتختبر alternate/canonical على HTML |
| offline | تحميل جزئي، تبديل ذري، وعودة إلى آخر إصدار سليم في اختبار محاكاة الخطأ |
