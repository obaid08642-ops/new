# 22.3 Bundles and alternatives: built with the pharmacist-safe rules

**Rules (plan 22.3, owner-approved):** no prescription or controlled item is ever promoted (as an alternative or as "frequently bought together"); interaction warnings are shown.

**Built (backend)**
- `NOT_PROMOTABLE_FILTER` (`medicines/promotion-rules.ts`): `requires_prescription`, `controlled` and the older `is_rx` flag are not true.
- Every promotion path uses that filter: alternatives (`MedicinesService.alternatives`, the `alternatives` of the medicine details), the entity-graph alternatives and condition-medicines list, the recommendations (`seo-search` `medicineRecommendations`), and the product equivalents and similar products (`publicProductEquivalents`). A prescription product therefore promotes nothing on its page (its similar list is empty).
- New `GET /medicines/:id/frequently-bought-together` (public): items bought with this one, counted from delivered or completed orders (counts only, no patient data), most frequent first, at most 6. A pairing is shown only when at least 3 orders contain it (one order must not be identifiable). A prescription item suggests nothing. Each suggestion carries `interaction_warnings` against the item being viewed.
- Interaction rules moved to `ai/interaction-rules.ts` (unchanged rule set). `matchInteractions` keeps the existing patient check's behaviour; `pairInteractions` is new.

**Tests:** promotion filter on alternatives and condition list; prescription source suggests nothing and reads no orders; Rx suggestions filtered by the query; warnings attached; interaction rule pairs in either order; existing alternatives projection and ai tests still pass.

**Not in this PR:** a patient-facing "frequently bought together" block (screen work belongs to the design batch); the rule set is still the short built-in list (a larger, pharmacist-reviewed list is an owner decision).

**Known limits**
- Orders whose lines carry only `matched_sku` (intake and seed data) are not counted: the aggregation matches `items.medicine_id`.
- `pharmacy_orders` has no index on `items.medicine_id`, so the endpoint scans that collection on each call. It has no cache yet; a multikey index and a short public cache are the next step.
- The old-price branch for prescription alternatives in `details()` is now unreachable and left in place.

**Open questions (answer on this PR)**
- Co-purchase counts use delivered and completed orders only. Should pending orders count too?
- Is a threshold of 3 orders right, and should the index and cache be built in this PR?
- The interaction list is the existing six-rule set. Should the pharmacist supply the list for this feature?
