# R7 - Data tier: replica set, PITR, pools, what moves off the host (2026-11-03)

Owner topology (2026-11-02): launch on ONE bigger VPS (8-16 GB), self-hosted, no managed service without an approved price. Everything below works on one host first and splits later without code changes (connection strings and member hosts are config).

## Where we are (found in the repo)
- MongoDB 7 in Docker, a **single-member replica set** `rs0` (`deploy/mongo/mongod.conf`). One voting member: no failover, no read scaling.
- PITR exists: nightly encrypted dump + an oplog slice every 10 minutes, shipped to a private bucket (`deploy/scripts/oplog-backup.sh`), monthly restore drill (`dr-drill.sh`) with targets **RPO 900 s, RTO 3600 s**. The brief's target is **RPO < 1 min, RTO < 15 min**: the slice interval alone makes 1 min impossible with this design.
- The driver pool was 200 per process against `maxIncomingConnections: 300` (api + worker could ask for 400, ~1 MB each). **Fixed in this PR** (below).

## Why the arbiter and the two phases (what the tasks enforce)
A replica set with **2 voting members is worse than 1**: lose either and there is no primary. So a data member is first added **non-voting** (hidden, priority 0, votes 0), it syncs, and only then the third vote (an arbiter) is added in the **same** reconfig that gives the secondary its vote. With an arbiter MongoDB requires an explicit default write concern; the task sets `w:1` (journaled by default). Consequence to accept knowingly: with primary + secondary + arbiter, **if the secondary is down, writes with `w:majority` cannot be acknowledged**; the code uses the default (w:1) and transactions inherit it, so the app keeps writing, but then the standby is not protecting those writes until it is back. A three-data-member set removes the caveat (needs a third host).
Tasks (not in `tools/ops/RUN`; the lead reviewer schedules them on `review/server-inspect`):
- `tasks/100-mongo-rs-status.sh` - read-only: members, lag, votes, oplog window, connections, age of the newest slice and dump, and the primary's member host.
- `tasks/101-mongo-rs-member.sh` - `PHASE=data` then `PHASE=vote`, dry run first, rollback removes only the two members; refuses shell metacharacters; `vote` refuses until the secondary is SECONDARY with lag <= 30 s. Tested against a fake mongosh (`tools/ops/tests/test_mongo_rs_tasks.py`).
- **Before the first run**: the primary's own member host is probably a Docker alias (`mongodb:27017`) the standby cannot reach: change it in the same change window to the WireGuard address; mongod must listen only on the private link; keep the keyFile (already enabled) and add TLS between members. Nothing of this is applied here.

## Connection pools (done in this PR)
`MONGO_MAX_POOL_SIZE`/`MONGO_MIN_POOL_SIZE` are now set in compose: api 80/10, worker 40/5. `tools/ops/mongo_pool_budget.py` (CI: `.github/workflows/mongo-pool-budget.yml`, test `test_mongo_pool_budget.py`) checks worst case = sum over clients of (maxPoolSize + 4 monitor connections) x replicas + 50 for tools <= `maxIncomingConnections`, and <= 25 % of the mongodb memory limit in MB. Today: 282 of 300. The fastapi service has no readable Mongo client in this repo, so it is counted at the pymongo default of 100 (unknown, check its image). **With the second API replica (R4) the api pool must be 40 each** (the test proves 80 x 2 does not fit). 134 req/s at ~20 ms of database time per request is about 3 concurrent operations, so 80 is generous; lowering from 200 does not throttle the measured load. Not measured on production: look at `100-mongo-rs-status` "connections: current=" first.

## Read preference for heavy reads
A **hidden member is invisible to normal clients**, so `secondaryPreferred` will not reach it. The design is a second, non-hidden secondary tagged `{use:"analytics"}` or the hidden member reached by a dedicated connection string with `directConnection=true`. That is R17; here: one dedicated connection (a second Mongoose connection with `readPreference=secondary` to the standby's address) is the code change, and it needs the standby first.

## Redis and Meilisearch off the app host
Configuration, not code, since the compose change of this section: `deploy/docker-compose.production.yml` used to fix `REDIS_URL` (3 places) and `MEILI_URL` (2 places) to the Docker aliases, so an env value alone could not move them. They now read `${REDIS_URL:-redis://:${REDIS_PASSWORD}@redis:6379}` and `${MEILI_URL:-http://meilisearch:7700}`: **unset, the resolved file is identical to before** (pinned by `tools/ops/tests/test_compose_data_urls.py`, which also checks it with `docker compose config`), set in `.env.production` they move the API, the worker and fastapi. The backend takes the Redis host from `REDIS_URL` first, so `REDIS_HOST`/`REDIS_PORT` stay as they are. **Before the first deploy with this change run `102-data-services-move-dryrun.sh`**: it says whether `.env.production` already holds a `REDIS_URL` or `MEILI_URL` (then the new default would honour it, which the old file ignored). Nothing is moved by this change; the owner decides the move. Env names: `REDIS_URL`/`REDIS_CACHE_URL`, the Meilisearch host/key env of the API and worker. Order of value per MB of RAM freed on the app host: Meilisearch (limit 1024m, rebuildable index, search only) first, then Redis (queues and sessions: latency-sensitive, move only to the same private network). Move = run the service on the standby VPS, point the env at the WireGuard address, re-index (Meilisearch) or let queues drain (Redis). Not done here; it needs the second host.

Dry run of the move (names and yes/no only, no values, refuses a public address, prints the migration and rollback steps): `tools/ops/tasks/102-data-services-move-dryrun.sh`, tested by `tools/ops/tests/test_data_move_dryrun.py`. Rollback: put the values back to the aliases and recreate the same containers; keep the local containers stopped, not removed, for a day.

## Host RAM is the ceiling: why mongod restarts, and what decides the fix (ops run 108, 2026-11-09)
**What `96h` showed:** `nabdah-mongodb` restarts 296 -> 356 in 13 h (`unless-stopped`, health OK); the container's cgroup hit its 1.6 GB limit 3755 times (`memory.events max`), `oom_kill 0` for the current instance; the kernel log has 11 "Killed process (mongod)" lines, but `96h` could not say when they happened or whether they were cgroup or host-wide kills (`dmesg` counts since boot); MemAvailable about 1050 MB; mongod uses 950 MiB of 1.56 GiB.

**The WiredTiger cache is NOT the cause and is already explicit.** `deploy/mongo/mongod.conf` sets `cacheSizeGB: 0.6`, compose starts mongod with `--config /etc/mongod.conf`, and `tools/ops/mem_budget.py check` ties the value to the host plan. Repeating it as `--wiredTigerCacheSizeGB` on the command line would be a second source of truth and was not done. Without that setting mongod would size the cache from HOST RAM (50 % of RAM minus 1 GB) and a bigger host would push it past the container limit; `tools/ops/tests/test_mongod_cache_explicit.py` now fails if compose stops reading the file, adds the flag, or if cache + connections (300 x 1 MB) + 350 MB of other structures exceeds 85 % of the container limit (today 614 + 300 + 350 = 1264 MB against 1360 MB). Changing 0.6 to 0.5 would not be justified by these numbers.

**Why it still dies: the host is the limit.** `deploy/HOST_RAM_MB` is 3800. The `mem_limit`s in compose add up to 7680 MB (2.0x the host) and the reservations to 3160 MB. Limits are ceilings, not reservations, so when several containers rise together the kernel can run out of memory before any cgroup limit applies and then picks a victim by `oom_score_adj` (mongod has -900, so it is chosen last; whether it was chosen at all is exactly what `96j` shows). R1 documents this as an honest limit of a 3.8 GB host; `earlyoom` (98p) is the guard that kills meilisearch/clamav first. The `max` events themselves are mostly the cgroup reclaiming page cache at its limit, which is harmless; what matters is the anon part.

**Read `tools/ops/tasks/96j-mongo-cache-check.sh` (read-only) before changing anything.** It prints the cache mongod actually runs with next to the line in the repo file (a mismatch means the file was edited but mongod not restarted), the cgroup split anon / file / peak, the kernel kills of the last 48 h **with their time** and kind (cgroup = the 1.6 GB limit; global = the host ran out) and the log-derived count of starts that had no signal or shutdown before them. (`96h` could not show this: `dmesg` counts since boot, and `docker events` keeps only a short in-memory buffer that health checks fill, so its die-event list comes back empty.) Decision rule:
- kills are old or none, restarts without a prior shutdown are few -> mongod is not being killed, look at what stops it (`signals_received`/`shutdowns`) and at the health check;
- kills in the last 48 h with `kind=global` and other commands killed too -> the host is short: free memory (meilisearch/clamav off the host, R9 and the dry-run in 102), or more RAM;
- kills with `kind=cgroup` and anon near the limit -> then, and only then, lower `cacheSizeGB` by 0.1 through `mem_budget.py render --write` (never by hand), with this evidence in the PR;
- the file and the running value differ -> restart mongod in the next deploy window so the file takes effect.

**The owner's decision:** more RAM is the durable fix. `echo <MB> > deploy/HOST_RAM_MB && python3 tools/ops/mem_budget.py render --write` rewrites every limit and the cache for the new size (8192 MB gives mongod a 4688m limit; plan in R1). Providers and prices: `docs/ops/SERVER_MOVE.md`. Until then the restarts are the cost of running a 7.7 GB limit plan on a 3.8 GB host.

## Launch checklist: the RAM to buy (owner decision 2026-11-09)
**Decision:** no RAM upgrade now (no users yet, no paying for idle capacity). The RAM is raised **at launch**. Everything is built as if the host were sized for launch: the design is **not** bent to the 3.8 GB host. The safety measures already merged stay (mongo-wait before the pre-deploy dump, dump retry, alert hysteresis, the watchdog mail gap). The OOM-style restarts on the current host are known and accepted until launch; the alert rules (#2530: a mail only for a confirmed change, at most one repeat per 24 h) keep them from flooding the owner's inbox.

**How the size is decided (`tools/ops/mem_budget.py`):** steady use (sum of `mem_reservation` of the always-on containers, clamav excluded) + the largest one-off container (700 MB) + the host reserve (10 % of the host, at least 512 MB) must fit in `deploy/HOST_RAM_MB`. The tool then scales mongod, redis, meilisearch, backend, worker and patient-web by one factor so the plan fills the host. Output of `mem_budget.py render --host-ram-mb N` (limits in MB, no files written):

| host RAM | scale | mongod limit / cache | sum of always-on reservations | + one-off 700 + reserve | sum of ALL limits |
|---|---|---|---|---|---|
| 3800 (today) | 1.0 | 1600 / 0.6 GB | 2560 | 3772 | 7680 |
| **8192 (launch floor)** | 2.94 | 4688 / 1.75 GB | 6594 | 8113 | 16944 |
| 12288 | 4.69 | 7488 / 2.8 GB | 10290 | 12218 | 25344 |
| 16384 | 6.44 | 10288 / 3.85 GB | 13986 | 16324 | 33744 |

**Size to buy: at least 8 GB (8192 MB).** It is the first common size at which the budget rule holds with the services scaled to roughly 3x today (mongod gets a 4.7 GB limit and a 1.75 GB cache instead of 1.6 GB and 0.6 GB). Today's measured use with almost no traffic (ops run 109, `96j`/memory report): mongod 871 MB, backend 325 MB, worker 281 MB, redis 255 MB, patient-web 136 MB, nginx 66 MB, admin-web 57 MB, livekit 24 MB, meilisearch 12 MB: about 2.1 GB, so the 3.8 GB host is the ceiling only because the plan is sized for launch. The model fills whatever host it is given, so the right size above 8 GB depends on the launch working set, not on this document: take the next row (12 or 16 GB) when, after launch, any of these holds for a week: swap in use stays over 256 MB (`memory` task WARN), mongod's `memory.events max` keeps rising on the new instance, or `MemAvailable` stays under 15 % of the host.

**Launch steps (all existing tooling, nothing new):**
1. Move the services to the new host or resize it (providers, prices, move plan: `docs/ops/SERVER_MOVE.md`; data residency rules for the provider: `docs/platform/R19-data-residency.md`).
2. `echo 8192 > deploy/HOST_RAM_MB && python3 tools/ops/mem_budget.py render --write` rewrites every limit, reservation, node heap and `cacheSizeGB`; commit the result in its own PR (the CI check `mem_budget.py check` and `check-compose-limits.py` must pass).
3. Deploy in a normal window. mongod reads the new `mongod.conf` at its next recreate, which the deploy does; confirm with `96j-mongo-cache-check` (running `cacheSizeGB` equals the file) and `98-memory-report` (no WARN).
4. Re-run `98q-alert-mail-state` a day later: the mails-per-day table must show no mail for a state that did not change.
