# R14 - Data integrity inside the database (2026-11-03)

Found: 0 `$jsonSchema` validators; 224 `unique: true` declarations in the schemas with no way to know whether each index really exists in production (a unique index whose build failed because duplicates already existed is silently absent; R21 found two such candidates); no scheduled check for impossible states or orphans.

## 1. Validators (`modules/db-integrity/db-validators.ts`, CLI `src/scripts/db-validators.ts`)
Seven collections: `transactions`, `platformledgerentries`, `appointments`, `coupons`, `refund_totals`, `refund_reservations`, `durable_events`. Each validator states only what the code already guarantees (required keys the Mongoose schema marks required, the enums the code defines, amounts that cannot be negative), no new business rule. `validationLevel: moderate` always: a document that is ALREADY invalid is not re-checked when something unrelated in it is updated, so legacy rows cannot make healthy updates fail.
**A test caught a real mismatch while I wrote them**: `LedgerService.append` stores `gross`, `commission`, `vat` as `null` when absent (the driver turns `undefined` into null); the first draft refused every ledger row. The validators now allow null on those optional fields and the spec runs the real writers (`LedgerService.append`, the Mongoose Transaction model, `DurableEventsService.enqueue`, `RefundExecutor.execute`, `CouponService.apply`) in `error` mode.
**Rollout (reversible, nothing is applied by this PR)**: (1) dry run on the server: `node dist/scripts/db-validators.js` prints the plan and, per collection, how many EXISTING documents would not pass; (2) `DB_VALIDATORS_CONFIRM=<db name> ... --apply=warn`: mongod logs violations, writes go through; (3) a week later, if the mongod log and the findings below are clean, `--apply=error`; (4) `--remove` takes them off. Collections that do not exist yet are skipped, never created. `collMod` fails with a clear error while an index build runs on that collection; run it outside deploys.
**Not covered yet** (I did not read all their writers, a wrong validator would reject real traffic): orders, pharmacy_orders, lab/radiology/home-care bookings, payouts, wallets, users. Same recipe, one collection per PR with the writer-in-error-mode test.

## 2. Nightly checks (`DbIntegrityService`, 03:20 UTC, worker, one run across workers via the R3 lease)
Fifteen read-only invariants (`invariants.ts`), each bounded (5 sample ids, `maxTimeMS` 30 s). `error` = impossible by the code: negative or over-refunded transactions, unknown or negative ledger rows, duplicated refund/earning/clawback rows, coupon used over its maximum, a refund reservation stuck for an hour, two active appointments or two slot locks for one doctor/provider and slot, an appointment outside the state machine, dead outbox events. `review` = unusual, a legacy path may produce it: paid without `paid_at`, status refunded with a smaller refunded amount, per-user coupon counter that differs from the usage rows, stuck outbox events, ledger rows whose `order_id` matches no booking in any collection (orphans, last 14 days).
Findings are kept once per id in `db_integrity_findings` with first/last seen, shown by `GET /api/v1/admin/db-integrity` (permission `data.export`), resolved automatically when they stop showing, counted in the gauge `nabd_db_integrity_error_findings`, and an error-level log line (Sentry) lists the failing ids when any `error` is open. The tests seed every violation and assert each invariant finds exactly its own, and that healthy data reports nothing.

## 3. Unique-index review (`index-audit.ts`, same nightly run)
For every registered Mongoose model, each unique index its schema declares must exist with the same key, `unique: true` and the same partial filter. A missing one is reported together with the duplicate groups that stop it from being built (the pre-flight; it honours the partial filter), a non-unique or differently filtered one as such. The first production run is the answer to "which of the 224 unique declarations are really enforced".

## Limits
- Nothing was run against production data; the first `INVALID_EXISTING` numbers and the first nightly findings are the real result of this work. Expect noise in `review` on old data.
- `moderate` means: MongoDB does not validate updates to documents that are ALREADY invalid (the test shows an invalid legacy row accepting an unrelated update), so a legacy-invalid row can be changed into another invalid state. `strict` closes that and needs the legacy rows repaired first.
- Orphan detection looks at ledger rows only; other cross-collection links (a notification for a deleted user, a family member of a deleted account) are not checked.
