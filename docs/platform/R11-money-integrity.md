# R11 - Money correctness (2026-11-02)

State found: amounts are JS doubles with `round2()` copies in 5 files (`Math.round(n * 100) / 100`, wrong for 1.005, 4.35 * 100 = 434.99999999999994, ...), 0 Decimal128 / integer fields, `platformledgerentries` rows with doubles, Moyasar refunds sent as `Math.round(amount * 100)`. The existing "daily gateway-ledger reconciliation" (`FinanceSuiteService.reconciliation`) never calls Moyasar: it compares our own collections (and has a dead `mapped` stub).

## Decision: integer halalas, stored as plain integers (`*_halalas`), not Decimal128
SAR has 2 decimals; a safe integer holds up to 90 trillion SAR; integers sum, compare and index exactly, need no driver type, and Moyasar already speaks halalas. Rates and splits use BigInt integer math (`common/money.ts`: `toHalalas`, `fromHalalas`, `formatSar`, `rateOf`, `percentOf`, `allocate`, `sumHalalas`, `isCleanSar`). Rounding rule: half away from zero, decided on the decimal text, never on a binary double.

## Daily checks (`modules/finance-integrity`)
- `FinanceIntegrityService.daily()` (cron 01:40 UTC, worker role; one run per (kind, day) across any number of workers via a unique insert in `finance_integrity_runs`).
- **Ledger invariants** for every order touched in the last 48 h, in halalas: INV-1 refunds never exceed what was paid (card); INV-2 ledger refunds equal the payment record's `refunded_amount`; INV-3 clawback, commission reversal and VAT reversal never exceed the earning; INV-4 the provider's clawback is proportional to the refunded share of what the patient paid (tolerance 1 halala per refund); INV-5 every amount is finite, >= 0 and a clean 2-decimal value; INV-6 no duplicated idempotent row. NOTE: the brief's "sum of entries per order = paid - refunded" cannot be asserted literally: the earning row holds only the provider's lines and the platform keeps its own fees outside it, so INV-4 states the same idea (what is kept is proportional to what is not refunded) in a way the data supports.
- **INV-7 shadow consistency** (with the P1 dual write of transactions and moyasar_payments): a payment row carrying `amount_halalas` / `refunded_amount_halalas` must carry the halalas of its double, finding `payment_shadow_mismatch`. A mismatch means a write changed the double without the shadow (a raw `collection()` write that skipped `common/halala-shadow.ts`). Rows with no shadow yet are not findings (the backfill fills history); a double with float drift has no shadow by design.
- **Moyasar reconciliation** for yesterday: pages `GET {moyasarBase}/payments?created[gte]&created[lt]&page=N`, compares id, status, amount (halalas) and refunded with `transactions` and `moyasar_payments` (sandbox ids ignored). Findings: `gateway_paid_not_recorded`, `recorded_paid_not_at_gateway`, `status_mismatch`, `amount_mismatch`, `refund_mismatch`. **Off by default (`FINANCE_RECONCILE_MOYASAR=1` enables it)**: the list endpoint's query and `meta.next_page` pagination are written from the public API docs and tested against a fake, NOT against the live API, and the match between our `gateway_intent_id`/`moyasar_id` (invoice or payment id) and the gateway payment id has to be seen on real data first. Run once by hand with the sandbox key and look at the findings before enabling.
- Findings: `finance_integrity_findings` (one per code + entity, `status: open`), `GET /api/v1/admin/finance/integrity` (admin, `finance.read`), error log line per run (Sentry). Not yet an admin-alert kind: the admin alerts screen has a fixed kind list and Arabic texts (admin/src/pages/admin/alerts.tsx); adding `finance_integrity` there is a small follow-up that touches the admin UI. R5's external alert (#2407) can page on the error log or on the endpoint's `count`.

## Tests
`money.spec.ts` (21: float traps, 1M round trips, BigInt rate, allocate sums, rejects), `finance-integrity.spec.ts` (invariant cases incl. rounding tolerance, reconciliation cases, real MongoDB: one run per day under 3 concurrent workers, no duplicate findings, clean ledger = none, paged gateway fetch), `halala-backfill.spec.ts` (dry run writes nothing, unclean skipped and listed, originals untouched, idempotent, ledger needs the flag, unclean rows do not hide clean ones), and the existing finance-engine specs pass with the ledger dual write.

## Not done here (and why)
Replacing `round2` in the 5 files and the Moyasar `Math.round(amount * 100)` call: these are P2, after P1 data exists; changing them first would change money behaviour without the cross-check. Invoices/ZATCA totals, wallet and payouts need their own P1 PR. A `$jsonSchema` validator forcing integers is R14.
