# Facility accounts audit — 2026-10-23

Read-only research (no code changed). How facilities (polyclinic, hospital, medical complex) and their workers use the platform today in the backend, provider-app and admin. Paths are relative to the repository root; `file:line` was read on `main` at the time of writing.

## Summary

There is **no single facility-membership model**. Four parallel mechanisms exist, each with a different identity rule, and none matches the target (practitioner owns an account and licence, joins one or several facilities by invitation, facility can deactivate only the membership). Earnings are always credited to the **practitioner's own** provider account; the facility has no payout account and "wallet" for a facility is a revenue sum.

## 1. Account types and what a facility can own

- Provider types: doctor, pharmacy, hospital, clinic, lab, radiology, home_care, nursing (`backend/src/common/enums.ts:67-76`). Roles include `HOSPITAL`, `HOSPITAL_ADMIN`, `BRANCH_ADMIN`, `RECEPTIONIST`, `PHARMACIST`, `DOCTOR`, `LAB`, `RADIOLOGY`, `NURSE`, `NURSING`, `HOME_CARE`, `FINANCE` (`enums.ts:1`, `PROVIDER_ROLES` `:38`).
- A **clinic and a hospital share one role**: `typeToRole` maps both `CLINIC` and `HOSPITAL` to `UserRole.HOSPITAL` (`backend/src/modules/provider/providers.service.ts:443-452`). A "medical complex" has no type of its own.
- Self-registration creates one user + one provider profile per account, `active:false` until admin approves (`providers.service.ts:139-170`); admin can create an account with `auto_approve` (`:178-200`).
- One facility account can hold **several practitioners and service units**, but through roster lists and sub-users, not typed units:
  - Provider profile holds `doctors_roster` (typed items with optional `doctor_user_id`, name, specialty, modes, prices, insurance, hours) (`backend/src/schemas/provider-profile.schema.ts:173-187`), `lab_roster` `:189-190`, `radiology_roster` `:192-193`, `nursing_roster` `:195-196` (untyped `any[]`), `pharmacy_roster` `:256`.
  - Branches (`provider-branch.schema.ts:31`, `doctors_roster: string[]` of user ids) and departments (`hospital.controller.ts:13-31`).
  - Units are not first-class: a facility with a pharmacy and a lab is one account with `pharmacy_roster`/`lab_roster` arrays, not separate unit accounts with their own licence, wallet or catalogue.
- Licence/CR fields exist per profile (`provider-profile.schema.ts:41-47`: license_number, scfhs_license_number, cr_number, moh_license_number, sfda_license_number; `provider/schemas/index.ts:70-71`: medical_license_number, facility_license_number). The same profile type carries both facility and practitioner licences; nothing ties a practitioner licence to a facility membership.

## 2. Onboarding rosters

- Roster DTO fields are free `Record<string, unknown>[]` lists (`backend/src/modules/provider-onboarding/provider-onboarding.dto.ts:258,372,391,421,443`), saved onto the profile (`provider-onboarding.module.ts:166,170`). The onboarding module only **stores** them and uses them for directory search by name/specialty (`:470-471,489`). It does not create users, send invitations or link accounts. **Rosters are name lists, not login accounts.** `doctors_roster[].doctor_user_id` is optional and nothing in onboarding fills it.
- Real accounts for staff come from three other paths:
  1. **Owner creates the user** (`POST hospital/staff`, `hospital-staff.module.ts:41-71`): the owner supplies phone, email and password (bcrypt, `:43-55`), `verified:true` (`:57`), `parent_provider_account_id` = the facility (`:58`). An existing phone/email is rejected `user_exists` (`:46-47`), so **a doctor who already has an account cannot be added this way**. Roles allowed: doctor, lab, radiology, nurse, pharmacy (`:19`). The provider-app sends a client-generated temporary password (`provider-app/src/screens/facility/facility/AddSubAccountScreen.tsx:85-93`).
  2. **Hospital module `addStaff`** (`backend/src/modules/hospital/services/hospital.service.ts:153-234`): facility chooses email + password (`:174-179,189-192`); clinical roles also get a raw `provider_accounts` row with `facility_id` (`:197-204`) and a `provider_profiles` row with `parent_facility_id`/`staff_role` (`:205-217`); reception/insurance roles get **no app login**, only a staff record (`:158,167-169`).
  3. **Branch staff** (`providers.service.ts:90-130`): hospital/branch admin creates a DOCTOR or RECEPTIONIST user with a typed or auto-generated password, `parent_provider_account_id` from the admin (`:100`); a doctor is created **already ACTIVE with `license_verified:true`, bypassing the admin verification queue** (`:107-120`); the id is pushed into `branch.doctors_roster` (`:123`).
- **Invitation link / OTP:** only `provider/operators` uses an invite (email link, 72 h token, invitee sets own password) (`provider-operators.service.ts:27-40,42-57`). It produces a `provider_operators` record with its own `password_hash` (`:49`), not a `users` account; no login path for operators was found (grep of `OperatorStatus.ACTIVE`/operator login in `src` hits only the service and schema). Labs read operators as technicians (`backend/src/modules/labs/labs.service.ts:585-608`). No phone/OTP step exists for any of these flows.
- **Invitation to an existing practitioner:** `facility_invitations` (`hospital.service.ts:60-83`, `hospital-invitation.schema.ts:13-31`). The invitee must **already be a registered user** (`provider_not_found`, `hospital.service.ts:66`); one pending invitation per facility+invitee (`:74-75`); permission keys limited to pricing, schedule, insurance, vacation, availability, online_consultation, home_visit, catalog, read_stats, manage_wallet (`:19-22`). Accept (`:99-118`) writes `users.parent_provider_account_id` and permissions (`:109-112`) and `provider_accounts.facility_id` (`:114-115`). Provider-app screens: send (`provider-app/src/screens/facility/FacilityInvitationScreen.tsx:53`), inbox/respond (`provider-app/src/screens/doctor/FacilityInvitationsScreen.tsx:35,57`). The schema's `cancelled` status (`hospital-invitation.schema.ts:31`) has no route that sets it.
- **Can one doctor belong to two facilities?** No. Membership is a single scalar: `users.parent_provider_account_id`, `provider_accounts.facility_id` (overwritten by a second accept, `hospital.service.ts:109-115`), `affiliated_hospital_id` (`:270-283`). Facility lookups read the scalar (`provider-production.module.ts:525-528`, `facility-ops.module.ts:233-240`, `provider-facility.controller.ts:8-12`).
- **Can an independent doctor register alone?** Yes: self-registration for type `doctor` (`providers.service.ts:139-170`), pending admin approval. An independent doctor can later accept an invitation (above); `leaveFacility` returns them (`hospital.service.ts:121-131`).

## 3. Permissions inside a facility and disabling a member

- Facility endpoints require HOSPITAL/HOSPITAL_ADMIN/ADMIN (`hospital-staff.module.ts:116-118`); `getOwnerAccount` lets only `UserRole.HOSPITAL` or ADMIN resolve the owner account (`:29-30`). The hospital module splits readers (hospital, hospital_admin, branch_admin, receptionist, finance, admin, super_admin) from writers (hospital, hospital_admin, branch_admin, admin, super_admin) (`hospital.service.ts:36-43`); receptionist cannot read the wallet (`:312-314`).
- Fine-grained model exists only for operators: roles owner, admin, pharmacist, doctor, lab_technician, radiology_technician, nurse, cashier, insurance_officer, dispatcher, customer_support, with a permission enum and defaults per role (`backend/src/modules/provider/provider.enums.ts:53-90`). Invitees' permissions in facility invitations use a different, ten-key list (`hospital.service.ts:19-22`). The two vocabularies are not connected.
- There is **no "manager / receptionist / doctor / pharmacist" model in one place**; roles are spread across `UserRole`, `HospitalStaff.staff_role`, `OperatorRole` and the invitation permission keys.
- **Disabling a member today:**
  - `hospital-staff` suspend sets `users.suspended` (`hospital-staff.module.ts:91`), a **global user flag**, not a membership flag. `remove` **hard-deletes** the user (`:100`).
  - hospital module `removeStaff` sets staff `is_active=false`, `users.active=false`, `provider_accounts.status='suspended'` (`hospital.service.ts:257-268`) — disables the practitioner's whole account, not just the membership.
  - Operators: `disable`/`enable`/`revoke` change only the operator status and are audited (`provider-operators.service.ts:72-96`; OWNER cannot be changed `:63,76,94`).
  - Leave by the member: `leaveFacility` (`hospital.service.ts:121-131`). A manager has no endpoint that removes only the link while keeping the practitioner's account.
- Provider-app list shows `suspended` as inactive and deletes through `DELETE hospital/staff/:id` (`provider-app/src/screens/facility/facility/SubAccountsScreen.tsx:70,76,94`).
- Audit: operators write `provider_audit_logs` (`provider-operators.service.ts:39,56,69,79`); `hospital-staff` and `hospital.service` do not use `recordAudit` for membership changes (not found in the files read); the facility screen reads `facility_audit_logs` (`provider-facility.controller.ts:29-39`).

## 4. Money and attribution

- Earnings are credited on `service.completed` by `creditCompletedService` (`backend/src/modules/provider-ops/provider-ops.module.ts:55-96`). For consultations the provider field is `doctor_user_id` (`:59`); the credit goes to the **doctor's own provider account** (`:86-92`, `creditEarning` `:640-665`). Lab/radiology/nursing use `lab_id`/`facility_id`/`provider_account_id` etc. (`:60-62`), so those units pay to the account named on the booking.
- **No facility share is computed.** `creditEarning` applies the platform commission and VAT only (`:643-650`); no facility cut, no sub-ledger per membership.
- Withdrawals are per account: balance is summed by `provider_account_id` (`backend/src/modules/payouts/provider-payouts.controller.ts:36-52`), bank account is `provider_bank_accounts.account_id = user.id` and must be approved (`:69-71`), request stored with `provider_id: user.id` (`:92`). So a doctor inside a facility withdraws to **their own** IBAN; a facility user withdraws only what is credited to the facility account.
- Facility "wallet" is a revenue total over completed appointments of doctors with `affiliated_hospital_id` — a sum of `total_price`, not a ledger and not a payable balance (`hospital.service.ts:312-322`).
- Attribution of a booking to a doctor inside a facility: appointments carry `doctor_user_id`, `doctor_id` (profile id), `provider_id`, and optionally `facility_id`; facility views match any of them (`provider-facility.controller.ts:47-51,66-69`). Instant consultations set `doctor_user_id` and `provider_id` to the accepting doctor with no facility (`backend/src/modules/instant-consultation/instant-consultation.service.ts:222-238`). Facility id is therefore not stamped at booking time; facility reports infer it from staff lists.
- Admin: `admin/providers` approve/reject/approve-bank are gated by `facility.edit` (`provider.controllers.ts:160-175`); the admin UI shows one `facility_license_number` per profile (`admin/src/components/ProviderFullDetail.tsx:267`) and has no screen for memberships, rosters or facility staff (grep in `admin/src` for staff/operators/invitations found nothing).

## 5. Gap table against the target model

| # | Target | Today | Evidence | Gap |
|---|---|---|---|---|
| 1 | Facility account with owner/manager, CR + facility licence | Provider profile with role `HOSPITAL`; clinic and hospital share the role; CR/licence fields exist on the same profile | `providers.service.ts:443-452`, `provider-profile.schema.ts:41-47` | No distinct facility entity; no facility type for medical complex; licence verification not tied to facility |
| 2 | Units (specialty clinics, pharmacy, lab, radiology, home nursing) under the facility | Roster arrays on one profile; branches/departments | `provider-profile.schema.ts:173-196,256`, `hospital.controller.ts:13-31` | Units are not entities (no own licence, catalogue, wallet, staff) |
| 3 | Practitioner has own account + licence | Yes for independent registration; facility-created staff get accounts but facility-chosen passwords | `providers.service.ts:139-170`, `hospital-staff.module.ts:43-58` | Facility-created accounts are not the practitioner's identity; branch doctors skip verification |
| 4 | Join by invitation (phone/email), practitioner sets own password with OTP | Invitation exists but invitee must already be registered; operator invite uses email link, no OTP; owner-set passwords elsewhere | `hospital.service.ts:60-83`, `provider-operators.service.ts:27-57` | No invite-to-unregistered flow with OTP; three flows hand out passwords |
| 5 | Several facilities or independent | Single scalar facility field, overwritten on accept; hard "user_exists" block on staff create | `hospital.service.ts:109-115`, `hospital-staff.module.ts:46-47` | Needs a membership collection (practitioner × facility × role × status) |
| 6 | Roles per facility (manager, receptionist, doctor, pharmacist…) | Roles in `UserRole`, `staff_role`, `OperatorRole`, invitation permission keys | `enums.ts:1`, `provider.enums.ts:53-90`, `hospital.service.ts:19-22` | Four vocabularies; role is global to the user, not per facility |
| 7 | Manager deactivates a membership only | Suspends or deletes the user, or suspends the provider account | `hospital-staff.module.ts:91,100`, `hospital.service.ts:257-268` | No membership-level deactivation; hard delete destroys the practitioner's account |
| 8 | Payout to facility or independent provider | Always to the practitioner's own account; facility has no split | `provider-ops.module.ts:86-92,640-665`, `provider-payouts.controller.ts:36-71` | No facility payout rule, split or per-booking destination; facility wallet is a revenue sum |
| 9 | Booking attributed to practitioner and facility | `doctor_user_id`/`doctor_id`/`provider_id`, optional `facility_id` | `provider-facility.controller.ts:47-51`, `instant-consultation.service.ts:222-238` | Facility not stamped at creation; reports rely on staff-list matching |
| 10 | Audit of membership changes | Operators audited; staff create/remove not found using `recordAudit` | `provider-operators.service.ts:39-79` | Membership changes need chained audit |
| 11 | Admin visibility | Provider approval only; one licence field shown | `provider.controllers.ts:160-175`, `ProviderFullDetail.tsx:267` | No admin screen for facility members, invitations or disabled memberships |
