# DATA_MAP — where Nabd Plus data and files live

Status: first version, written by the review session for owner decision 32 (`docs/product/OWNER_DECISIONS_2026-10-06.md` §32) and decision 22 (PDPL).
Base: `origin/main` @ `d956ea82` (2026-10-08). Read-only research; nothing in the code was changed.
All paths below are relative to `backend/src/` unless they start with `provider-app/`, `patient-app/` or `admin/`.

Target rule used for §3 (owner, newer than the wording of decision 32):
- medicine images on Cloudflare R2 only;
- every provider image or file on Cloudinary;
- private provider files (licences, KYC, contracts, documents) on Cloudinary with delivery type `authenticated`;
- no file kept inline as base64 in MongoDB.


## Summary (read this first)

- **All records** are in MongoDB on the server. The table in §1 lists every collection the backend uses, with its personal [PII], medical [MED], money [PAY] and file [FILE] fields. The "who writes" and "who reads" columns are folder-level guesses, not per-route proofs (§0).
- **Files today:** almost everything uploaded goes to Cloudflare R2, including provider licences and KYC documents, provider logos and galleries, patient prescription photos, chat files and reports. Only processed doctor and nurse profile photos reach Cloudinary. Medical and provider documents are also kept as **base64 inside MongoDB** in 16 places (§3 D).
- **Target rule (owner, newer than the decision 32 wording):** medicine images on R2 only; every provider image or file on Cloudinary; private provider files (licences, KYC, contracts, documents) on Cloudinary with type `authenticated`. §3 lists every place that breaks it, with file:line.
- **Account deletion:** three paths that disagree (§4). The patient's own `DELETE /users/me` **hard-deletes medical records** (prescriptions, lab results, medical reports, bookings) and misses most of its own list because 21 of its 37 collection names do not exist (for example `patientprofiles` instead of `patient_profiles`). Payment records are kept on every path, but `invoices` and `orders` are never anonymised. The owner's rule (anonymise the person, keep invoices and medical records) is the subject of the reviewer's storage/erasure acceptance spec.
- **Retention:** no retention period exists in code except the `slotlocks` TTL and the 30-day hard delete of an erased `users` row (decision 22 is not implemented).

## 0. How this map was built (and its limits)

- **Schema collections**: every `@Schema(...)` class under `schemas/` and `modules/**` (231 classes). When the decorator has `collection: '<name>'`, that name is used. When it has none, the Mongoose default (lower-case plural of the model name) is shown and marked **(derived name)**; the derived name is correct only if the model is registered under its class name — unknown otherwise.
- **Raw collections**: every literal `conn.collection('<name>')` / `db.collection('<name>')` (189 names; 110 of them have no schema at all — marked **raw only**). Indirect uses (`collection(CATALOG_COLLECTIONS.x)`, `collection(spec.collection)`, `collection(k.collection)` etc., ~120 call sites) were not resolved one by one.
- **Key fields** are taken from the schema `@Prop`s and tagged by name: `[PII]` personal, `[MED]` medical, `[PAY]` money, `[FILE]` file/image reference. Tagging is by field name, so catalogue collections (e.g. `medicines`) get `[MED]` on non-personal clinical text — read `[MED]` as "personal medical" only on patient-owned collections. Raw-only collections show "unknown (raw collection, no schema)".
- **Who writes** = non-schema source files that reference the model/collection and call a write method (`create/insertOne/updateOne/save/...`). First 4 are listed, `+N` = more.
- **Who reads** = role guards found on the controllers in the same folders as the referencing files (`@Public()` → public, `UserRole.ADMIN` → admin, provider roles → provider, `JwtAuthGuard`/`UserRole.PATIENT`/`@CurrentUser` → `patient-own?`). This is a folder-level heuristic, **not** a per-route proof. "none found" means no controller in those folders.
- **Retention** = TTL indexes (`expireAfterSeconds` / `expires:`), soft-delete writes (`is_deleted: true`, `deleted_at`, `deleted: true`), and the three account-deletion paths in §4. Only one TTL index exists in the whole backend: `slotlocks.expires_at` (`schemas/slot-lock.schema.ts:16`). No `archive_*` collections or archive jobs were found (`grep archive_` only hits legal-acceptance archive ids, `modules/legal/legal-enterprise.service.ts:47`).

Collections named in decision 32 and where they are in the table: `medicines`, `provider_accounts`, `provider_profiles`, `provider_settings` (raw only), `provider_contracts` (raw only), `provideravailability` (raw only, 1 use) **and** `provider_availability` (schema `modules/provider/schemas/requests.schema.ts:147`) **and** `provideravailabilities` (derived, `schemas/provider-availability.schema.ts:5`) — three spellings exist, `provider_schedule_slots`, `facilities`, `insurance_networks`, `insuranceservicerequests`, bookings (`appointments`, `labbookings`, `radiologybookings`, `homecarebookings`, `doctor_appointments`, `surgery_bookings`), orders (`pharmacy_orders`, `orders`), payments (`moyasar_payments`, `transactions`, `wallet_transactions`, `platformledgerentries`, `pharmacy_payment_evidence`, `providerwithdrawals`, `einvoices`).

Duplicate schemas for the same collection (two or more classes write the same collection, fields can disagree): `appointments` (3: `schemas/appointment.schema.ts:42`, `:52`, `schemas/extra.schemas.ts:42`), `labbookings`, `radiologybookings`, `homecarebookings`, `medicalsupplyrequests`, `provider_profiles`, `provider_deltas`, `providerdeltas`, `pharmacy_inventory`, `pharmacy_chat_threads`, `procurementrequests`, `pushtokens`, `refundrequests`, `auditlogs`. Near-duplicate names that are different collections: `return_requests` vs `returnrequests`, `feature_flags` vs `featureflags`, `fraud_alerts` vs `fraudalerts`, `refund_requests` vs `refundrequests`, `system_events` vs `systemevents`, `system_config` vs `system_configs`, `chat_sessions` vs `chatsessions` (PDPL list), `emergency_requests` vs `emergencyrequests` (PDPL list).

Schemas with no runtime reference found (embedded sub-documents or unused): `ai_interactions`, `candidateexperiences`, `checkups`, `contractionlogs`, `encounterrecords`, `health_records`, `homecarenurses`, `homecarepackages`, `infantgrowthlogs`, `insurancedetailses`, `insurancenetworkcontracts`, `kicklogs`, `locationcoordinateses`, `locationcoverages`, `medication_doses`, `medication_plans`, `orderitems`, `orderresults`, `patient_crm_tags`, `pharmacy_prescription_intakes`, `pharmacy_substitute_map`, `prescriptionitems`, `statetransitions`.

## 4. Account deletion — what the code does today

There are **three** separate deletion paths and they do not agree.

### 4.1 Patient self-erasure — `DELETE /users/me` (`modules/users/users.controller.ts:109-113` → `modules/users/pdpl.service.ts:148-254`)
- Requires a password; accounts without one (social sign-in) are refused (`pdpl.service.ts:162-178`).
- Iterates the `OWNED` list (`pdpl.service.ts:38-76`), skipping names that do not exist in the database (`:182`, `:193`).
- **Anonymised (row kept, `patient_name='deleted'`, phone/email null, `patient_id`/`user_id` unset)** (`:195-201`): only `transactions`, `refund_requests`, `return_requests`, `pharmacy_orders` — the `ANONYMISE` set also names `invoices`, `billing`, `claimssubmissions`, `auditlogs`, `orders` (`:187-190`) but these are not in `OWNED`, so they are never touched. Note: `pharmacy_orders` is matched on `patient_account_id`, but the anonymise step unsets only `patient_id`/`user_id`, so `patient_account_id` and `delivery_address` stay (`:197-198`).
- **Hard-deleted** (`:203-204`): `appointments`, `labbookings`, `radiologybookings`, `homecarebookings`, `prescriptions`, `labresults`, `medicalprofiles`, `medicalreports`, `notifications`, `pushtokens`, `reviews`, and every other existing name in `OWNED`. **Medical records are deleted, not kept**, and the booking rows that carry prices/fees (`appointments.total_price`, `labbookings.total` etc.) are deleted too.
- Names in `OWNED` that match no collection used by the code (so nothing happens): `patientprofiles` (real: `patient_profiles`), `nursingbookings`, `healthpassports`, `healthrecords` (real: `health_records`, unused), `vitals` (real: `vitalreadings`), `allergies`, `medications`, `insurancepolicies`, `insurance_requests`, `claims` (real: `insurance_claims`), `loyalty`, `loyaltytransactions` (real: `loyalty_accounts`, `loyalty_transactions`), `wishlists`, `addresses`, `chatsessions` (real: `chat_sessions`), `chatmessages` (real chat collection is `chat_messages`; `chatmessages` would only exist through the unregistered `schemas/pharmacy-chat.schema.ts:5` class), `supporttickets`, `supportmessages` (real: `supportrequests`), `emergencyrequests` (real: `emergency_requests`), `consentrecords`, `devices`, `refreshsessions`.
- **Not touched at all** (patient data that survives erasure), among others: `patient_profiles` (name, phone, email, DOB, national id, allergies…), `moyasar_payments`, `wallets`, `wallet_transactions`, `platformledgerentries`, `einvoices`, `orders`, `doctor_appointments`, `chat_messages`/`chat_threads` (real chat collections), `media_assets` + their R2 objects, `storage_objects`, `booking_attachments`, `supportrequests`, `customservicerequests`, `family_groups`, `nutrition_*`, `mood_entries`, `maternityprofiles`, `medicationreminders`, `insurance_claims`, `gdpr_exports`, `analytics_events`, `ai_triage_sessions`. No file in R2 or Cloudinary is deleted on this path.
- The `users` row is anonymised in place (`full_name='Deleted User'`, email/phone/password/national_id/MRN unset, `deleted_at` set) (`:220-238`), then `DataRetentionService` hard-deletes users with `deleted_at` older than `DATA_RETENTION_DAYS` (default 30) daily at 03:00 (`modules/users/data-retention.service.ts:19-35`). That job deletes only the `users` row, nothing else.

### 4.2 Admin hard delete — `DELETE /admin/users/:userId` (step-up; `modules/admin/admin.controller.ts:516-568`)
- Emits `storage.delete_by_url` for the provider's `profile_photo`, `logo`, `clinic_images` and every `storage_objects.external_url` owned by the user (`:528-543`) → R2/Cloudinary objects deleted (best effort). `media_assets` objects are not included.
- `deleteMany` on: `patients`, `provider_profiles`, `carts`, `pushtokens`, `notifications`, `notificationpreferences`, `wallets`, `familymembers`, `healthmedications`, `wearabledevices`, `medicationreminders`, `provider_contracts`, `storage_objects` (`:545-563`). `patients`, `notificationpreferences`, `familymembers` match no collection used by the code.
- Hard-deletes the `users` row (`:565`). Orders, appointments and ledgers are kept on purpose ("kept for audit integrity", comment `:543-544`) with the patient's identifiers still in them. `provider_accounts`, `provider_documents` and `provider_settings` are not touched.

### 4.3 Admin GDPR erasure — `POST /admin/gdpr/:id/delete/complete` (`modules/admin/enterprise/admin-crm.controller.ts:243-273`)
- Overwrites `users.full_name/phone/email` with an `anon` marker and clears password/OTP (`:256-261`); the row is not deleted and `deleted_at` is not set, so the retention job never removes it.
- Sets `patient_name`/`patient_phone` to the marker in `pharmacy_orders`, `orders`, `labbookings`, `radiologybookings`, `homecarebookings`, `appointments` where `patient_id` matches (`:262-267`; collections from `ORDER_KINDS`, `modules/admin/enterprise/orders-console.service.ts:35-80`). `pharmacy_orders` keys the patient by `patient_account_id`, so its rows are not matched. Medical records and payments are kept.

### 4.4 Are invoices/payments and medical records kept?
- **Payments / invoices**: kept on all paths. `moyasar_payments`, `einvoices`, `wallet_transactions`, `platformledgerentries`, `pharmacy_payment_evidence` are never touched (still linked to the patient id). `transactions` is anonymised on self-erasure only. But the price/fee fields on `appointments`/`labbookings`/`radiologybookings`/`homecarebookings` are lost when PDPL self-erasure deletes those rows.
- **Medical records**: deleted on self-erasure (`prescriptions`, `labresults`, `medicalreports`, `medicalprofiles`, bookings); kept on both admin paths. No retention period for medical records exists in the code (no TTL, no archive).
- `wallets` is deleted by the admin hard delete (`admin.controller.ts:552`) even though it holds a money balance.
