# Runtime check, Batch 1 (patient-web)

**Test data.** The four routes with an order id in the query are served by a TEST stand-in kept outside the repo (the local test backend cannot select an offer, accept a quote or reach a payment provider: no gateway key, no Mongo replica set); its payloads copy `governedView`, `getPharmacyCapabilities`, `createPaymentIntent` and `verifyPayment` field for field. The routes without an id are the real backend. Interaction checks (single-flight, idempotency keys, error sentences, result states) ran against the same production build with the stand-in: 107 assertions, one expectation of the script itself was wrong (a streamed 404 reports status 200; the page body is the not-found page).

Generated by `node tools/design/runtime-check.mjs` against http://localhost:3140 (locale `ar`, 390 px) talking to a seeded backend.
Scenarios: **normal** = real responses; **empty** = every data GET answered `200 []`; **error** = every data GET answered `500`. Injected by `tools/design/fault-proxy.mjs` between patient-web and the backend, so server-rendered fetches are covered too.
Server-rendered fetches are not visible to the browser, so for the normal scenario the backend's HTTP log is read as well (listed as "Server" below).
