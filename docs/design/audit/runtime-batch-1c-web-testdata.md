# Runtime check, Batch 1c (patient-web): TEST DATA

**Test data.** The local test backend cannot produce pharmacy offers (see `needs-review/batch-1c-web.json`), so these 21 runs go through a stand-in kept OUTSIDE the repo that answers the order, offers, chat and payment-capability reads of seven TEST orders with payloads copied field for field from `backend/src/modules/pharmacy` (`patientDtoAsync`, `governedView`, the chat service). Everything it returns is marked TEST. Normal, empty (`[]`) and error (500) are all injected at that layer. "Server (backend log)" is empty for these runs because the stand-in, not the backend, answered. Interaction checks (select with a slow answer and two clicks = one POST, idempotency key reuse after 503, every error sentence, accept with the server hash and revision, COD, insurance, cancel confirm, message escape, 403 shown as 403) are in the slice report: 40 checks, all passed on the final build.

Generated by `node tools/design/runtime-check.mjs` against http://localhost:3130 (locale `ar`, 390 px) talking to a seeded backend.
Scenarios: **normal** = real responses; **empty** = every data GET answered `200 []`; **error** = every data GET answered `500`. Injected by `tools/design/fault-proxy.mjs` between patient-web and the backend, so server-rendered fetches are covered too.
Server-rendered fetches are not visible to the browser, so for the normal scenario the backend's HTTP log is read as well (listed as "Server" below).
