# Runtime check, Batch 1c (patient-web): REAL order, real seeded backend

Slice 1c, production build of `wip-b1c-web` on port 3130, backend `http://localhost:3002` (NODE_ENV=test) through the fault proxy. The order is one created by the seeded patient through `POST /patient/pharmacy/orders` (id `761e9693-…`, status `ready_for_split`; its `submit` answered 500 because the local mongod has no replica set), so every read here is a **real** answer: the offers list is `[]`, there are no negotiation threads, the order has no selection. A second run with TEST stand-in data (offers, selected, accepted, insurance, negotiation) is in `runtime-batch-1c-web-testdata.md` (21 runs, 0 issues).

Two "FAIL" cells are not defects of the screens: (1) `/orders/<id>/offers/negotiation/00000000-…` asks for a thread that does not exist: the page is the not-found page and the backend's 404 is the expected answer; (2) `GET /api/v1/prescriptions/0f0f0f0f-…` -> 404 on the offers route is another slice's traffic in the shared backend log (this page makes no such call; the tool attributes every log line of the time window to the page). The earlier run of this file reported a CSP `script-src` violation for the zod chunk on every route of this slice; the schema library is no longer in these client bundles (commit "no schema library in the client bundle") and the violation is gone.

Not exercised against the real backend (it cannot produce them here): a populated offers list, selecting an offer, accepting the final price, cash on delivery, insurance acceptance, payment intents, negotiation messages.

Generated by `node tools/design/runtime-check.mjs` against http://localhost:3130 (locale `ar`, 390 px) talking to a seeded backend.
Scenarios: **normal** = real responses; **empty** = every data GET answered `200 []`; **error** = every data GET answered `500`. Injected by `tools/design/fault-proxy.mjs` between patient-web and the backend, so server-rendered fetches are covered too.
Server-rendered fetches are not visible to the browser, so for the normal scenario the backend's HTTP log is read as well (listed as "Server" below).
