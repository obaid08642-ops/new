# Quality standards (owner, 2026-10-05)

Every screen PR must pass these, with the **measured numbers** in the checklist in the PR description (template at the end). "Automated" means CI fails on it today; "measured" means the PR author runs the tool and pastes the number until CI covers it.

## 0. Identity (fixed)
Canvas `#F5F5F7` (plain, no patterns or decorative shapes), action `#D42A38`, brand coral `#FF4B55`, ink `#0B1B2B`, the Noon Dot logo (`canvas/Main.dc.html`), Readex Pro, and the boards' icons, buttons and cards. **Never** introduce a colour, logo variant, background pattern or shape that is not on a board; if something is missing, ask the owner first. Every PR description says **"Identity check: no new colours/logo/patterns"** and includes the token diff (`git diff origin/main -- packages/design-tokens/tokens.json`, or "no token change").

## 1. Images and assets
| Rule | How it is checked |
|---|---|
| Photos and illustrations ship as WebP (AVIF on web); PNG only for app icons, splash and store assets | review |
| No raster over 200 KB in the apps or `patient-web/public` | **automated**: `tools/design/no-large-raster.ts` (CI step "No raster asset over 200 KB"; also in `npm test` of design-tokens) |
| Unused assets and fonts are removed (target: `patient-app/assets/fonts/MaterialSymbolsRounded.ttf`, 1.7 MB, used by 28 files today, goes when the last screen moves to the shared icons) | review |
| Remote images go through the CDN at the displayed size, lazy-loaded, with a placeholder and a fixed aspect ratio | review; layout shift is measured (CLS) |

## 2. Performance budgets
Web (mobile, 4G), per route, **automated** by `lighthouse.yml` (`patient-web/.lighthouserc.json` and `.github/lighthouse-budget.json`):
- LCP < 2.5 s, CLS < 0.1, TBT ≤ 200 ms (the lab stand-in for INP < 200 ms; INP itself is **measured** in the field), Lighthouse Performance ≥ 90.
- First-load JS per route ≤ 170 KB gzip (the `script` budget), fonts subset and self-hosted. Measure on a production build (`next build`, standalone server) with `node tools/design/js-size.mjs` and Lighthouse (median of 3); `next experimental-analyze -o` shows which module a chunk's bytes are. Rules that keep it down: client components import component modules directly (no barrel), icons and illustrations are per-glyph or loaded on demand, no library for something the design system already draws, nothing on the always-loaded path (layout, error boundary) imports the component set.

App (**measured** per release, pasted in the PR): cold start < 2 s on a mid-range Android; lists virtualised (FlashList / FlatList); Hermes on; animations on the UI thread at 60 fps; images cached with `expo-image`; the app download size per release.

Data: API responses cached (stale-while-revalidate), long lists paginated, no re-fetch on every render.

## 3. Accessibility
axe / Lighthouse Accessibility ≥ 95 on web (**automated**, same Lighthouse job), a screen-reader label on every control, 44 px targets (DEVICE_STANDARD §3), dynamic type to 200%.

## 4. Security and privacy
Keep the CSP and the security headers (components never set a `style` attribute: `tests/design-system-components.test.tsx`, CSP block), no tokens in localStorage, no secrets in client code, no medical data in logs or analytics.

## 5. SEO (public web pages)
Title and description per locale, hreflang for the 6 languages, canonical URLs, JSON-LD (Product/Drug, Physician, MedicalOrganization), sitemap and robots, SSR.

## 6. Reliability
No new Sentry errors; loading, empty, error and offline states on every screen; no console errors (the DOM/console check used for Batch 0: `scripts` in the PR).

## 7. Per-batch audit (owner, 2026-10-05: inside every batch PR, never a separate pass)
1. **Element audit.** For every button, field, icon, link, list and number on each screen of the slice: its source (API field / user input / static copy) and status. Written as a compact `docs/design/audit/<slice>.json` and rendered by `node tools/design/audit-table.mjs <file>` into a short table per route (route, element, source, status); notes only for problems, one line each (owner, 2026-10-06).
2. **Mock / placeholder section.** `WIRING_REPORT.md` section "Mock / placeholder found" (generated by `tools/design/mock-scan.mjs`): hard-coded data, fake numbers, `Math.random`, sample arrays, TODO/dummy text, dead buttons (no handler, `href="#"`), each with file:line. Zero hits in the batch's own screens at merge.
3. **Runtime check (once per slice, at the end, on one production build).** Every screen opened against the seeded backend (dev/staging): each request 2xx with real data; empty and error states render when data is missing. Web: `node tools/design/runtime-check.mjs --batch <n>` writes `docs/design/audit/runtime-batch-<n>-web.md`; app: the endpoints each screen calls are exercised with the seeded patient token and listed in `docs/design/audit/batch-<n>-app.md` (mutations are listed, not executed).
4. **No unresolved calls.** `WIRING_REPORT.md` reports 0 unresolved calls built from variables (`inventory/manual-calls.json` for the rare manual resolution), and every web screen with no API call is classified in `inventory/static-screens.json`.
5. **Needs review.** Anything whose target cannot be traced, any call suspected wrong, anything unsure: `docs/design/needs-review/*.json` (screen, element, **exact file and line of the element in the client (required from Batch 2 on, enforced by `audit-table.mjs`)**, found with its `[client]`/`[backend]`/`[owner]` tag, suspected), rendered into `WIRING_REPORT.md`. Backend gaps are reported there, not fixed by the design session; the reviewer session verifies and fixes them.
6. **Colours, strictly.** Only `@nabd/design-tokens`: the base palette (canvas, cards, text, secondary text, action red, brand coral, with their dark versions) and the 10 service tones. No other colour on any button, text, icon, border, chart or background. Every screen the PR touches ends with zero raw colours; any legacy colour found (brown, stray turquoise, old blue...) is replaced with the nearest token, never kept and never added as a token without the owner's approval. The `client-token-sync` baseline is lowered in every PR and **the new number is stated in the PR description**; it never goes up. A token change changes app and web together, with no screen-level override.

## 8. Translation, strictly (owner, 2026-10-06: same strictness as colours)
1. **No user-visible text in code.** Every button label, field label, placeholder, error, toast, empty state, `accessibilityLabel` / `aria-label`, `alt`, page title and meta tag comes from the translation files: `patient-web/messages/*.json`, `patient-app/src/i18n/locales/*.json`. A screen or component never holds a sentence of its own. A line that cannot be translated (a brand name, a code) carries `// i18n-ok: <reason>`.
2. **Gates (CI, both only go down).** `tools/design/no-literal-ui-string.mjs` fails on hard-coded text in JSX/TSX of the app and the web, against `no-literal-ui-string.baseline.json` (`--update` lowers it and refuses to raise it; `--changed <ref>` fails on literals in the files a branch touched). `tools/design/locale-parity.mjs` fails when a key is missing or empty in any of the six locales (ar, en, ur, hi, bn, fil; the app's file is `tl`) or when English text is left inside a non-English file (brand names and units excepted); `--base origin/main` also requires every key the branch adds to be complete and translated. `i18n-coverage.mjs` keeps the web files key-for-key identical.
3. **Every new key arrives with all six translations in the same PR.** No fallback to Arabic or English in the UI: a missing key is a failed gate, not a screen in the wrong language.
4. **Layout survives every language.** RTL for ar and ur, LTR for en, hi, bn, fil. Buttons grow with the text (min-width and padding, never a fixed width that cuts a long Hindi, Bengali or Filipino label; no `numberOfLines={1}` on a label without a measured reason). Numbers, dates, times and currency go through the locale formatter (`Intl` / next-intl formatters), never a hand-built string. Directional icons (arrows, chevrons, back, send) mirror in RTL; logos, play, check, clock and media do not.
5. **Languages are checked, not photographed.** No screenshots are committed or sent (owner, 2026-10-06). While building, check each screen in ar, en and ur (or hi) at 390 with a temporary render and delete it; the long-LTR and second-RTL layouts must hold, and a test or the DOM check covers overflow.
6. **Report the number.** Every PR states the literal-string baseline (old → new) and the locale-parity totals, as with `client-token-sync`. The screens a PR rebuilds end with zero literals and zero parity problems in their own keys.
