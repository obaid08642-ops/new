# Capacity report, 2026-10-16 (P14.27, extends 14.2)

**What was measured:** the API under the real traffic mix of `SCALE_ARCHITECTURE.md` §5, on a local test stack with
production-sized **test data**. **What was not:** staging or production (there is no staging host; see "Blocked").
Every number here is this machine's, so read them as a baseline to compare the next scale steps against, not as
production's ceiling. The production backend runs the same way as here, as **one Node process**
(`CLUSTER_MODE: "false"` in `deploy/docker-compose.production.yml`), so the shape of the result (what saturates first) carries over.

## Set-up
- **Machine:** one container, 4 vCPU (Intel Xeon @ 2.10 GHz), 15 GB RAM, holding everything: the backend (main
  `79c82876`, built, one process, Node 22), MongoDB 8.2 (single-node replica set), Redis 7, the test doubles
  (S3, SMTP sink, Moyasar), LiveKit 1.10.1, and k6 1.3.0 itself.
- **Data (test data, `tools/perf/k6/seed-perf-data.js`):** 21,000 public catalogue rows translated into the six site
  languages (the size of production's catalogue on 2026-10-15) and 20,000 patient accounts for the fan-out.
- **Fixtures (`tools/perf/k6/fixtures.py`, through the real API with the live-journey helpers):** an approved doctor
  with video hours tomorrow, 10 patients, a paid booking (card, fake gateway) with its chat thread, and a started
  video visit with a call session.
- **Mix per virtual user and iteration (`tools/perf/k6/capacity.js`):** catalogue list, product search, site search,
  autocomplete, one product, the doctors list and one doctor (always); logged-in reads 50%; add to cart 15%; chat
  send + read 10%; booking (slot list + slot hold) 5%; payment webhook (the gateway re-sending a paid event) 3%;
  call join 2%; then 1–3 s of think time.
- **Method (`tools/perf/k6/ladder.sh`):** a constant load per step, 60 s each, the CPU of the backend and Mongo
  sampled every 2 s from `/proc`; `summarize.py` writes the tables. Targets are §5's: public p95 < 300 ms,
  logged-in < 500 ms, checkout/booking < 800 ms, errors < 0.5%.

## First bottleneck: catalogue queries read every row
Mongo uses about two of the four cores at 20 VUs while the backend uses less than one. The Mongo profiler (slow ops
over 20 ms during a 30 s run at 20 VUs) puts all of the top time on the `medicines` collection:

| Request | What Mongo does | Evidence |
|---|---|---|
| catalogue list (`GET /public/products/search` with no term) | the filter uses the `public_eligibility` index, then reads and sorts all 21,000 rows by `usage_count` in memory; **and** counts all 21,000 for `total` on every call | 64 finds: 4.3 s, docsExamined 21,000 each; 64 counts: 2.8 s |
| product search with a term | the same read of all 21,000 rows, then the regex on names and translations | ≈ 1–2 s per group of 4–5 calls, docsExamined 21,000 |
| site search (`GET /search`) | `search_index` scanned by `type` | 42 getMores: 1.35 s |

**Proof that it is the first bottleneck:** with the four `medicines` indexes that `backend/scripts/add-performance-indexes.js`
already defines (`perf_usage_count`, `perf_review_status`, `perf_catalog_category`, `perf_search_text`) created on the
test database, the same ladder gives:

| VUs | req/s | public reads p95 | errors | backend CPU avg % | Mongo CPU avg % | all targets met |
|---|---|---|---|---|---|---|
| 10 | 34 | 127 (was 264) | 0.00% | 49 | 29 (was 120) | yes |
| 20 | 61 | 258 (was 363) | 0.00% | 85 | 51 (was 199) | **yes** (was no) |
| 40 | 71 | 960 (was 1660) | 0.00% | 96 | 59 (was 210) | no (public reads, chat) |

The ceiling doubles (10 → 20 VUs) and product search drops from p95 559 ms to 85 ms at 20 VUs. The script is not
run by any deploy step, and as written it cannot run: it declares `const db = db.getSiblingDB(dbName)`, which
mongosh refuses (the name is used before it is defined), and it only knows the databases `nabd_nestjs` and `nabd_staging`.
So production most likely has none of these indexes. (Read-only check for the next ops run: `db.medicines.getIndexes()`.)

## Second bottleneck: the single backend process
With the indexes, the backend process reaches one full core (96% average, 130% peak) at 40 VUs and throughput stops
at ≈ 71 req/s. The doctors list is then the slowest request (p95 1.67 s at 40 VUs with only two doctors in the
database), so its cost is in the backend, not in Mongo. Production disabled cluster mode on 2026-10-04 after a crash,
so it has the same one-process limit on any number of cores.

## Next steps (in order; each is a separate PR for the owner/reviewer)
1. **Indexes (scale step 1, "tuned single server"):** fix `add-performance-indexes.js` (the `db` name, the database
   name from `DB_NAME`) and run it on production through ops, with a read-only `getIndexes()` before and after.
   Measured gain above: 2× the ceiling on this machine.
2. **Catalogue total:** cache the `countDocuments` of the public catalogue (it changes only when an admin publishes),
   or return `has_more` without a total for page 1; today every catalogue page pays a full count.
3. **More than one API process (step 1, then step 3 of §6):** find why cluster mode crashed on 2026-10-04, or run two
   backend containers behind nginx (14.28). On a 4-core host this is the step after the indexes.
4. **Doctors list:** profile `listDoctors` (backend CPU per call is high with two doctors; it will grow with real ones).
5. **Campaign fan-out:** the broadcast queues one job per user, one at a time, inside the HTTP request (16 s for
   20,000; ≈ 80 s for 100,000, all in one open admin request), and `resolveSegment` stops at 100,000 users without
   saying so. Queue in bulk (`addBulk`) from a background job and report the true audience size.

Re-run after each step: Actions → "Capacity (k6)" → Run workflow (the ladder, the fan-out and both tables land in the
run summary and its artifact). The GitHub runner is smaller than this machine, so compare runs with each other, not with this page.

## Not checked here
- "0 lost orders; 0 duplicate charges" under load (§5): the mix adds to the cart and replays paid webhooks (all
  answered, deduplicated) but does not place orders; the order and payment idempotency journeys (tools/live) cover
  the logic, not the load.
- Edge-cached pages (TTFB < 150 ms) and the website: this report is the API; the edge cache is 14.9.
