# Maximum throughput on the current server, 2026-10-30

**Question (owner):** keep the current server (about 4 vCPU, 3.8 GB RAM, Germany) and get the most out of it: thousands of users at once, the fastest responses.

**Rules kept:** test data only, in throwaway databases; production is never load-tested; every number below says where it was measured. Numbers marked *local sandbox* come from a 4 vCPU / 16 GB sandbox that also ran k6 and the test doubles; they are for comparing one change with the next, **not** the production host's ceiling. Numbers marked *CI, production shape* come from `.github/workflows/capacity-prod-shape.yml` (the API, MongoDB and Redis in one container with `--cpus=4 --memory=3.8g`, production-sized test data: 21,000 catalogue rows in six languages and 20,000 patient accounts).

Status of this document: **part 1** (tools, the first findings, the edge-cache pass). The CI production-shape numbers, steps 4–6 (write path, calls, rate limits and waiting room) and the projections for 8 GB and 16 GB are added as each step lands; a section that has no number yet says so.

## 2. Baseline (before any change of this pass), *local sandbox*
Mixed traffic, Express, one Node process, MongoDB 8.2 with a 1 GB WiredTiger cache, Redis, k6 on the same 4 vCPUs. 30 s per step.

| VUs | req/s | public reads p95 (target 300 ms) | logged-in p95 (500) | add to cart p95 (800) | booking p95 (800) | errors | backend CPU avg / max % |
|---|---|---|---|---|---|---|---|
| 10 | 33 | 134 | 47 | 157 | 18 | 0.00% | 50 / 82 |
| 20 | 63 | 170 | 154 | 278 | 241 | 0.00% | 66 / 113 |
| 40 | 107 | **381** | 391 | **828** | 443 | 0.00% | 90 / 122 |

Ceiling on this sandbox: **20 VUs, about 63 requests/s with every target met**; at 40 VUs the single Node process is at 90% of a core on average and public reads and the cart miss their targets.

## 3. Step 1, Fastify: not worth it on this evidence
`USE_FASTIFY=true` does not boot today: `main.ts` registers Express-only middleware after the Fastify adapter (`express.json`, `express.text`, raw-body capture for the payment webhooks, `compression`, `cookie-parser`) and the process stops at `@fastify/static` is missing. Making the whole suite and the live gate pass under Fastify means porting about 110 `res.*` calls in 19 `@Res()` files, 10 middlewares, the raw body of 27 call sites and the upload handling.

What it would buy, measured: the CPU profile of the Express process under the mixed load (*local sandbox*, steady state, 27 s busy):

| share of busy CPU | package |
|---|---|
| 31% | mongoose (documents built from query results) |
| 14% | node internals (sockets, crypto, async context) |
| 7% | bson |
| 7% | application code |
| 5.5% | garbage collection |
| 3% | ioredis |
| about 4% together | express, router, path-to-regexp, compression |

The HTTP framework Fastify would replace is about **4% of the CPU**; a faster router cannot return more than that. The weight is in MongoDB document hydration, so the work that pays is in steps 2 and 3 (serve from cache; read less and lean), and in using the other cores (`CLUSTER_WORKERS`). **Recommendation: leave Fastify opt-in, as `deploy/SCALING.md` 14.12 already says; do not spend the gate cycles on it.** If the owner wants it measured anyway, the production-shape workflow takes `container_env=USE_FASTIFY=true` the day it boots.

## 4. Step 2, anonymous GETs at the edge
`tools/perf/edge-audit.py` calls every anonymous GET route without a path parameter on a running backend and sorts the 200 answers by `Cache-Control`.

| | before | after |
|---|---|---|
| answers `public, s-maxage` (the nginx micro-cache and Cloudflare may keep them) | 17 | 28 |
| answers `private, no-store` | 63 | 52 |

Added (all `@PublicCache`, none reads the user, the 14.7 route-table gate stays green; a signed-in or cookie request still answers `private, no-store` and skips the cache both ways): `GET /public/products/search` (2 min), `GET /search` (5 min), `GET /medicines/autocomplete|categories|filters|hot` (5 min), `GET /labs/carousel` and `/radiology/carousel` (2 min), `GET /i18n` and `/i18n/all` (5 min, 36 KB and 96 KB per call), `GET /insurance/companies` (5 min, 41 KB). All are pinned in `catalogue-cache-wiring.spec.ts`.

Deliberately **not** cached, with the reason:
* `GET /care/doctors`: with `payment=insurance` it reads the signed-in patient's saved policy (`@CurrentUser`), so it cannot be shared. The default list has its own saving below; a public variant without the insurance mode would be a separate, reviewed change.
* `/config`, `/config/flags`, `/feature-flags`, `/modules`, `/system-config/public`: the kill switches and module switches must change the moment an admin changes them.
* Everything else of the remaining 52 is either small, user-aware or an operations endpoint; the list is in `edge-audit.py`'s output.

Where the edge is: the nginx micro-cache (`deploy/nginx/snippets/api-microcache.conf`, key = scheme + method + host + URI + Accept-Language, stale-if-error, lock against stampedes) is in the catch-all location, so it already applies to every route above. Cloudflare still **bypasses** the API (`CLOUDFLARE_STATE.md` A: "Bypass: API"); switching it to "respect origin Cache-Control" is the owner-approved next change there and is what moves these answers off the server entirely. The patient web's server-side calls go straight to `http://backend:8002` (`NABD_API_BASE_URL`), not through nginx, so they are only helped by the backend's own Redis cache, not by the micro-cache.

## 5. Step 3, MongoDB and the queries
* **Indexes:** with the profiler on at 20 ms during the mixed run, the only operations over 20 ms are the site-search fallback's `search_index` scans (20–60 ms; Meilisearch answers in production, this is the path used when it is down). No other query in the mix is slow, so **no new index was needed for this mix**. The catalogue lists were already covered by the `medicines` covering indexes.
* **Queries per request** (`query-count.js`, warm): catalogue list 1, product search 1, nursing list 2, the cached lists 0, **doctors list 10 for two doctors** (five per doctor for the next free time, ten doctors per page: up to 50 queries a page).
* **Fixed in this pass:** the doctors list keeps each doctor's next free time for a minute (the cache `sort=available_today` already used); a booking is still checked against the real slots when held. The site-search fallback scored every row inside the sort comparator (5 s of CPU in one profile); it scores each row once. The boot-time location seed sent about 2,000 single upserts at every start, right as traffic returns; it is a few bulk writes now.
* **WiredTiger cache:** production runs `cacheSizeGB: 0.5` (`deploy/mongo/mongod.conf`). The right size depends on the whole host's memory budget (clamd, Meilisearch, both Next.js apps, Redis 256 MB + queues, LiveKit all share the 3.8 GB), which has not been read from the server in this pass; the production-shape workflow takes `container_env=WT_CACHE_GB=1` to compare 0.5 with 1.0. Mongo used 21 to 35% of a core in the ladder: it is not what limits the API today.
* **Connection pool:** `MONGO_MAX_POOL_SIZE` 200, min 20. More than the box can use at once; 50–100 is the usual size for 4 cores. Not changed without a measured reason.
* **NABD-BACKEND-1B/1C (N+1 on `GET /public/categories/:locale/items`):** the route is Redis-cached and costs 0 Mongo operations warm; cold it is one aggregate plus one query (61 ms). No N+1 shows in the path measured here. I did not read the Sentry events themselves in this pass, so whether they are older than the covering index and the `medicines.ranked-page` work is not established.

## 6. Step 6, limits and the overload answer (first result: a negative one)
What exists: nginx `limit_req` zones per client address (`api` 500 r/s, `search` 20 r/s, `auth` 10 r/min, `checkout` 2 r/s; `deploy/nginx/nginx.conf`), the per-account/per-address `UserRateLimitGuard` buckets, and the opt-in `@ShedOnOverload()` guard (14.17) that sheds a few low-priority routes when the event loop lags. The `api` zone at 500 requests/s per address is above what the whole API can do (about 60 to 110 requests/s of mixed uncached traffic, section 2), so it cannot protect the server from one busy address; it was set high on purpose for shared mobile-carrier addresses. Sizing it needs the real distribution of requests per address from the nginx log, which I have not seen; that is the input still missing.

Experiment: a middleware that answered **anonymous GET reads** with `503 + Retry-After` once the event loop lagged past 200 ms or 120 requests were in flight (payments, sign-in, calls, writes and health never shed). Run with 150 virtual users for 40 s on the mixed traffic (*local sandbox*, k6 closed loop):

| | requests/s | public p95 | logged-in p95 | checkout p95 | booking p95 | errors |
|---|---|---|---|---|---|---|
| shedding off | 165 | 985 ms | 797 ms | 1,703 ms | 1,473 ms | 0.00% |
| shedding on | 164 | 1,176 ms | 1,054 ms | 2,113 ms | 1,969 ms | 12.57% |

It made everything slower, so it was **removed** (the commit and its revert are both in the history). Why, as far as I can tell: the anonymous reads are the cheap ones (Redis-cached, about 1 ms), so refusing them frees almost no CPU, and a refused request returns at once so each k6 user loops faster and sends more; the load that fills the process is the writes and signed-in reads, which must not be shed. k6 also ignores `Retry-After`, which real browsers and the apps honour, so this test cannot show the benefit a client that backs off would see. Conclusion: shedding by request class does not help for this mix; the protection that does is capacity (cluster workers) and keeping anonymous traffic at the edge (section 4).
