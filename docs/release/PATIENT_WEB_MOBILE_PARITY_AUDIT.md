# تدقيق استعادة برنامج إنتاج منصة المريض

> هذا التدقيق يصف الحالة الفعلية عند بدء استعادة الخطة الأساسية. لا يعني وجود مسار أو شاشة أن سلوكه مرتبط بعقد خادمي حاكم أو أنه مكافئ للمنصة الأخرى.

## نطاق التدقيق الأولي

يضم `patient-web` حالياً **66** صفحة Next.js ضمن المسار المحلي، بينما يضم `patient-app` **245** مساراً أو شاشة Expo. في مجال الصيدلية وحده، يوجد **22** مساراً في الموبايل مقابل **14** صفحة ويب ذات صلة عامة بالدواء أو السلة أو الطلب أو المحادثة أو التأمين؛ كثير من صفحات الويب الحالية عامة ولا تمثل رحلة بث عروض الصيدليات الحاكمة.

## قيود حاكمة مستعادة

لا توجد محفظة عميل. الدفع الإلكتروني يعتمد فقط على إمكانات البوابة المعتمدة، ونجاحه webhook خادمي؛ النقاط خصم خادمي لا يتجاوز 5% ولا تتحول إلى وسيلة دفع. يبدأ طلب الصيدلية ببث، ثم عروض inventory-backed، ثم اختيار مريض واحد، فالتفاوض عند الحاجة، ثم final quote قبل الدفع. التأمين يمر بقرار لكل بند قبل co-pay أو self-pay أو الإلغاء.

لا يدمج هذا العمل إلى `main` ذاتياً. تبقى الفروع المحمية وطلبات المراجعة والـCI والمراجعة المستقلة شروطاً لازمة. كما يبقى تشغيل scheduler أو worker أو Redis للإنتاج أو migration أو deployment خارج النطاق إلى أن تحسم القيود التشغيلية المطلوبة.

## مصفوفة الصيدلية — baseline للتنفيذ

الـBackend يتيح الآن مسارات حاكمة للمريض تحت `patient/pharmacy/orders`: إنشاء الطلب، إرساله، قراءة العروض، اختيار عرض، قبول final quote، قبول co-pay، قبول self-pay، وCOD. تستخدم شاشات الموبايل الحالية، في مواضع منها، endpoints `orders/bids/*` الموروثة؛ وهي ليست بديلاً عن العرض inventory-backed أو الاختيار المحكوم. لذلك يكون التنفيذ التالي على العقد الحاكم فقط، ولا ينقل واجهة legacy إلى الويب.

## معيار الإغلاق

لا يغلق أي صف في مصفوفة التطابق إلا عندما يحدد بوضوح: مسار الويب، مسار الموبايل، endpoint أو action، الحالة الخادمية، المالك أو الدور، سياسة الإعادة، حالات loading/empty/error/forbidden/success، واختبار قبول. عندها فقط يمكن فتح PR مستقل للحزمة وإلحاق دليل CI بها.
