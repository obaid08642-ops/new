# تدقيق استعادة برنامج إنتاج منصة المريض

> هذا التدقيق يصف الحالة الفعلية عند بدء استعادة الخطة الأساسية. لا يعني وجود مسار أو شاشة أن سلوكه مرتبط بعقد خادمي حاكم أو أنه مكافئ للمنصة الأخرى.

## نطاق التدقيق الأولي

يضم `patient-web` حالياً **66** صفحة Next.js ضمن المسار المحلي، بينما يضم `patient-app` **245** مساراً أو شاشة Expo. في مجال الصيدلية وحده، يوجد **22** مساراً في الموبايل مقابل **14** صفحة ويب ذات صلة عامة بالدواء أو السلة أو الطلب أو المحادثة أو التأمين؛ كثير من صفحات الويب الحالية عامة ولا تمثل رحلة بث عروض الصيدليات الحاكمة.

| المجال | وضع الموبايل الظاهر | وضع الويب الظاهر | التقييم الأولي |
|---|---|---|---|
| الصيدلية | 22 شاشة، تشمل السلة، البث، مقارنة العروض، الاختيار، التفاوض، الدفع، التتبع، الوصفة وإعادة الطلب. | سلة وcheckout عامان، كتالوج الأدوية، الطلبات والتتبع والمحادثة. | فجوة عالية؛ يلزم تنفيذ رحلة عروض الصيدلية الحاكمة في الويب وإعادة ربط الموبايل بالعقود الحالية. |
| التأمين | 13 شاشة متخصصة تشمل policy، approval، co-pay، claims وشبكة المزودين. | صفحة عامة واحدة ظاهرة. | فجوة عالية؛ تحتاج مصفوفة موحدة لحالات القرار والتحمل والدفع الذاتي والإلغاء. |
| الاستشارات | 28 مساراً. | أطباء وتخصصات وموعد ومحادثة ظاهرة. | تدقيق عقدي مطلوب قبل الادعاء بالتطابق. |
| التشخيص | 20 مساراً. | صفحات مختبر/أشعة/باقات ظاهرة. | تدقيق عقدي وحالات دفع/تأمين مطلوبان. |
| الرعاية المنزلية والتمريض | 4 شاشات تمريض إضافة إلى مسارات خدمة أخرى. | كتالوجات ومزودون وخدمات ظاهرة. | تدقيق عقدي وحالات حجز مطلوبان. |
| الصحة والأسرة والإعدادات | 26 شاشة صحة، و12 أسرة، و12 إعدادات. | جزء من مسارات الصحة والأسرة والإعدادات. | فجوة كمية ووظيفية؛ لا تستنتج المساواة من تسمية المسارات. |

## قيود حاكمة مستعادة

لا توجد محفظة عميل. الدفع الإلكتروني يعتمد فقط على إمكانات البوابة المعتمدة، ونجاحه webhook خادمي؛ النقاط خصم خادمي لا يتجاوز 5% ولا تتحول إلى وسيلة دفع. يبدأ طلب الصيدلية ببث، ثم عروض inventory-backed، ثم اختيار مريض واحد، فالتفاوض عند الحاجة، ثم final quote قبل الدفع. التأمين يمر بقرار لكل بند قبل co-pay أو self-pay أو الإلغاء.

لا يدمج هذا العمل إلى `main` ذاتياً. تبقى الفروع المحمية وطلبات المراجعة والـCI والمراجعة المستقلة شروطاً لازمة. كما يبقى تشغيل scheduler أو worker أو Redis للإنتاج أو migration أو deployment خارج النطاق إلى أن تحسم القيود التشغيلية المطلوبة.

## فجوات مؤكدة قبل التنفيذ

| المعرف | الفجوة | الأثر | الإجراء المرحلي |
|---|---|---|---|
| PAR-001 | شاشة `patient-app/app/pharmacy/broadcast-status.tsx` تستخدم `setInterval`. | يخالف قرار عدم استعمال مؤقتات داخل تطبيق المريض، ويستدعي endpoint bids قديم. | استبدالها بتحديث يدوي صريح وربطها بعقود عروض الصيدلية الحاكمة. |
| PAR-002 | `patient-web` لا يقدم رحلة بث وعروض واختيار وتفاوض وعرض نهائي وتأمين صيدلية مكافئة للموبايل. | لا يمكن اعتبار الويب مطابقاً للموبايل أو مؤهلاً لرحلة الصيدلية المتفق عليها. | تنفيذها على حزم صغيرة، بواجهة لكل حالة حاكمة واختبارات قبول. |
| PAR-003 | عدد مسارات الموبايل أكبر بكثير من الويب. | لا دليل على التكافؤ الوظيفي عبر بقية المجالات. | بناء مصفوفة route/action/API/state مكتملة قبل التنفيذ، ثم ترتيب التنفيذ وفق خطورة المال والحالة والخصوصية. |
| PAR-004 | وجود مسار لا يثبت ارتباطه بواجهة API أو صلاحيات أو idempotency صحيحة. | خطر واجهات تجريبية أو عقود قديمة في سياقات المرضى والدفع. | تدقيق كل مسار ذي فعل حاكم ومطابقته بالعقد والخدمة والاختبار. |
| PAR-005 | تظهر مؤقتات `setInterval`/`setTimeout` متعددة في تطبيقات المريض، بما فيها polling للبث والتأمين والدفع والتتبع. | تخالف قرار عدم منح العميل سلطة lifecycle داخل الذاكرة، وتستدعي أحياناً مسارات legacy. | تصنيف كل مؤقت: واجهة فقط أو business/polling، ثم إزالة الثاني واستبداله بتحديث صريح أو حدث موثق؛ لا تعالج بزيادة فترة polling. |
| PAR-006 | توجد cron/queue/worker وlegacy sweep paths متعددة في الباكند خارج أمر انتهاء الصيدلية الجديد. | لا يمكن اعتبار نطاق الإنتاج مضبوطاً قبل حصر الملكية وسلامة persistence والمراقبة لكل مسار. | تدقيق مستقل لكل مسار؛ أمر انتهاء عروض وبث الصيدلية فقط يبقى مؤجلاً إلى القرار التشغيلي ولا ينشأ له runner الآن. |
| PAR-007 | كانت mutations `create` و`update` و`submit` و`cancel` لطلب الصيدلية لا تفرض idempotency، بخلاف اختيار العرض والدفع. | إمكانية تكرار إنشاء أو إرسال أو إلغاء طلب عند إعادة المحاولة من العميل. | تفرض جميع mutations المملوكة للمريض `IdempotencyInterceptor` و`RequireIdempotency` ويثبتها اختبار controller. |

## مصفوفة الصيدلية — baseline للتنفيذ

الـBackend يتيح الآن مسارات حاكمة للمريض تحت `patient/pharmacy/orders`: إنشاء الطلب، إرساله، قراءة العروض، اختيار عرض، قبول final quote، قبول co-pay، قبول self-pay، وCOD. تستخدم شاشات الموبايل الحالية، في مواضع منها، endpoints `orders/bids/*` الموروثة؛ وهي ليست بديلاً عن العرض inventory-backed أو الاختيار المحكوم. لذلك يكون التنفيذ التالي على العقد الحاكم فقط، ولا ينقل واجهة legacy إلى الويب.

| تجربة المريض | Mobile الحالي | Web الحالي | الفعل الحاكم المستهدف | الحالة |
|---|---|---|---|---|
| اكتشاف الدواء والبحث | `pharmacy/product-search` و`barcode-scanner` | `medicines` و`medicine-catalog` | catalog/search ثم عناصر سلة صيدلية | يحتاج تدقيق مدخلات البحث والمسح وتكافؤ UX. |
| تفاصيل الدواء | `pharmacy/product-detail` | `medicines/[medicineId]` | إضافة/تعديل عنصر السلة | يحتاج تحقق أن إضافة السلة لا تقبل سعراً أو كمية غير خادميين. |
| وصفة أو طلب يدوي أو عنصر مخصص | `rx-order` و`scan-prescription` و`manual-order` و`custom-item` | `cart/prescription` و`prescriptions` | `POST patient/pharmacy/orders` ثم submit | فجوة Web/Mobile؛ يلزم عقد طلب صيدلية موحد وحالات خصوصية للمرفقات. |
| مراجعة السلة | `pharmacy/cart` | `cart` | إنشاء/تعديل draft للمريض | يحتاج فصل واضح بين سلة عامة وطلب صيدلية broadcast-first. |
| إرسال الطلب للبث | `pharmacy/checkout` و`order-confirm` | لا توجد صفحة مكافئة | `POST patient/pharmacy/orders/:id/submit` | فجوة Web مؤكدة. لا ينشأ payment intent هنا. |
| انتظار عروض الصيدليات | `pharmacy/waiting-for-pharmacy` و`broadcast-status` | لا توجد صفحة مكافئة | `GET patient/pharmacy/orders/:id/offers` | فجوة Web وموبايل: مسار الموبايل يستخدم polling بـ`setInterval` وendpoints bids موروثة. |
| مقارنة عروض مستقلة | `pharmacy/medicine-compare` | لا توجد صفحة مكافئة | `GET …/offers` | فجوة Web مؤكدة؛ يلزم عرض items وبدائل وإجمالي ومهلة ببيانات خادمية فقط. |
| اختيار صيدلية واحدة | `broadcast-status` | لا توجد صفحة مكافئة | `POST …/offers/:offerId/select` مع idempotency key | فجوة كاملة؛ لا قبول bid موروث. |
| تفاوض البدائل والنواقص | `chat-with-pharmacist` و`pharmacist-chat` | `chat/[threadId]` عام | مسارات `pharmacy/chat/threads/*` وربط اختيار البديل | يحتاج تقييد ownership وربط order-item والتحقق قبل final quote. |
| قبول السعر النهائي | `pharmacy/checkout` و`payment` | `cart/checkout` عام | `POST …/final-quote/accept` مع hash/revision | فجوة Web/Mobile؛ لا يسمح بالدفع قبل قبول snapshot الصحيح. |
| نقد/بطاقة/Apple Pay/Google Pay | `pharmacy/payment` | لا توجد خطوة صيدلية مكافئة | payment intent من quote مقبول أو COD eligible | فجوة؛ لا wallet ولا نجاح دفع محلي. |
| تأمين: قرار البنود ثم co-pay أو self-pay | شاشات تأمين عامة و`payment` | `insurance` عام | `…/insurance/co-pay/accept` أو `…/insurance/self-pay/accept` | فجوة عالية؛ يلزم no-payment عندما التغطية كاملة وقرار صريح لكل بند. |
| COD مؤهل | `pharmacy/payment` | لا توجد خطوة صيدلية مكافئة | `POST …/cod/register` | فجوة؛ يظهر فقط عند eligibility خادمية ولا يسجل كمدفوع. |
| التتبع والسجل وإعادة الطلب | `order-tracking` و`order-history` و`reorder` | `orders` و`orders/[orderId]` و`tracking` | `GET patient/pharmacy/orders*` وفعل reorder الآمن | يحتاج مواءمة DTO والحالات المحكومة بعد الاختيار والتأكيد. |
| wishlist والفلاتر وعدم العثور | `wishlist` و`filters` و`drug-not-found` | `wishlist` وكتالوجات عامة | query/favorites وshortage lookup | يحتاج توحيد intent من دون تحويل عدم العثور إلى عرض أو سعر مختلق. |

## معيار الإغلاق

لا يغلق أي صف في مصفوفة التطابق إلا عندما يحدد بوضوح: مسار الويب، مسار الموبايل، endpoint أو action، الحالة الخادمية، المالك أو الدور، سياسة الإعادة، حالات loading/empty/error/forbidden/success، واختبار قبول. عندها فقط يمكن فتح PR مستقل للحزمة وإلحاق دليل CI بها.

## موجات التنفيذ المقررة

| الموجة | النطاق | مخرج المراجعة | شرط الإغلاق |
|---|---|---|---|
| W0 | ضبط المسارات الموروثة: منع wallet، حصر timers وpolling، وفصل endpoints القديمة عن العقود الحاكمة. | PRs صغيرة حسب المجال؛ لا scheduler جديد. | لا يبقى فعل مالي أو expiry أو broadcast يعتمد على timer عميل أو endpoint bid قديم. |
| W1 | رحلة الصيدلية النقدية: إنشاء الطلب، الإرسال، العروض، الاختيار، التفاوض، final quote، card/COD، التتبع. | Backend contract gap PR ثم Web PR وMobile PR. | يمر مسار واحد كامل بعقد خادمي ويدعم الحالات الست للواجهة. |
| W2 | رحلة تأمين الصيدلية: قرار كل بند، تغطية كاملة، co-pay، self-pay، والإلغاء الصريح. | PRs منفصلة للعقد والعميلين. | لا يُنشأ دفع قبل القرار ولا يوجد دفع صوري عند zero co-pay. |
| W3 | الاستشارات والتشخيص والرعاية المنزلية والتمريض: cash مقابل insurance على عقد موحد لكل خدمة. | مصفوفة خدمة ثم PRs حسب الخدمة. | السعر والموعد والتغطية والدفع والملكية مثبتة بالخادم وظهرت في العميلين. |
| W4 | الصحة والأسرة والملف والإعدادات والمحتوى والدعم: إغلاق المسارات المفقودة أو إعلانها خارج نطاق الإصدار. | PRs موضوعية، لا صفحات صورية. | كل route في الموبايل له نظير ويب أو قرار product موثق، والعكس صحيح. |
| W5 | اختبارات قبول متقاطعة، accessibility، خصوصية، سلامة التحويلات، أدلة CI، وحزمة المدقق. | مراجعة إصدار مستقلة. | لا توجد فجوات حرجة مفتوحة، وكل PR في سلسلة الإصدار اجتاز CI ومراجعة مستقلة قبل أي دمج. |

لا يعني هذا الجدول نشر التطبيق أو إعطاء وعد بالجاهزية؛ فهو يحدد فقط ترتيب إغلاق الأدلة الفنية اللازمة للوصول إلى مراجعة إصدار منظمة.
