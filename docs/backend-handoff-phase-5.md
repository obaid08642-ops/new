# حزمة تسليم Backend — فجوات Web App المريض

## الغرض وحدود الأمان

هذه الحزمة تحدد التغييرات الخلفية اللازمة لاستكمال صفحات المريض التي **لم تُنشأ ببيانات بديلة**. جميع المتطلبات مخصصة لواجهة المريض فقط، وتفترض أن كل قراءة خاصة تُنفذ باسم المريض الحالي المستخرج من JWT، لا من معرّف يرسله العميل. لا يجب أن تحتوي أخطاء الرفض على بيانات أو معرّفات مورد تخص مريضاً آخر.

| الأولوية | الفجوة | أثرها الحالي في الويب | قرار الويب الحالي |
|---|---|---|---|
| حرجة | G-HOME-001 | لا توجد تفاصيل حجز رعاية منزلية آمنة | عرض القائمة فقط بلا رابط تفاصيل |
| حرجة | G-OTP-001 | لا يمكن إنشاء جلسة ويب بعد تحقق OTP | تعطيل دخول OTP؛ دخول كلمة المرور فقط |
| حرجة | G-PROFILE-001 | لا توجد هوية عرض موثوقة للملف الشخصي | عرض المجال الصحي المسموح فقط |
| عالية | G-FAMILY-001 | لا يوجد اسم عرض آمن لعضو العائلة | حجب المعرّف والصلاحيات الخام |
| عالية | G-OAPI-001 / G-OAPI-002 | لا تكفي المواصفة لتوليد عميل آمن أو مراجعة كاملة | الاعتماد على BFF ومحللات Zod واختبارات Sandbox |
| عالية | G-FILE-001 / G-RTC-001 | لا يمكن بناء رفع الوثائق أو الاتصال اللحظي بأمان | لا أزرار رفع أو مكالمات أو غرف لحظية |

## G-HOME-001 — تفاصيل حجز الرعاية المنزلية

أضيفوا عملية مريض قرائية صريحة: `GET /home-care/bookings/{bookingId}`. يجب أن يستنتج الخادم المريض من JWT، ويطبق شرط ملكية في الاستعلام نفسه، ويعيد `404` عند عدم وجود الحجز أو عدم ملكيته. لا تقبلوا `patientId` أو `userId` من query أو body لتحديد الملكية.

| بند العقد | المتطلب | غير مسموح |
|---|---|---|
| Path parameter | `bookingId` بصيغة المعرّف الرسمي فقط | تمرير معرّف مريض أو مزود أو مهمة في URI |
| DTO العرض | `service_name` أو رمز خدمة منشور، `status`، وموعد مجدول موحد المنطقة الزمنية عند توفره | موقع المريض، رقم هاتفه، ملاحظات سريرية، مرفقات، إحداثيات، سعر أو حقول مزود داخلية |
| التفويض | `booking.patient_id = currentUser.id` في backend | تحقق واجهة أو إرجاع مورد مريض آخر ثم إخفاؤه |
| الأخطاء | `401` بلا جلسة، `404` لمورد غير موجود أو غير مملوك، `422` لمعرف غير صالح | `403` يكشف وجود المورد أو رسائل تتضمن بياناته |
| OpenAPI | Bearer security وDTO نجاح/خطأ كاملان | تعريف مسار بلا responses أو security |

**معيار القبول.** يسجل حساب Sandbox المالك ويقرأ حجزه بـ`200`، بينما الحساب الآخر يحصل على `404` لنفس `bookingId`. يثبت اختبار SSR أن HTML لا يضم المعرف أو الموقع أو أي ملاحظة أو رابط تقرير أو توكن.

## G-OTP-001 — تأسيس جلسة بعد تحقق OTP

يحافظ `POST /auth/verify-otp` على الغرض الأمني للتحقق، لكنه يجب ألا يعيد `{ ok: true }` وحدها لرحلة دخول. اختاروا أحد العقدين التاليين فقط، ووثقوا الاختيار في OpenAPI:

| الخيار | استجابة النجاح | قيد إلزامي |
|---|---|---|
| جلسة كاملة مباشرة | نفس بنية `POST /auth/login`: `accessToken` و`refreshToken` وبيانات device اللازمة | تدوير/إبطال الرمز بعد استخدام واحد، حد معدل، صلاحية قصيرة، وتحقق ملكية القناة |
| رمز تبديل قصير العمر | `exchange_token` أحادي الاستخدام مع `expires_at` | endpoint تبديل خادمي فقط يعيد حزمة الجلسة؛ لا يقبل client-side token في URL |

يجب أن تعرف استجابات الفشل `400` أو `422` للمدخلات غير الصالحة، و`401` أو `403` للرمز غير الصالح أو المنتهي، و`429` لحد المعدل، دون إخبار العميل ما إذا كان رقم الهاتف أو البريد مسجلاً. لا يضع Web App أي توكن في `localStorage` أو query string، بل يحول نجاح الخلفية إلى cookies خادمية httpOnly فقط.

## G-PROFILE-001 — DTO هوية الملف الشخصي

ينبغي أن يعيد `GET /users/me/profile` DTO عرض مستقلاً عن نموذج التخزين. لا تعتمد الواجهة على أسماء أعمدة أو مسارات صور داخلية. الحقول اختيارية بالكامل باستثناء بنية الاستجابة.

```ts
type PatientProfileView = {
  display_name: string | null;
  avatar_url: string | null;
  preferred_locale: "ar" | "en" | null;
  date_of_birth: string | null;
  gender: "female" | "male" | "unspecified" | null;
};
```

لا يعيد DTO: `user_id`، البريد أو الهاتف، tokens، مسارات تخزين خام، بيانات اعتماد، سجل جلسات، أو حقول admin/provider. إن كانت صورة الحساب خاصة، فلتكن `avatar_url` مؤقتة وموقعة ومحدودة العمر، أو اجعلوا القيمة `null` بدلاً من رابط عام ثابت.

## G-FAMILY-001 — DTO قائمة العائلة

ينبغي أن يحل DTO مقيد محل `user_id` و`permissions` الخام. يكفي للصفحة القرائية الحالية الاسم المعروض والدور وتاريخ الانضمام عند إتاحته.

```ts
type FamilyMemberListItem = {
  display_name: string | null;
  role: "owner" | "member" | "dependent";
  joined_at: string | null;
};
```

لا تعرضوا معرّفات المستخدمين أو الصلاحيات الدقيقة أو سجلات الصحة أو الدعوات. أي endpoint تفاصيل عضو أو صحته يحتاج تفويضاً مستقلاً، وحدود موافقة، واختبار BOLA بين أعضاء مختلفين؛ لا يكفي نجاح القائمة.

## G-OAPI-001 وG-OAPI-002 — اكتمال المواصفة

| عنصر المواصفة | الحد الأدنى المطلوب |
|---|---|
| `servers` | عنوان production وSandbox/اختبار معلنان بوضوح دون أسرار |
| `securitySchemes` | Bearer JWT وتعريف ما إذا كانت refresh token تُرسل في body أو cookie |
| `security` | تطبيق عالمي ثم overrides فقط للمسارات العامة وتسجيل الدخول |
| Responses | مخططات نجاح وخطأ لـ`200/201` و`400/401/403/404/409/422/429/5xx` حيث تنطبق |
| DTOs | تعريف الحقول العامة والخاصة، enums، صيغ المعرفات والتواريخ، وقيود length/pattern |
| أمثلة آمنة | بلا توكنات أو بريد أو سجلات صحية حقيقية أو روابط موقعة |

## G-FILE-001 وG-RTC-001 — عقود مؤجلة مقفلة افتراضياً

قبل تفعيل رفع وثيقة أو نتيجة أو محادثة أو مكالمة، يلزم توثيق endpoint منح upload ومحددات MIME والحجم وفحص الحالة وعمر URL الموقّع وقاعدة ملكية القراءة. وللمكالمات أو الاتصال اللحظي، يلزم إصدار room token قصير العمر مربوط بالمريض والمشارك والغرض، مع التحقق في خادم token وفي Signal/LiveKit، وحالات رفض وانتهاء وإعادة اتصال. تبقى هذه الواجهات غير موجودة في Web App إلى إتمام ذلك.

## ترتيب التسليم وإعادة الاختبار

ابدؤوا بالرعاية المنزلية وDTO الملف الشخصي، ثم OTP وDTO العائلة، ثم إعادة تصدير OpenAPI. بعد كل تسليم، يضاف اختبار Sandbox قرائي منفصل إلى `pnpm test:sandbox` ويثبت نجاح المالك وحجب الحساب الآخر حيث يوجد مورد قابل للعزل. لا تبدأ واجهة تعديل أو رفع أو مكالمة أو إعادة صرف من الويب بسبب هذه الحزمة وحدها؛ كل عملية تغير حالة لها بوابة أمن مستقلة.
