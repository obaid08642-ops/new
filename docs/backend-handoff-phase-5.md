# حزمة تسليم Backend — فجوات Web App المريض

## الغرض وحدود الأمان

هذه الحزمة تحدد التغييرات الخلفية اللازمة لاستكمال صفحات المريض التي **لم تُنشأ ببيانات بديلة**. جميع المتطلبات مخصصة لواجهة المريض فقط، وتفترض أن كل قراءة خاصة تُنفذ باسم المريض الحالي المستخرج من JWT، لا من معرّف يرسله العميل. لا يجب أن تحتوي أخطاء الرفض على بيانات أو معرّفات مورد تخص مريضاً آخر.

| الأولوية | الفجوة | أثرها الحالي في الويب | قرار الويب الحالي |
|---|---|---|---|
| حرجة | G-HOME-001 | لا توجد تفاصيل حجز رعاية منزلية آمنة | عرض القائمة فقط بلا رابط تفاصيل |
| حرجة | G-OTP-001 | لا يمكن إنشاء جلسة ويب بعد تحقق OTP | تعطيل دخول OTP؛ دخول كلمة المرور فقط |
| حرجة | G-PROFILE-001 | لا توجد هوية عرض موثوقة للملف الشخصي | عرض المجال الصحي المسموح فقط |
| عالية | G-FAMILY-001 | لا يوجد اسم عرض آمن لعضو العائلة | حجب المعرّف والصلاحيات الخام |
| عالية | G-DATA-004 | عدّ مزودي الخدمة الظاهر لبعض التخصصات يساوي صفراً رغم أن اكتشاف التخصصات والأطباء غير فارغ إجمالاً | لا تعرض الواجهة عدّاً أو مزودين مشتقين محلياً |
| عالية | G-OAPI-001 / G-OAPI-002 | لا تكفي المواصفة لتوليد عميل آمن أو مراجعة كاملة | الاعتماد على BFF ومحللات Zod واختبارات Sandbox |
| عالية | G-FILE-001 / G-RTC-001 | لا يمكن بناء رفع الوثائق أو الاتصال اللحظي بأمان | لا أزرار رفع أو مكالمات أو غرف لحظية |
| حرجة | G-SEO-002 | كتالوج `/medicines` العام يعيد عناصر دوائية وغير دوائية معاً بلا حقل نشر أو تصنيف موثوق | كتالوج عام `noindex` بلا وسم `Drug` أو sitemap للتفاصيل |
| حرجة | G-PRESCRIPTION-001 | قائمة الوصفات الذاتية قابلة للقراءة، لكن لا يوجد عقد موثق أو قابل للاختبار لتفاصيل وصفة مملوكة | لا صفحة تفاصيل ولا إرسال أو رفع أو OCR أو طلب صرف |
| حرجة | G-CHAT-001 | قائمة المحادثات الذاتية قابلة للقراءة، لكن لا يوجد عقد موثق أو قابل للاختبار لتفاصيل محادثة ورسائلها | لا فتح رسائل أو إرسال أو تسليم أو تعليم قراءة |

## G-HOME-001 — تفاصيل حجز الرعاية المنزلية

أضيفوا عملية مريض قرائية صريحة: `GET /home-care/bookings/{bookingId}`. يجب أن يستنتج الخادم المريض من JWT، ويطبق شرط ملكية في الاستعلام نفسه، ويعيد `404` عند عدم وجود الحجز أو عدم ملكيته. لا تقبلوا `patientId` أو `userId` من query أو body لتحديد الملكية.

| بند العقد | المتطلب | غير مسموح |
|---|---|---|
| Path parameter | `bookingId` بصيغة المعرّف الرسمي فقط | تمرير معرّف مريض أو مزود أو مهمة في URI |
| DTO العرض | `service_name` أو رمز خدمة منشور، `status`، وموعد مجدول موحد المنطقة الزمنية عند توفره | موقع المريض، رقم هاتفه، ملاحظات سريرية، مرفقات، إحداثيات، سعر أو حقول مزود داخلية |
| التفويض | `booking.patient_id = currentUser.id` في backend | تحقق واجهة أو إرجاع مورد مريض آخر ثم إخفاؤه |
| الأخطاء | `401` بلا جلسة، `404` لمورد غير موجود أو غير مملوك، `422` لمعرف غير صالح | `403` يكشف وجود المورد أو رسائل تتضمن بياناته |
| OpenAPI | Bearer security وDTO نجاح/خطأ كاملان | تعريف مسار بلا responses أو security |

**معيار القبول.** يسجل حساب Sandbox المالك ويقرأ حجزه بـ`200`، بينما الحساب الآخر يحصل على `404` لنفس `bookingId`. يثبت اختبار SSR أن HTML لا يضم المعرف أو الموقع أو أي ملاحظة أو رابط تقرير أو توكن.

## G-OTP-001 — تأسيس جلسة بعد تحقق OTP

يحافظ `POST /auth/verify-otp` على الغرض الأمني للتحقق، لكنه يجب ألا يعيد `{ ok: true }` وحدها لرحلة دخول. اختاروا أحد العقدين التاليين فقط، ووثقوا الاختيار في OpenAPI:

| الخيار | استجابة النجاح | قيد إلزامي |
|---|---|---|
| جلسة كاملة مباشرة | نفس بنية `POST /auth/login`: `accessToken` و`refreshToken` وبيانات device اللازمة | تدوير/إبطال الرمز بعد استخدام واحد، حد معدل، صلاحية قصيرة، وتحقق ملكية القناة |
| رمز تبديل قصير العمر | `exchange_token` أحادي الاستخدام مع `expires_at` | endpoint تبديل خادمي فقط يعيد حزمة الجلسة؛ لا يقبل client-side token في URL |

يجب أن تعرف استجابات الفشل `400` أو `422` للمدخلات غير الصالحة، و`401` أو `403` للرمز غير الصالح أو المنتهي، و`429` لحد المعدل، دون إخبار العميل ما إذا كان رقم الهاتف أو البريد مسجلاً. لا يضع Web App أي توكن في `localStorage` أو query string، بل يحول نجاح الخلفية إلى cookies خادمية httpOnly فقط.

## G-PROFILE-001 — DTO هوية الملف الشخصي

ينبغي أن يعيد `GET /users/me/profile` DTO عرض مستقلاً عن نموذج التخزين. لا تعتمد الواجهة على أسماء أعمدة أو مسارات صور داخلية. الحقول اختيارية بالكامل باستثناء بنية الاستجابة.

```ts
type PatientProfileView = {
  display_name: string | null;
  avatar_url: string | null;
  preferred_locale: "ar" | "en" | null;
  date_of_birth: string | null;
  gender: "female" | "male" | "unspecified" | null;
};
```

لا يعيد DTO: `user_id`، البريد أو الهاتف، tokens، مسارات تخزين خام، بيانات اعتماد، سجل جلسات، أو حقول admin/provider. إن كانت صورة الحساب خاصة، فلتكن `avatar_url` مؤقتة وموقعة ومحدودة العمر، أو اجعلوا القيمة `null` بدلاً من رابط عام ثابت.

## G-FAMILY-001 — DTO قائمة العائلة

ينبغي أن يحل DTO مقيد محل `user_id` و`permissions` الخام. يكفي للصفحة القرائية الحالية الاسم المعروض والدور وتاريخ الانضمام عند إتاحته.

```ts
type FamilyMemberListItem = {
  display_name: string | null;
  role: "owner" | "member" | "dependent";
  joined_at: string | null;
};
```

لا تعرضوا معرّفات المستخدمين أو الصلاحيات الدقيقة أو سجلات الصحة أو الدعوات. أي endpoint تفاصيل عضو أو صحته يحتاج تفويضاً مستقلاً، وحدود موافقة، واختبار BOLA بين أعضاء مختلفين؛ لا يكفي نجاح القائمة.

## G-PRESCRIPTION-001 — تفاصيل وصفة مريض مقيدة

أثبت تحقق Sandbox القرائي أن `GET /prescriptions/mine` ينجح للمريض المسجل ويعيد `401` بلا جلسة، لكنه لا يثبت ملكية تفصيل وصفة: لا يعرّف OpenAPI مسار تفاصيل للمريض، ولا تتوفر واجهة ويب بمسار يمكن اختبار حساب Sandbox الآخر عليه. أضيفوا عملية قراءة تفصيلية صريحة، مثل `GET /prescriptions/{prescriptionId}`، على أن يستنتج الخادم المريض من JWT ويطبق شرط الملكية في الاستعلام نفسه.

| بند العقد | المتطلب | غير مسموح |
|---|---|---|
| التفويض | `prescription.patient_id = currentUser.id` في الاستعلام الخادمي | تمرير `patientId` أو الاعتماد على إخفاء الواجهة |
| DTO العرض | حالة الوصفة، تاريخ الإصدار، وبنود دوائية محدودة صالحة للعرض عند الحاجة الطبية | معرف مريض، تشخيص، ملاحظات سريرية، توقيع، مرفق، رابط تخزين، سعر أو تغطية تأمين |
| الأخطاء | `401` بلا جلسة، `404` لوصفة غير موجودة أو غير مملوكة، `422` لمعرف غير صالح | `403` يكشف وجود وصفة مريض آخر أو رسالة تتضمن وصفها |
| الحدود | قراءة فقط؛ لا ينشئ أو يرفع أو يترجم OCR أو يرسل للصيدلية أو يبدل الدواء أو يطلب الصرف | تفعيل أي mutation من الويب استناداً إلى نجاح القائمة |
| OpenAPI | Bearer security، نمط المعرف، success/error DTOs، وحدود الحقول المعروضة | مسار غير موثق أو DTO تخزين داخلي |

**معيار القبول.** يستخرج اختبار Sandbox معرف الوصفة داخلياً من قائمة المالك دون طباعته، فينجح طلب التفاصيل للمالك بـ`200` ويحصل الحساب الآخر على `404` للمعرف نفسه. يثبت اختبار SSR أن HTML لا يتضمن معرّف الوصفة أو أي تشخيص أو ملف أو سعر أو توكن.

## G-CHAT-001 — تفاصيل محادثة مريض مقيدة

أثبت تحقق Sandbox القرائي أن `GET /chat/threads` ينجح للمريض المسجل ويعيد `401` بلا جلسة، لكنه لا يثبت ملكية محادثة بعينها: لا يعرّف OpenAPI عملية قراءة threads أو الرسائل للمريض، ولا يوجد مسار تفاصيل مثبت يسمح باختبار حساب Sandbox الآخر. أضيفوا قائمة وتفاصيل مخصصتين للمريض، مثل `GET /chat/threads` و`GET /chat/threads/{threadId}`، على أن تستنتج هوية المريض من JWT وتطبق عضوية المشارك في الاستعلام الخادمي.

| بند العقد | المتطلب | غير مسموح |
|---|---|---|
| التفويض | عضوية `currentUser` في thread قبل جلب أي بيانات أو رسائل | تمرير `userId` أو الاعتماد على إخفاء عناصر الواجهة |
| قائمة العرض | نوع المحادثة ووقت آخر نشاط فقط للعرض المختصر | معرفات المشاركين، الأسماء، معاينة الرسالة، نص الرسائل، مرفقات أو روابط غرف |
| التفاصيل والرسائل | DTO منفصل ومحدود يُتفق عليه لاحقاً، مع paging وحدود ردود الفعل والحذف | إرجاع سجل الرسائل أو المرفقات أو metadata لحساب غير مشارك |
| الأخطاء | `401` بلا جلسة، `404` لمحادثة غير موجودة أو غير مملوكة، `422` لمعرف غير صالح | `403` يكشف وجود المحادثة أو رسالة/مشارك منها |
| الحدود | لا إرسال ولا تسليم ولا تعليم قراءة ولا إنشاء thread أو مكالمة حتى تثبت عمليات mutation وtoken/RTC | زر أو mutation شكلي أو client-side state بديل |
| OpenAPI | Bearer security، schema لقائمة المريض والتفاصيل والأخطاء، وتعريف paging | عمليات لا تصف التفويض أو response fields |

**معيار القبول.** يستخرج اختبار Sandbox معرف thread داخلياً من قائمة المالك دون طباعته، فينجح طلب التفاصيل للمالك بـ`200` ويحصل الحساب الآخر على `404` للمعرف نفسه. لا يجلب اختبار القائمة رسائل أو يغير حالة المحادثة، ويثبت اختبار SSR أن HTML لا يتضمن المعرّفات أو الأسماء أو الرسائل أو المشاركين أو المرفقات أو التوكن.

## G-DATA-004 — عدّ مزودي الخدمة للتخصصات

أكد اختبار Sandbox أن `GET /care/specialties` و`GET /care/doctors` يعيدان سجلات غير فارغة إجمالاً، من دون كشف أي سجل في مخرجات الاختبار. لذلك لا ينبغي معالجة العَدّ الصفري ببيانات محلية أو استنتاج علاقة مزود/تخصص في الويب. المطلوب عقد اكتشاف مخصص يعيد فقط البيانات المنشورة والصالحة للعرض.

```ts
type PublishedSpecialtyListItem = {
  id: string;
  name_ar: string | null;
  name_en: string | null;
  published_provider_count: number;
};
```

| بند العقد | المتطلب | غير مسموح |
|---|---|---|
| المصدر | عدّ مولّد من مزودين منشورين ونشطين ومؤهلين للحجز فقط | عدّ ثابت أو اشتقاق الواجهة من قائمة عامة للأطباء |
| الاتساق | يطابق `published_provider_count` نتيجة فلتر الأطباء للتخصص نفسه في البيئة ذاتها | إرجاع صفر عند وجود مزودين منشورين أو احتساب مزودين موقوفين/غير منشورين |
| الخصوصية | لا يعيد معرفات مزود أو بيانات اعتماد أو حالة مراجعة داخلية | تسريب تراخيص أو حالات KYC أو بيانات تواصل |
| التوثيق | schema وBearer/public security وحدود paging/filter والأخطاء | تعريف بلا DTO أو وصف دلالة العَدّ |

**معيار القبول.** يختبر Sandbox أن كل تخصص منشور يعيد عدداً صحيحاً غير سالب، وأن أي تخصص بعدد أكبر من صفر ينتج قائمة أطباء منشورة عند الفلترة نفسها. يبقى الويب على empty state ولا يعرض العَدّ حتى تسليم العقد وتحقق هذا المعيار.

## G-OAPI-001 وG-OAPI-002 — اكتمال المواصفة

| عنصر المواصفة | الحد الأدنى المطلوب |
|---|---|
| `servers` | عنوان production وSandbox/اختبار معلنان بوضوح دون أسرار |
| `securitySchemes` | Bearer JWT وتعريف ما إذا كانت refresh token تُرسل في body أو cookie |
| `security` | تطبيق عالمي ثم overrides فقط للمسارات العامة وتسجيل الدخول |
| Responses | مخططات نجاح وخطأ لـ`200/201` و`400/401/403/404/409/422/429/5xx` حيث تنطبق |
| DTOs | تعريف الحقول العامة والخاصة، enums، صيغ المعرفات والتواريخ، وقيود length/pattern |
| أمثلة آمنة | بلا توكنات أو بريد أو سجلات صحية حقيقية أو روابط موقعة |

## G-SEO-002 — تصنيف ونشر الكتالوج العام

مسار الكتالوج العام الحالي يعيد عناصر ليست أدوية إلى جانب عناصر دوائية، لذلك لا يمكن للويب أن يستنتج نوع الكيان من الاسم أو المادة الفعالة. أضيفوا DTO عاماً منفصلاً عن DTO المريض، ولا تجعلوا الوصول العام مجرد نسخة بلا Bearer من مورد خاص.

```ts
type PublishedCatalogueItem = {
  id: string;
  slug: string;
  entity_type: "medicine" | "medical_device" | "personal_care" | "other";
  is_published: boolean;
  name_ar: string | null;
  name_en: string | null;
  active_ingredient: string | null;
  generic_name: string | null;
  dosage_form: string | null;
  strength: string | null;
  updated_at: string;
};
```

| بند العقد | المتطلب | غير مسموح |
|---|---|---|
| قائمة عامة | `GET /public/catalogue?entity_type=medicine&locale=ar&page=…` لا يعيد إلا `is_published=true` | إرجاع عناصر مختلطة ثم الاعتماد على الويب لتخمين النوع |
| تفاصيل عامة | `GET /public/catalogue/medicines/{slug}` يعيد عنصراً منشوراً مصنفاً دواء | إتاحة تفاصيل عنصر غير منشور أو غير دوائي على مسار دواء |
| الهوية | `slug` ثابت وفريد ولا يتضمن معرف مريض أو تخزين داخلي | استخدام معرف قابل للتخمين أو raw database key كعنوان فهرسة معلن |
| الصفات | الحقول الظاهرة فقط، مع `updated_at` موثوق | السعر، المخزون، وصفة مريض، تأمين، مورد، صور خاصة أو روابط موقعة |
| الأخطاء | `404` لعنصر غير منشور/غير موجود و`422` لمدخل غير صالح | `403` أو رسالة تكشف حالة النشر أو سبب الحجب |

**معيار القبول.** ينجح اختبار بلا جلسة على قائمة `entity_type=medicine` وينتج عناصر ذات `is_published=true` و`slug` صالح، ويعيد مسار الدواء `404` لأي عنصر غير دوائي أو غير منشور. عندها فقط يفعّل الويب canonical وhreflang و`Drug` JSON-LD وsitemap لعناصر الدواء، مع اختبار SSR يمنع السعر والبيانات الخاصة.

## G-FILE-001 وG-RTC-001 — عقود مؤجلة مقفلة افتراضياً

قبل تفعيل رفع وثيقة أو نتيجة أو محادثة أو مكالمة، يلزم توثيق endpoint منح upload ومحددات MIME والحجم وفحص الحالة وعمر URL الموقّع وقاعدة ملكية القراءة. وللمكالمات أو الاتصال اللحظي، يلزم إصدار room token قصير العمر مربوط بالمريض والمشارك والغرض، مع التحقق في خادم token وفي Signal/LiveKit، وحالات رفض وانتهاء وإعادة اتصال. تبقى هذه الواجهات غير موجودة في Web App إلى إتمام ذلك.

## ترتيب التسليم وإعادة الاختبار

ابدؤوا بالرعاية المنزلية وDTO الملف الشخصي، ثم OTP وDTO العائلة، ثم إعادة تصدير OpenAPI. بعد كل تسليم، يضاف اختبار Sandbox قرائي منفصل إلى `pnpm test:sandbox` ويثبت نجاح المالك وحجب الحساب الآخر حيث يوجد مورد قابل للعزل. لا تبدأ واجهة تعديل أو رفع أو مكالمة أو إعادة صرف من الويب بسبب هذه الحزمة وحدها؛ كل عملية تغير حالة لها بوابة أمن مستقلة.
