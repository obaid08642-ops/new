## What it was not

- **Not memory:** no OOM kill in the kernel log for the last 48 h; `OOMKilled=false` on every container; 1.7 GB available
  now, swap 4 GB almost unused. (Risk noted below, but not the cause.)
- **Not disk:** `/` 68 % (13 GB free), inodes 15 %.
- **Not a crash or a hang:** the stop was orderly (exit 0 / SIGTERM in container order, fail2ban stopping cleanly),
  no hung-task, soft-lockup, I/O or file-system error in the kernel log.
- **Not the application:** no container died before the shutdown; container logs carry no fatal error.
- **Not the firewall or fail2ban:** UFW allows 22/80/443, and a firewall or ban cannot explain a host that logged a
  shutdown and nothing for 17 h. One side note: on 2026-10-14 fail2ban banned `20.115.x.x` from 15:54 to 16:54; that
  range is Azure, where GitHub-hosted runners run (full address `20.115.209.228`), so an SSH timeout from a runner in
  that hour (after the host was back) may have been a ban. The ops workflow authenticates with a key on the first
  try, so it should not trip the `sshd` jail itself.

## Cause

The VPS was **powered off from the provider side at 2026-10-13 21:48:55 UTC** and stayed off until 2026-10-14
15:27 UTC. The previous boot's journal shows the QEMU guest agent receiving `guest-shutdown` (mode `powerdown`) from
the hypervisor; systemd reached `poweroff.target` 12 s later. That call only comes from outside the machine: the OVH
control panel or API ("stop"), or an OVH operation on the host node. Nothing on the server asked for it:

- no login: the last interactive SSH login was 2026-07-28; between 20:00 and 21:50 only cron sessions;
- no ops run of this repo at that time; no crontab entry with shutdown/poweroff/reboot;
- unattended-upgrades has `Automatic-Reboot` off (commented out), and its last run on 10-13 (06:16) upgraded only
  `libx11`; a reboot would have come back in minutes anyway.

The same agent receives `guest-fsfreeze` every day at ~19:30 UTC (OVH's automated snapshot/backup), so the guest
agent channel is the provider's. The machine was started again ~17 h 38 min later, on the newer kernel already
installed on disk.

**Owner action:** OVH control panel → the VPS → history/tasks and the account e-mail for 2026-10-13 ~21:48 UTC: was it
a manual "stop", an OVH intervention or maintenance, a billing/abuse action, and who started it on 10-14 at 15:27?
That decides whether we need an alert from OVH or a different plan.

## Fix

| What | Why | Where |
|---|---|---|
| External uptime check with an alert to the owner (API readiness + `https://nabd.plus/ar`, every minute). | 17 h passed before anyone acted; nothing on the host can report its own power-off. | Owner action (UptimeRobot / Better Stack free tier) or a scheduled GitHub workflow; proposed in the next ops PR. |
| Backups off the server. | The only backups are on the same disk (`/opt/nabdah/backups`); a host that does not come back takes them with it. The 10-14 backup was skipped. | D-33 (build session item 6). |
| Staging on its own host. | Staging shares this host (disabled since 2026-10-04), so CI smoke tests lost their API with it. | Build session item 5. |
| Container memory limits. | No container has a memory limit (`mem_limit=0`) and the committed memory is ~300 % of RAM (`sar -r` `%commit`); not the cause today, but one runaway container can take the whole host. | Deploy of `main` (item 3) brings the compose file from `main`; limits checked there. |
| Kernel updates without a surprise. | A newer kernel was on disk and only loaded at the next boot. | Proposal: unattended-upgrades `Automatic-Reboot` at a set low-traffic hour (e.g. 02:30 Asia/Riyadh), so a reboot is planned and short; owner decides. |
