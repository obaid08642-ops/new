## What it was not

- **Not memory:** no OOM kill in the kernel log for the last 48 h; `OOMKilled=false` on every container; 1.7 GB available
  now, swap 4 GB almost unused. (Risk noted below, but not the cause.)
- **Not disk:** `/` 68 % (13 GB free), inodes 15 %.
- **Not a crash or a hang:** the stop was orderly (exit 0 / SIGTERM in container order, fail2ban stopping cleanly),
  no hung-task, soft-lockup, I/O or file-system error in the kernel log.
- **Not the application:** no container died before the shutdown; container logs carry no fatal error.
- **Not the firewall or fail2ban:** UFW allows 22/80/443, and a firewall or ban cannot explain a host that logged a
  shutdown and nothing for 17 h. One side note: on 2026-10-14 fail2ban banned `20.115.x.x` from 15:54 to 16:54; that
  range is Azure, where GitHub-hosted runners run, so an SSH timeout from a runner in that hour (after the host was
  back) may have been a ban. The ops workflow authenticates with a key on the first try, so it should not trip the
  `sshd` jail itself; the follow-up read checks which address it was.

## Cause

The VPS was **powered off cleanly at 2026-10-13 21:49 UTC and stayed off until 2026-10-14 15:27 UTC**. A clean stop
that does not come back by itself is a *halt/power-off*, not a reboot: an unattended-upgrades reboot (or a kernel
panic + watchdog) would have been back within minutes. The new kernel on the next boot shows a kernel update had been
installed before the stop, and was only picked up when the machine was started again 17 h later.

So the trigger was one of:

1. a stop from the provider (OVH control panel / API, or an OVH maintenance on the host node), then a start ~17 h later;
2. a `shutdown -h` / `poweroff` on the host (a person or a script) — no deploy script in `/opt/nabdah/deploy/scripts`
   contains one, and no ops run of this repo ran at that time.

Which of the two cannot be decided from the boot list alone; the follow-up read below settles it.

## Fix

| What | Why | Where |
|---|---|---|
| External uptime check with an alert to the owner (API readiness + `https://nabd.plus/ar`, every minute). | 17 h passed before anyone acted; nothing on the host can report its own power-off. | Owner action (UptimeRobot / Better Stack free tier) or a scheduled GitHub workflow; proposed in the next ops PR. |
| Backups off the server. | The only backups are on the same disk (`/opt/nabdah/backups`); a host that does not come back takes them with it. The 10-14 backup was skipped. | D-33 (build session item 6). |
| Staging on its own host. | Staging shares this host (disabled since 2026-10-04), so CI smoke tests lost their API with it. | Build session item 5. |
| Container memory limits. | No container has a memory limit (`mem_limit=0`) and the committed memory is ~300 % of RAM (`sar -r` `%commit`); not the cause today, but one runaway container can take the whole host. | Deploy of `main` (item 3) brings the compose file from `main`; limits checked there. |
| Kernel updates without a surprise. | The kernel update waited for the next boot. | Proposal: unattended-upgrades `Automatic-Reboot` at a set low-traffic hour (e.g. 02:30 Asia/Riyadh), so a reboot is planned and short; owner decides. |
