## 1. الملخص التنفيذي

كانت تجربة الدواء السابقة تعتمد في أجزاء مهمة منها على حالة واجهة محلية: يمكن للمستخدم أن يظهر أنه أخذ الجرعة من دون تسجيلها في الخلفية، ويمكن أن يظهر المخزون أو تذكير إعادة الطلب من حقول لا يعيدها الخادم. كما كانت قائمة التذكيرات تختزل جميع مواعيد الدواء في حالة يومية واحدة، ولا تفرض منطقة زمنية أو تمنع تسجيل نتيجة الجرعة نفسها أكثر من مرة في اليوم.

تعالج هذه المرحلة تلك الفجوات. أصبح التذكير يتطلب **منطقة زمنية بصيغة IANA** ومواعيد 24 ساعة صالحة، وتعرض الواجهة كل موعد جرعة على حدة. تسجل واجهة المستخدم فقط نتيجتين صريحتين هما «تم أخذها» و«تم التخطي»، وتُرفض المحاولة المكررة لنفس الموعد في اليوم المحلي للمريض. لا توجد «غفوة» محلية وهمية، ولا تعديل تلقائي للجرعة، ولا ادعاء بوصول إشعار لا يمكن إثباته.

## 2. التغييرات المنفذة

### 2.1 عقد الخلفية لتذكيرات الدواء

تم توسيع نموذج `MedicationReminder` بحقل `time_zone`، مع اعتماد صيغة المنطقة الزمنية من قاعدة IANA. عند إنشاء أو تعديل أي تذكير تتحقق الخلفية من اسم الدواء، والجرعة، وعدد الوحدات، والمدة، والمخزون، وصيغة المواعيد `HH:mm`، وصلاحية التاريخ، واتساق تاريخ النهاية مع تاريخ البداية. تقبل الواجهة التكرار اليومي والأسبوعي وعند الحاجة فقط؛ لم يعد هناك تحويل صامت وغير صحيح للتكرار الشهري إلى أسبوعي.

تسجل الخلفية نتيجة واحدة فقط لكل **موعد جرعة** في اليوم المحسوب بمنطقة المريض الزمنية. يجب أن تكون نتيجة الجرعة واحدة من `taken` أو `skipped` أو `missed`، وأن يطابق `time_key` موعداً موجوداً في التذكير. إذا سبق تسجيل هذا الموعد في اليوم نفسه، تعيد الخدمة تعارضاً ولا تضيف سجلاً جديداً.

| السلوك | التنفيذ |
|---|---|
| ملكية التذكير | كل قراءة أو تعديل أو حذف أو تسجيل جرعة يقيد بـ `patient_id` للمستخدم المصادق عليه. |
| المنطقة الزمنية | إلزامية للتذكيرات المنشأة أو المعدلة من التطبيق؛ تتحقق منها الخلفية بصيغة IANA. |
| صحة الموعد | مواعيد 24 ساعة فقط، مع إزالة التكرارات وترتيبها. |
| منع التكرار | لا يمكن تسجيل نتيجتين للموعد نفسه في اليوم المحلي نفسه. |
| صحة الإدخال | حدود للمدة وعدد الوحدات والمخزون، والتحقق من التواريخ. |
| قائمة اليوم | `today_doses` تعرض حالة كل وقت جرعة، مع ملخص الالتزام اليومي. |
| الأدوية المزمنة | تعيد حالة إعادة التعبئة الفعلية، وتاريخها، وعدد الأيام المتبقية، والمخزون المتاح فقط إن كان مسجلاً. |

### 2.2 واجهات تطبيق المريض

أعيد بناء أربع شاشات لتستهلك العقود الفعلية بدل الحالة المحلية أو البيانات التي لا يدعمها الخادم.

| الشاشة | الوظائف المكتملة |
|---|---|
| `health/medications.tsx` | لوحة أدوية من بيانات `GET /health/reminders`، تعرض ملخص جرعات اليوم وروابط التذكيرات والأدوية المزمنة والوصفات. |
| `health/medication-reminder-list.tsx` | قائمة فعلية لكل تذكير ولكل موعد في اليوم، مع تسجيل «تم أخذها» أو «تم التخطي» عبر `POST /health/reminders/:id/log`، وتعديل أو إيقاف التذكير عبر الخلفية. |
| `health/medication-reminder-add.tsx` | إنشاء وتعديل تذكير باستخدام `POST/PATCH /health/reminders`، مع المنطقة الزمنية، المواعيد، التكرار، المدة، وحالة الدواء المزمن. |
| `health/chronic-medications.tsx` | أدوية مزمنة من `GET /health/chronic-meds` مع معلومات إعادة التعبئة الحقيقية، وبدء طلب إعادة التعبئة أو التأجيل أو إيقاف متابعته عبر المسارات الخلفية. |

تتضمن الشاشات حالات تحميل، وفشل قابل لإعادة المحاولة، وحالة فارغة صادقة، وحالة حفظ أو تنفيذ صريحة. كل النصوص عربية والاتجاه البصري RTL. لا تظهر الواجهات شريط مخزون بافتراض إجمالي غير موجود، ولا تعرض زر غفوة أو طلباً محلياً يبدو وكأنه تم تنفيذه في الخلفية.

### 2.3 سلامة الدواء وإعادة التعبئة

> **هذه المرحلة تنظم التذكير والتسجيل ولا تقدم تشخيصاً أو تعدل علاجاً أو جرعة.**

نصوص الواجهة تذكّر المستخدم باتباع الوصفة أو تعليمات مقدم الرعاية. عند اختيار بدء إعادة التعبئة، يتم ذلك بفعل المستخدم الصريح فقط؛ لا تنشئ الواجهة طلباً تلقائياً، والخلفية تبقى مسؤولة عن التحقق من عنوان التوصيل وإنشاء الطلب الحقيقي. وفي حال الفشل، تعرض الواجهة أن الطلب لم يكتمل بدلاً من إعلان نجاح غير مؤكد.

لا تَعِد الواجهة بوصول إشعار على الجهاز؛ فهي تحفظ جدول التذكير ونتائج الجرعات، بينما تسليم الإشعار الفعلي وربطه بالقنوات سيكتمل ضمن مرحلة التنبيهات اللاحقة.

## 3. اختبارات العقد المضافة

أضيف ملف اختبار مخصص لخدمة الصحة يغطي عقد Phase 3 في الخلفية:

1. إنشاء تذكير مملوك للمريض مع منطقة زمنية صالحة ومواعيد 24 ساعة مرتبة وغير مكررة.
2. رفض منطقة زمنية غير صالحة أو موعد لا يتبع صيغة 24 ساعة.
3. تسجيل نتيجة واحدة للموعد نفسه في يوم المريض المحلي، ثم رفض التكرار.
4. رفض تسجيل نتيجة لموعد غير موجود ضمن جدول التذكير.

## 4. التحقق المنفذ

نفذت أوامر التحقق التالية في النسخة المحلية المستعادة:

```bash
# الخلفية
cd /home/ubuntu/nabdah-phase1-work/backend
npm run build
npm test -- --runInBand

# تطبيق المريض
cd /home/ubuntu/nabdah-phase1-work/patient/nabd_plus
npm run typecheck
npm test -- --runInBand
npx expo export --platform web --output-dir dist-phase3 --no-bytecode --clear --max-workers 1
```

نجح بناء الخلفية واختباراتها الكاملة: **40 مجموعة و273 اختباراً**. ونجح فحص أنواع تطبيق المريض واختباراته: **7 مجموعات و23 اختباراً**. كما نجح التصدير البديل للويب بعد إعادة بناء ذاكرة Metro المؤقتة، وأنتج حزمة إدخال بحجم 9.4 MB.

ظهرت أثناء اختبارات الخلفية تحذيرات موجودة في المصدر المستعاد تتعلق بمسار Mongoose محجوز وفهارس مكررة، ورسائل اختبارية لفشل قنوات خارجية بطريقة fail-closed. لم تمنع هذه الرسائل البناء أو الاختبارات، وليست سلوكاً جديداً في Phase 3؛ سُجلت للمراجعة في المرحلة النهائية ولا تمثل نجاحاً وهمياً.

## 5. ملاحظات الاستعادة المحلية

فقدت بيئة التنفيذ مجلد العمل المحلي السابق، لذلك أعيدت استعادة المصدر من الفرع المعتمد واستخراج الأرشيفات محلياً. أثناء ذلك استعيدت أيضاً إصلاحات خط الأساس اللازمة لاستمرار العمل، ومنها سياسة CORS مشتركة لاتصالات WebSocket، ومنع تسجيل بيانات OTP الحساسة في خدمة الرسائل، وفشل بريد مقدمي الخدمة بشكل آمن عند غياب بيانات الاعتماد، وإخفاء رمز دعوة المشغل من الاستجابة، وتصحيح ملف القفل الخاص بتطبيق المريض حتى يمكن تثبيت الاعتمادات من المصدر الرسمي.

لا يحتوي المستودع المستعاد على ملفات الوحدات المستخرجة تحت تتبع Git؛ لذلك يظهر مجلد كل وحدة محلياً كمحتوى مستخرج غير متعقب إلى جانب الأرشيفات الأصلية. هذا لا يمثل التزاماً أو رفعاً، ولا ينبغي تنفيذ أي `git add` أو `commit` أو `push` قبل تعليماتكم الصريحة بعد اكتمال جميع المراحل.
