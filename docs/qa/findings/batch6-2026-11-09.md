# QA batch 6 findings (lane Y, 2026-11-09): SY-01

## SY-01 Nightly jobs run once and report
**Status stays PARTIAL; the evidence changed.** The row named `j_jobs.py`, which is the medical jobs board (`/recruitment/jobs`), not the scheduled jobs: that was never evidence for SY-01.

**What now proves the claim (runs in CI and locally):**
- `backend/src/common/cron-jobs-run-once.spec.ts` scans all backend source for `@Cron` / `@Interval` (the spec requires at least 35 and fails if the scan finds fewer; a line count today gives 43). Each must carry `@ScheduledOnce` (the Redis lease: N workers on one tick run the job once) or be one of five documented exceptions, each with its own once-guard or a reason: `beat` (worker heartbeat, per process on purpose), `scheduledKeepAlive` (this process's SMTP connection), `sweep` in `seo-indexing.service.ts` (its own Mongo lease), `sweep` in `durable-events.processor.ts` (R2 atomic Mongo claim), `daily` in `finance-integrity.service.ts` (one run per kind and day through a unique insert in `finance_integrity_runs`). A stale exception fails the spec. Removing the lease from a job fails it (checked by hand on `db-integrity.service.ts`).
- The five nightly jobs are pinned by schedule and method: `finance-integrity` `daily` 01:40, `audit-chain.verifier` `nightly` 02:15, `consistency` `scheduledReconcile` 03:17, `db-integrity` `nightly` 03:20, `event-reliability/reconciliation` `nightly` 04:17 (UTC); no two share a minute; each has a place it reports to (admin read route or its report collection).
- The lease itself is proved with real Redis in `scheduled-once.spec.ts` (2 and 8 workers on one tick -> 1 run, late tick not rerun, dead worker's lease expires).

**Why there is no live journey, and what would make one possible:**
1. A nightly job fires at its own time of day; the live gate cannot wait for 01:40-04:17 UTC.
2. No HTTP route reaches the *leased entry point* of any of the five. Where a route exists it calls the plain work method, not the scheduled one: `POST /consistency/reconcile` and `POST /events/reconciliation/run` call `reconcile()` (the cron is `scheduledReconcile()` / `nightly()`), `GET .../audit/chain` (admin-security.controller.ts:55) verifies the audit chain through `verifyChain()` (the cron is `AdminAuditChainVerifier.nightly()`), and finance `daily()` and `db-integrity` `nightly()` can only be read (`GET /admin/finance/integrity`, `GET /admin/db-integrity`). So a request can never exercise the lease.
3. The live gate runs one backend process, so "no double run across api and worker" cannot be observed there.
A journey would need (a) a second backend process in the gate (role `worker`) and (b) an admin or test-only trigger that fires the same tick on both. Neither exists; adding a trigger to production code only for a test is a product decision, not made here. **Owner/lead decision:** accept the contract spec as COVERED for SY-01, or ask for the trigger and the second process.

**Known limit of the contract:** it proves every job is leased, not that a job's own work is idempotent after a lease loss (`cron_lease_lost` is logged; the running job cannot be cancelled, R3).
