# QA PT-38 (lane Y, 2026-11-09): deep links into a booking or chat

**Row:** `NOT COVERED` -> `PARTIAL`. Booking links are covered on every path; chat links are covered except one product gap, so the row stays PARTIAL (same rule as batch 5: a scenario blocked by a product gap is not claimed as done).

## What is proven (all run in CI; the web test also runs locally)
**App (already on main, found while scoring; its header names PT-38):** `patient-app/src/__tests__/qa/deep-links-push.test.tsx` - a tapped push for an appointment, booking, chat or order opens the right screen with the right id; signed out nothing is opened until sign-in and then the tap is answered; malformed data never throws or opens a screen with an empty id. `patient-app/src/__tests__/native-intent.test.ts` and `src/hooks/usePushNotifications.routes.test.ts` - the web-link and backend-route translators land on screens that exist, every associated-domain path has an app mapping, and the intent filters equal the AASA list. A chat notification's target is `/consultations/appointments/<booking id>` (`notifications.service.ts:671`), which the app opens as the appointment detail, where the conversation lives.

**Web (new, `patient-web/tests/deep-link-return.test.ts`, 11 tests):** the real chain `proxy.ts` -> `x-nabd-path` -> `requirePatientAccess()` -> `?next=` -> `safeNextPath()`, with only next-intl's middleware, `cookies()` and `headers()` stood in. In all six locales a signed-out request for `/<l>/appointments/<id>`, `/<l>/appointments/<id>?pay=1`, `/<l>/chat/<id>` and `/<l>/consultations/booking-status?appointmentId=<id>` redirects to `/<l>/login?next=<that exact page>`; the same pages with an access cookie are not redirected; the way back survives the round trip; `safeNextPath` keeps those paths and drops off-site, protocol-relative, backslash, control-character, login-loop, unknown-locale and over-long values, and an unsafe remembered path gives the plain sign-in. Mutation checked: making the redirect drop `next` fails the locale tests.
Already on main for the web pages themselves: `appointments-ssr.test.ts` and `chat-ssr.test.ts`.

## Not covered
- **Product gap (H/S), recorded with file:line:** a **web chat link opened in the app lands on the appointments list, not on the conversation** - `patient-app/src/navigation/webLinkMap.ts:100-102` (`case 'chat': return '/consultations/appointments'`, comment: "a thread id is not an app appointment id"), pinned as intended by `patient-app/src/__tests__/native-intent.test.ts:118`. Pushes are fine (they carry the booking id); only a shared `https://nabd.plus/<l>/chat/<threadId>` link loses the thread. A fix needs the app to resolve a thread id to its booking (`GET` thread -> `booking_id`) or the web to put the booking id in the shared link; either is a product decision.
- **No live journey** for the signed-in landing (sign in, then open an appointment/chat link): it needs a Playwright sign-in plus a seeded appointment and thread, and I could not run the stack here, so I did not add one blind to a gate every PR depends on. The unit chain above covers the redirect and the return path; the page render itself is `appointments-ssr` / `chat-ssr`.
- Installed-app behaviour on a real device (universal links / app links opening the app) is the native E2E's area, not covered here.


## Update (lane X, 2026-11-09): the chat link gap is closed
A web chat link (`/<l>/chat/<threadId>`) now opens `patient-app/app/consultations/chat-link.tsx`, which asks `GET /chat/threads/:id/permissions` for `booking_id` and replaces itself with the conversation of that booking (`chat-with-doctor?appointmentId=`). A thread the server does not give shows the error with a retry and the appointments. Tests: `patient-app/src/__tests__/qa/chat-link.test.tsx`; `native-intent.test.ts` now expects the new route. No new strings (existing keys). Still open: the live journey and the real device hand-over.
