# التدقيق الأولي للمصدر — المرحلة 2

**الحالة:** نتائج مصدرية أولية فقط؛ لا تثبت اتصالاً حياً بالخلفية أو جاهزية إنتاج.  
**النطاق المعتمد:** Web App للمريض فقط. لا يدخل تحويل لوحة الإدارة أو تطبيق مزودي الخدمات إلى Web ضمن هذا العمل.

## أدلة المصدر المفحوصة

تم استنساخ الفرع `main` من مستودع المستخدم وفك أرشيف تطبيق المريض وأرشيف الخلفية إلى مساحة تدقيق منفصلة بعد فحص مسارات الأرشيف. يحتوي تطبيق المريض على Expo Router وReact Native/Expo SDK 57، والـBackend على NestJS. لم تُشغّل أي شفرة مستخدم أو اختبار أو خدمة خارجية أثناء هذا التدقيق الأولي.

| الدليل | النتيجة الأولية |
|---|---|
| شجرة مسارات المريض | تم إحصاء **249 route file** فعلياً داخل `app/`، موزعة على المصادقة، التبويبات، الصيدلية، التشخيص، الحجوزات، الأسرة، الصحة، التأمين، التغذية، الحمل، الصحة النفسية، الذكاء الاصطناعي، المحفظة، التقارير، الدعم والطوارئ. |
| بنية التنقل | الجذر يضم Redux وApp/Socket/Cart/Diagnostics/Consultations providers وOffline Banner وNotification Handler؛ التبويبات الرئيسة هي المنزل والاستشارات والصيدلية والتشخيص والخدمات والصحة. |
| عنوان الخلفية | عميل الهاتف يكوّن قاعدة API من `EXPO_PUBLIC_API_URL` أو `https://api.nabd.plus/api/v1`. الخلفية تضبط `api` كـglobal prefix وURI version `v1`، ما يثبت مسار `/api/v1`. |
| المصادقة | المصدر يؤكد register/login/guest/OTP/reset/social/refresh، وحماية JWT، وrate limiting، ودورة refresh ذات queue ومدة قصوى للجلسة على الهاتف. |
| عقود الويب الخاصة | توجد عقود فعلية للملف الشخصي، medical profile، الطلبات، الصيدلية، المختبرات، الأشعة، العائلة، الصحة، الذكاء الاصطناعي، الدردشة/المكالمات، الإشعارات، التأمين، المحفظة والمحتوى. |

## جرد API الثابت الأولي

استخراج `apiFetch()` من تطبيق المريض أظهر استدعاءات تحت المجالات: `auth` و`users` و`medical-profile` و`health` و`family` و`medicines` و`cart` و`orders` و`care` و`labs` و`radiology` و`home-care` و`insurance` و`wallet` و`notifications` و`support` و`articles` و`community` و`maternity` و`nutrition` و`mental-health` و`wearables` و`ai` و`emergency` و`loyalty` و`medical-reports`. يجب ألا يُعامل هذا الاستخراج بوصفه عقداً نهائياً؛ إذ توجد مسارات ديناميكية وطلبات عبر clients أخرى، وستقارن القائمة بتوثيق API وبـcontrollers الخلفية.

## ملاحظات وفجوات مرشحة لا يجوز نقلها تلقائياً إلى الويب

| المعرف المقترح | الدليل في المصدر | المخاطرة | قرار المرحلة التالية |
|---|---|---|---|
| `G-AUTH-001` | `app/_layout.tsx` ينشئ local guest shell عند تعذر إعادة المصادقة ويضع `token: 'guest_token'`. | نجاح أو هوية محلية غير حقيقية عند غياب الخلفية. | لا ينقل للويب؛ يعتمد guest UI فقط على استجابة `/auth/guest` حقيقية أو يظهر حالة اتصال/خطأ صريحة. |
| `G-I18N-001` | جذر التطبيق يستدعي `I18nManager.forceRTL(true)` بلا شرط لغة. | قد يكسر الإنجليزية/LTR وتناسق الويب متعدد اللغات. | الويب يبني direction من locale على مستوى الوثيقة والroute، مع اختبار RTL/LTR. |
| `G-DATA-001` | شاشة الصيدلية تستخدم `CATEGORIES` ثابتة قبل جلب `/medicines/categories`، وتعطي السعر `0` عند نقصه. | تصنيفات أو أسعار ظاهرية لا تمثل الكتالوج الحقيقي. | أي fallback عام في الويب يجب أن يكون حالة تحميل/عدم توفر؛ لا خصائص طبية أو مالية مصطنعة. |
| `G-DATA-002` | شاشة التشخيص تحول فشل `/labs/*` و`/radiology/services` و`/providers` إلى `{ data: [] }`. | إخفاء فشل العقد كأنه empty state حقيقي. | فصل error عن empty في الويب وفتح gap إذا كانت الاستجابة/العقد غير متاح. |
| `G-FLOW-001` | فلاتر التشخيص الأساسية محلية حالياً، بينما controller الخلفي يدعم فلاتر مثل search/home/highest_rated/nearest/lowest_price. | تفاوت نتائج ومقياس غير حقيقي للمريض. | الويب يربط الفلاتر إلى query parameters المدعومة؛ المتبقي يوثق كفجوة عقد. |
| `G-DATA-003` | مدخل الاستشارات يحتوي قائمة شركات/فئات تأمين ثابتة وfallback route بمعرف `d1` عند غياب المعرف. | بيانات تأمين/معرف طبيب غير موثقة؛ خطر توجيه خاطئ. | الويب يستخدم `/insurance/companies` وما يثبته العقد؛ لا معرفات أو قوائم ثابتة لقرار حجز. |
| `G-ERROR-001` | توجد catch صامتة أو تحويل إلى قوائم فارغة في عدة شاشات، منها wallet/settings/insurance/pharmacy. | عدم وضوح الأعطال للمريض وصعوبة تتبع التكامل. | تدقيق كل موضع وتصنيف ما إذا كان cache مقبولاً، empty state، أو gap يجب إصلاحه. |

## عقود خلفية عالية الأولوية تم التحقق منها في المصدر

| المجال | أمثلة من العقد المصدرّي |
|---|---|
| المصادقة | `POST /auth/register`، `login`، `send-otp`، `verify-otp`، `reset-password`، `social-login`، `refresh`، وإجراءات جلسات/consent. |
| ملف المريض | `GET/PATCH /users/me/profile`، إعدادات الإشعار والخصوصية والأمان، sessions، wishlist، وإدارة العناوين في controller منفصل. |
| الملف الطبي | `GET/PATCH /medical-profile` وتحولات الأمراض المزمنة والحساسيات والعمليات والأدوية الطويلة، وhealth-passport token. |
| الطلبات | create/mine/reorder/cancel/tracking/owner-checked details/basket approval، مع تفويض منفصل للصيدلية والإدارة والتوصيل. |
| المختبر والأشعة | catalog عام، تفاصيل، bookings للمريض، إلغاء، tracking، documents وinsurance؛ وتوجد فلاتر فعلية في controller للبحث والسعر والقرب والتوفر المنزلي. |

## الخطوات التالية قبل التنفيذ الجوهري

يستكمل التدقيق بمقارنة route-by-route مع استدعاءات API وحالات التحميل/الفراغ/الخطأ وguards الخلفية، ثم تُنشأ مصفوفة التكافؤ وسجل العقود المفقودة. عند تزويد ملف API الكامل، يضاف كدليل مستقل ويطابق بالـcontrollers والمصدر بدلاً من استبدالهما.

| الفحص | النتيجة | الأثر |
|---|---|---|
| `patient-app: npm run typecheck` | نجح بلا أخطاء ظاهرة. | خط أساس صالح للأنواع في تطبيق المريض. |
| `patient-app: npm test -- --runInBand` | نجح: **22 suites** و**56 tests**. | تأكدت مجموعة الاختبارات الحالية لتطبيق المريض، وليست بديلاً عن اختبار الويب أو E2E. |
| `backend-app: npm test -- --runInBand` | بدأ ونجحت suites كثيرة تشمل التأمين والصيدلية والطلبات والرعاية والأشعة والمختبرات وSEO وLiveKit وغيرها، لكنه **توقف قبل ملخص Jest النهائي بسبب ضغط ذاكرة البيئة**. | لا يصح الادعاء بأن فحوص الخلفية كاملة نجحت. يعاد تشغيلها لاحقاً على دفعات أو في بيئة ذات ذاكرة كافية قبل أي اعتماد تكامل كامل. |
| اعتماديات المصدر | ثبتت مؤقتاً مع `--ignore-scripts` لأجل الاختبار ثم أزيلت لتخفيف الموارد. سجّل مدير الحزم 18 vulnerability في شجرة المريض و28 في شجرة الخلفية قبل تحليل تفصيلي. | تسجل فحص dependency/SBOM وقرار التحديث في بوابة الأمن؛ لا يطبّق إصلاح تلقائي أو breaking update الآن. |

> تحذيرات الاختبار المتعلقة بتكوين S3 غير موجود أو أسرار webhook غير موجودة أو مدخل Excel فاسد كانت داخل سيناريوهات اختبار متعمدة أو بيئة بلا أسرار؛ لا تعامل كدليل على تشغيل إنتاجي. تحذيرات مفاتيح Mongoose المحجوزة والفهارس المكررة تسجل كتقنية للتقييم، ولا تعدل أثناء تدقيق المصدر بلا اختبار تأثير.

## فحص ساكن شامل لتطبيق المريض

شغّل محلل ساكن مخصص على **551 ملفاً** قابلاً للقراءة في المصدر، بينها **250 ملف route** تحت `app/` و**120 ملفاً** يحوي استدعاءات API مباشرة. لم يشغّل المحلل أي شفرة تطبيق أو اتصالاً بالخلفية؛ اقتصر على قراءة النصوص واستخراج علامات المراجعة.

| الإشارة | العدد | تفسير القرار |
|---|---:|---|
| `@ts-nocheck` أو `as any` | 227 | مؤشر ضعف type safety في المصدر، لا دليل تلقائي على خطأ وظيفي. ويب المريض سيستخدم TypeScript strict وschemas لعقود API. |
| محتوى مرشح لأن يكون synthetic/guest/mock | 27 | يراجع كل موضع قبل النقل؛ أهمها local guest shell والقوائم أو المعرفات الاحتياطية. لا يعتمد أي منها إنتاجياً في الويب. |
| `catch {}` صامت | 24 | يصنّف كل موضع إلى cache مسموح أو حالة خطأ مفقودة أو فجوة عقد؛ الويب يميّز error وempty وoffline. |
| تحويل catch إلى قائمة بيانات فارغة | 1 | يسجل كـ`G-DATA-002` ويمنع إخفاء عطل API كأنه غياب نتائج. |
| فرض RTL | 1 | يسجل كـ`G-I18N-001` ويستبدل بقرار locale لكل route/document. |

يبقى ملف المحلل والـJSON الناتج في مساحة تدقيق منفصلة، ولا يدخلان حزمة إنتاج Web App.
