## ما بُني ونُفّذ فعلياً

بُني تطبيق الويب باستخدام **Next.js 16.3.1 App Router** و**TypeScript strict**. الواجهة تدعم اللغات الست المطابقة لتطبيق المريض: `ar`, `en`, `ur`, `hi`, `bn`, `fil`، مع RTL للعربية والأردية فقط. النظام البصري Premium خاص بنبض بلس، يعتمد خط الجهاز القانوني (من دون تضمين SF)، أيقونات ورسوم Vector أصلية، وحركة وصولية قصيرة تحترم `prefers-reduced-motion`.

| المجال | المنفذ |
|---|---|
| المصادقة والجلسة | تسجيل دخول بكلمة المرور، refresh واحد مقيد، logout، وcookies `httpOnly`. لا يوجد Bearer token في المتصفح أو `localStorage`. دخول OTP غير مفعّل لأن الخلفية لا تؤسس جلسة آمنة بعد التحقق. |
| BFF والأمن | BFF خادمي، allowlist لمسارات المتصفح يتيح قراءات `GET` للطلبات الموثقة فقط ويمنع الكتابة/الموارد غير المدرجة. أي فشل شبكة يتحول إلى `503 upstream_unavailable` بلا حمولة حساسة. |
| واجهات المريض القرائية | لوحة المريض، الطلبات وتفاصيلها، المواعيد وتفاصيلها، الملف الصحي بالحقل المسموح، الأدوية وتفاصيلها، التشخيص وتفاصيل الحجوزات، الرعاية المنزلية كقائمة، الأسرة كقائمة محدودة، الإشعارات، الصحة، التذكيرات، الوصفات كقائمة مقيدة، والمحادثات كقائمة وصفية. |
| الحماية والخصوصية | اختبارات SSR تمنع تسرب التوكنات والمعرّفات والبيانات السريرية والأسعار والتقارير والملفات حيث لا توجد ضرورة عرض. اختبارات Sandbox للتحقق من المالك/الحساب الآخر عندما يسمح العقد بمعرف مورد. |
| الظهور العام | صفحة عامة بست لغات، canonical وhreflang وrobots وsitemap وmanifest و`llms.txt` وOpen Graph/Twitter وJSON-LD محافظ. الصفحات الخاصة غير مفهرسة؛ الكتالوج المختلط يبقى `noindex`. |

## نتائج التحقق التي يجب تدقيقها

| التحقق | النتيجة المثبتة |
|---|---|
| `pnpm check` | ناجح. |
| `pnpm test` | 55 ملف اختبار ناجحاً و94 اختباراً ناجحاً. توجد 14 مجموعة Sandbox و23 اختبار Sandbox متخطاة عمداً في التشغيل المحلي لتجنب حدود معدل API. |
| `pnpm build` | ناجح في Next.js 16.3.1. |
| Sandbox العلامات الحيوية | إعادة تحقق منفردة ناجحة: قراءة ذاتية فقط للمالك و`401` بلا جلسة، بلا طباعة قيم صحية أو تعديل بيانات. |
| Sandbox التخصصات | اكتشاف التخصصات والأطباء غير فارغ، لكن 42 تخصصاً أعادوا حقل `count` الصفري؛ لا تعرض الواجهة عدّاً مشتقاً محلياً. |

أحدث الالتزامات بعد دورة `check/test/build` كانت توثيقية/تدقيقية وسكربتات قراءة محلية فقط، ولم تغيّر كود التطبيق المنتج. مع ذلك، يرجى تشغيل `pnpm check && pnpm test && pnpm build` مرة أخرى داخل بيئة المراجعة قبل أي اعتماد أو دمج.

## الفجوات الخلفية الحاكمة — لا ينبغي الالتفاف عليها في الويب

| الفجوة | الواقع الحالي | المطلوب من Backend |
|---|---|---|
| G-HOME-001 | قائمة الرعاية المنزلية فقط؛ لا تفاصيل أو تتبع أو تقرير. | `GET /home-care/bookings/{bookingId}` مع الملكية داخل الاستعلام و`404` لغير المالك وDTO عرض محدود. |
| G-OTP-001 | OTP غير مفعّل في الويب. | جلسة مباشرة أو `exchange_token` قصير العمر يمكن استبداله خادمياً، بلا توكن في URL أو المتصفح. |
| G-PROFILE-001 | لا هوية عرض موثوقة كاملة للملف. | DTO عرض منفصل للهوية دون بريد/هاتف/معرفات/مسارات تخزين. |
| G-FAMILY-001 | لا أسماء عرض موثوقة لأفراد العائلة. | DTO مقيد: `display_name`, `role`, `joined_at`. |
| G-PRESCRIPTION-001 | توجد عملية تفاصيل في OpenAPI ولكنها بلا `security` أو schema أو اختبار ملكية بعد. | Bearer security، DTO نجاح/خطأ مقيد، و`404` لغير المالك، ثم اختبار Sandbox owner/other. |
| G-CHAT-001 | توجد عملية تفاصيل thread في OpenAPI ولكنها بلا `security` أو schema أو اختبار ملكية بعد. | عقد تفاصيل ورسائل مقيد مع عضوية خادمية وpaging، و`404` لغير المشارك. |
| G-FILE-001 / G-RTC-001 | لا رفع وثائق أو OCR أو مكالمات أو غرف آنية. | عقود رفع مقيدة، وروابط/رموز قصيرة العمر مربوطة بالملكية والغرض. |
| G-SEO-002 | كتالوج الدواء العام غير مؤهل للفهرسة. | API عامة لعناصر منشورة ومصنفة `entity_type` و`is_published` و`slug` ثابت. |
| G-DATA-004 | عد مزودي التخصصات صفر رغم اكتشاف سجلات غير فارغة. | إصلاح مصدر العدّ أو تعريف contract منشور مثل `published_provider_count`؛ لا يُشتق في الواجهة. |
| G-OAPI-001/002 | OpenAPI الحالية بلا `servers`، والعمليات الحساسة المذكورة أعلاه بلا response schemas. | استكمال servers وsecurity annotations وDTOs وresponses/errors ثم إعادة تصدير المواصفة. |

## نتيجة فحص OpenAPI الأخير

فُحصت نسختا OpenAPI المسلّمتان محلياً دون استدعاء الخلفية أو كشف بيانات. ظهرت `GET /prescriptions/{id}` و`GET /chat/threads/{threadId}` و`POST /auth/verify-otp`، لكن كل واحدة تفتقر إلى security على مستوى العملية وresponse schema مفيد، وتعلن رمز نجاح فقط. مسار تفاصيل الرعاية المنزلية وواجهات الكتالوج العام المنشور غير موجودة في المواصفة. لهذا **لم تُبنَ** صفحات التفاصيل أو عمليات OTP اعتماداً على هذه المسارات.

## المطلوب من المراجع

1. راجع BFF والجلسة وcookies وallowlists، وتأكد أن كل مسار خاص خادمي فقط ولا يسمح بالكتابة من المتصفح.
2. راجع اختبارات SSR وSandbox، خصوصاً BOLA/IDOR ومنع تسرب التوكنات وبيانات المريض والأسعار والتقارير.
3. راجع i18n والـRTL/LTR والتصميم Premium والحركة والوصولية على الهاتف وسطح المكتب.
4. راجع سياسة SEO/AEO/GEO: لا تفهرس أي معلومات مريض أو كتالوج مختلط، ولا تضف `Drug` JSON-LD قبل G-SEO-002.
5. راجع OpenAPI وBackend للفجوات أعلاه. بعد كل عقد جديد، نفّذ بالترتيب: parser/allowlist في BFF، اختبار Sandbox owner/other، اختبار SSR، ثم UI قرائي أو عملي ضمن حدود العقد.
6. لا تقترح بيانات mock أو placeholder أو fallback ناجح؛ عند فشل backend أو غياب عقد يجب أن تبقى حالة error/empty/unavailable حقيقية.
7. لا تدمج الفرع بـ`main` ولا تدفع بالقوة قبل أن يقرر مالك المستودع استراتيجية تسوية التباعد.

الهدف من هذه المراجعة هو تحديد ما إذا كانت عقود Backend يمكن تسليمها الآن لاستكمال الرحلات المقفلة بأمان، أو ما إذا كانت هناك ملاحظات على ما تم بناؤه قبل أي دمج أو نشر.

مع الشكر.
