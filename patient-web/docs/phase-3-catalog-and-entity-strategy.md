# استراتيجية الكتالوج والكيانات الطبية — Web App المريض

## المبدأ المعماري

لا يحمل Web App أي قائمة كتالوج طبية أو أسعار أو توافر أو مزودين داخل bundle بوصفها مصدر حقيقة. مصدر الحقيقة هو الخلفية المعتمدة. طبقة الويب تعرض response متحققاً منه، وتستخدم cache محدد الصلاحية لتحسين الأداء فقط؛ وعند فشل الخلفية تعرض حالة خطأ أو نسخة cache موسومة بوقت تحديثها إذا كان المنتج يسمح بذلك، ولا تنشئ عنصر دواء أو مزود أو سعر أو تغطية بديل.

## نموذج الكيانات والهوية

| الكيان | مصدر الحقيقة/العقد المرجعي | المعرف الثابت | المفتاح العام | سياسة العرض |
|---|---|---|---|---|
| الدواء | `medicines` وواجهات medicines/pharmacy | `id` الخلفي غير قابل للتخمين كمرجع عمل | `slug` منشور فقط بعد التحقق من النشاط والملكية والاسم | السعر والمخزون والوصفة من response حي؛ لا تدخل sitemap إلا إذا أقر النشر. |
| الطبيب | `provider_profiles` و`care/doctors` | provider/doctor id | slug منشور يربط إلى entity resolver | الصفحة العامة لا تظهر إلا active/published؛ الحجز والسجل خاصان. |
| منشأة/عيادة/مستشفى | `facilities` أو provider profile موثق | facility id | slug منشور | بيانات الاتصال والخدمات من backend، ولا تدعي الاعتماد/التغطية بغير response. |
| مختبر/أشعة/خدمة منزلية | labs/radiology/home-care catalogs | service/package/provider id | slug منشور إن أقر | catalog عام مؤهل؛ booking/results/docs تتطلب patient ownership. |
| مقال/محتوى تثقيفي | articles CMS المنشور | article id | slug من CMS | public only إذا `published`؛ لا يستخرج منه حكم طبي أو توصية شخصية. |

## التطبيع والتعدد اللغوي

تُخزّن/تعرض الحقول العربية والإنجليزية كما يوردها العقد (`name_ar/name_en` وما يكافئها) عبر adapter typed لكل domain. يحظر تحويل اسم العرض إلى معرف أو استخدام الاسم العادي كمفتاح شراء/حجز. يتخذ URL للكيان المنشور slug ثابتاً، ويرتبط في الخادم بـid موثوق؛ ويطبق redirect canonical فقط عندما يثبت resolver أن الكيان منشور ونشط. تظل المعرفات وسياقات المريض والمواعيد والنتائج خارج URL العامة.

## دورة البيانات والتحديث

1. يطلب المستعرض فهارس البحث والفلاتر بصفحات ومؤشرات/limits تدعمها API؛ لا يحمّل الكتالوج الكامل في العميل، وخصوصاً كتالوج الأدوية الكبير.
2. تتحقق طبقة adapter من schema response وتفصل DTO الشبكة عن نموذج الواجهة، وتبلغ observability عند اختلاف العقد.
3. تبنى كل بطاقة من بيانات مكتملة فقط؛ الحقول التي لا تملكها الاستجابة تظهر على أنها غير متاحة، لا قيمة صفرية أو شعاراً أو تقييمًا افتراضياً.
4. يبطل cache أو يعاد جلبه بعد mutation، وعلى تغيّر السعر/المخزون/التوفر يراجع الخادم في خطوة الحجز/الدفع النهائية.
5. تعتمد التعديلات الكتالوجية في الخلفية وسير الموافقة، ولا يمنح Web App أي CRUD إداري أو نشر ذاتي.

## الفصل بين العام والخاص

| المجال | قابل للنشر العام | محظور من النشر أو الفهرسة |
|---|---|---|
| الأدوية والخدمات والمزودون | فقط entity نشطة ومنشورة ومصرح بنشرها، دون سعر/تغطية/مخزون شخصي | سلة المريض، الوصفات، طلبات المريض، العنوان، سعر شخصي، تفضيلات وتاريخ. |
| المحتوى | المقال المنشور ذو slug صالح | drafts، bookmarks، تعليقات/تذاكر غير منشورة، بيانات مؤلفين خاصة. |
| التقارير والمواعيد | لا شيء | النتائج، المستندات، QR passport، غرف الانتظار، المحادثات، الفيديو، التتبع. |

## اختبارات القبول

تغطي contract tests حقول الهوية والاسم متعدد اللغة والحالة والتسعير والوصفة والنشر، وتغطي E2E عنصر منشور وغير منشور وكيان محذوف/غير نشط واستجابة فارغة وفشل API وتغير السعر قبل checkout. يختبر crawler policy أن كل route خاص يعطي `noindex` ولا يدخل sitemap أو JSON-LD، وأن الـJSON-LD لا يصف حقولاً غير مرئية أو غير مثبتة في المصدر.
